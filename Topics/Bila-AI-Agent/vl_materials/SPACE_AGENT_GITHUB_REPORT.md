# 스페이스 에이전트가 연결된 GitHub 레포를 읽지 않는 문제 — 조사 및 수정 리포트

**날짜:** 2026-07-08
**피드백 출처:** M2 워크로그, `solkit70/CatchUpAI_VL` — 2026-07-05 **창발(changbal)** 스페이스에서 Bila/스페이스 에이전트 테스트
**상태:** 원인 파악 후 3개 레포 모두 수정하여 `main`에 반영 완료

---

## 요약 (TL;DR)

한 스페이스 멤버가 GitHub 레포(`solkit70/builders-lounge-personal-notes`)를 스페이스에 연결했습니다. 레포는 **정상적으로 연결·클론되었고 에이전트가 파일을 모두 읽을 수 있는 상태**였지만, 에이전트는 레포를 한 번도 들여다보지 않은 채 계속 *"스페이스 포스트에서 찾을 수 없습니다"* 라고만 답했습니다.

- **근본 원인:** 스페이스 에이전트의 시스템 프롬프트가 `/github`에 대해 **자기모순**을 갖고 있었습니다. 베이스 프롬프트는 에이전트가 읽어도 되는 경로를 나열하면서 "그 외 경로는 읽지 말라"고 했는데, 그 목록에 `/github`가 **빠져 있었습니다.** 레포를 실제로 설명하는 별도 블록은 그 뒤에 덧붙여졌기 때문에, 에이전트는 같은 프롬프트 안에서 "`/github` 읽지 마라"와 "`/github` 읽어라"를 동시에 받았고, 성능이 낮은 스페이스 모델은 보수적으로 "읽지 않는" 쪽을 택했습니다.
- **원인이 아니었던 두 가지 (착오):** 레포는 **일시중지(paused) 상태가 아니었고**, "README에 링크되지 않은 파일은 찾지 못한다"는 가설은 **사실이 아닙니다** — 워킹 트리 전체가 클론되며 모든 파일을 경로/Glob으로 읽을 수 있습니다.
- **수정:** `/github`를 명시적으로 접근 범위에 포함시키고, "찾을 수 없다"고 답하기 전에 반드시 레포를 검색하도록 지시를 강화했습니다. 추가로 일시중지된 레포에 대한 UI를 명확하게 개선했습니다.

## 신고된 증상

워크로그에 따르면 에이전트는 (한국어를 요약하면) 다음과 같이 답했습니다:

> "현재 창발 스페이스 내의 포스트나 기록에서 'HebronGuide'라는 이름이나 관련 내용을 찾을 수 없습니다."

그리고 핵심 관찰:

> **"GitHub 레포를 읽는 도구 호출이 단 한 번도 없다"** — Settings에서 레포가 **"Attached"**로 표시됨에도 GitHub 레포를 읽는 도구 호출이 전혀 없었음.

워크로그 작성자가 제기한 두 가지 가설:
1. 시스템 프롬프트가 데이터 소스를 "연결되지 않음"이라고 명시해서 에이전트가 시도조차 하지 않았다.
2. `README.md`에 링크되지 않은 파일은 발견되지 않는다("링크를 따라가는 리트리버이지 재귀 인덱싱이 아니다") — 재귀 인덱싱을 켜거나, README 의존 동작을 공식 제약으로 문서화해 달라.

## 조사

### 레포 접근이 실제로 동작하는 방식
에이전트 실행이 디스패치될 때 gobi-backend는 스폰 요청에 `mounted_github_repos` 리스트를 함께 보냅니다. 이 **하나의 리스트**가 두 가지를 동시에 결정합니다:
- **클론** — 각 레포는 워커 컨테이너 안 `/github/<owner>/<name>/` 로 부분 클론(`git clone --filter=blob:none --depth=50`)되고,
- **프롬프트** — 정확한 경로를 나열하는 `# GitHub Repos` 섹션이 프롬프트 뒤에 덧붙여집니다.

두 가지가 같은 리스트에서 나오므로, **클론이 성공했다는 것은 곧 프롬프트 블록도 존재했다는 증거**입니다. 별도의 "리트리버"나 인덱스는 없습니다 — 에이전트는 파일시스템 위에서 `Read`/`Glob`/`Grep`으로 레포를 읽습니다.

### 프로덕션 증거 (7/5 changbal 트랜스크립트, user `13`)
에이전트 파드의 `/sessions` 마운트에서 세션 트랜스크립트를 확인했습니다:

- `Glob "/github/**/*"` 가 `/github/solkit70/builders-lounge-personal-notes/.git/…` 를 포함한 **워킹 트리 전체**를 반환 → **레포가 클론되어 있었음.**
- 에이전트가 실제 파일 내용을 성공적으로 `Read` 했음:
  - `ideas/2026-07-03 … HebronGuide.md`
  - `ideas/2026-07-02 … Job Search Co-pilot.md` ← "README에 링크되지 않아 찾을 수 없다"던 바로 그 파일 — **경로로 곧바로 정상적으로 읽힘.**
  - `README.md`
- **타임라인:** 초반 턴(14:24–14:31)에서는 `/github`를 건드리지 않고 곧장 `list_space_posts`로 가서 "찾을 수 없다"고 답했습니다. 멤버가 스페이스 자체 지시문을 "레포부터 검색하라"로 고쳐 쓴 뒤(14:45–15:07)에야 에이전트가 `/github`에 `Glob`/`Read`를 쓰기 시작했고 — 그때는 완벽하게 동작했습니다.

### 이로써 배제되는 것들
- **일시중지 아님.** 일시중지된 레포는 `mounted_github_repos`에서 걸러지므로 애초에 클론되지 않습니다. 클론되었다 → 활성 상태였다.
- **README 링크 제약 아님.** 링크 여부와 무관하게 모든 파일이 경로/Glob으로 읽혔습니다. 클론은 HEAD 워킹 트리 전체를 실체화하며, `--filter=blob:none`은 *과거 이력* 블롭만 지연 로드할 뿐 현재 파일에는 영향이 없습니다.

## 근본 원인

컨파인드(confined) 스페이스 에이전트의 시스템 프롬프트에 **모순**이 있었습니다:

- **베이스 프롬프트** (`SP_SPACE.md`의 "File access scope")는 읽기 가능 경로를 `${workingDirectory}`, `/vault/`, `/gdrive/`, `${memoryPath}/` 로 나열하고 *"멤버의 명시적 승인 없이는 그 외 경로의 파일을 읽지 말라"*고 명시했습니다 — **`/github/`가 목록에 없었습니다.** "What you have access to" 섹션에서도 GitHub이 빠져 있었습니다.
- **덧붙여진 블록** (`# GitHub Repos`, webdrive가 추가)은 정반대로 *"여기 있는 파일을 Glob/Grep하고 Read하라"*고 했습니다.

즉 가장 앞에 나오는, 가장 단정적인 지시는 `/github`가 접근 불가라고 했고, 뒤의 블록은 `/github`를 읽으라고 했습니다. 스페이스 에이전트는 도구 사용을 소극적으로 하는 성능이 낮은 모델에서 돌아가는데, 이런 충돌 앞에서 보수적인 쪽 — 포스트만 검색하고 `/github`는 건드리지 않으며 "찾을 수 없다"고 답하는 쪽 — 을 택했습니다.

기여 요인:
- 덧붙여진 블록의 표현이 "레포가 *무엇을 담고 있는지* / 무언가가 *어떻게 동작하는지*"로 좁게 한정되어 있었고, "답이 이 파일들 안에 있을 수 있는 모든 질문"으로 열려 있지 않았습니다.
- 레포를 발견할 저렴한 수단이 없었습니다: 에이전트가 시도했을 때 `gobi github list-repos`(존재하지 않는 명령)와 `find /github`(셸 차단)를 추측하다가 겨우 `Glob /github/**/*`에 도달했습니다.

## 적용한 수정

### 수정 1 — 베이스 프롬프트 모순 해소 (gobi-backend) · PR #816 (머지됨)
`prompts/SP_SPACE.md` 및 `prompts/SP_PERSONAL.md`:
- **File access scope** 화이트리스트에 `/github/<owner>/<name>/` 를 추가하고, 마운트가 존재하면 그것은 *검색해야 할 범위 안*이지 승인을 받거나 "답할 수 없다"고 가정할 대상이 아님을 명확히 했습니다.
- "What you have access to"에 **Attached GitHub repos** 항목을 추가하여, 레포가 전체 클론되며 **README 링크 여부와 무관하게** 모든 파일을 경로/Glob으로 읽을 수 있음을 명시했습니다.

### 수정 2 — 레포 지시문 강화 (gobi-webdrive) · PR #58 (머지됨, 빌드 + 배포 완료)
`infrastructure/agent/app/agent_prompt.py`의 `_github_section`:
- 워킹 트리 전체가 디스크에 있으며, **README 링크 여부와 무관하게** 모든 파일이 경로/Glob으로 읽힘 — 인덱스도 없고 링크를 따라가지도 않음.
- 정확한 경로를 모르면 레포를 `Glob`한 뒤 Read.
- 트리거를 "답이 레포 안에 있을 수 있는 모든 질문 — 멤버, 제품, 노트, 결정 사항, 동작 방식"으로 넓힘.
- **"연결된 레포를 실제로 Glob/Grep으로 검색하기 전에는 멤버에게 '찾을 수 없다'고 말하지 말 것. 포스트만 검색하는 것으로는 충분하지 않음."**
- 프롬프트 골든 재생성 (레포가 포함된 두 케이스만 변경).

### 수정 3 — 일시중지 레포 UI 명확화 (gobi-web) · PR #610 (머지됨)
`components/pages/space/SpaceSettingsAgentsGithub.tsx`:
- *changbal의 원인은 아니지만* 실재하는 잠재적 함정: **일시중지된** 레포가 Settings의 "Attached" 목록에는 그대로 남아 있으면서 에이전트에서는 제외되는데, 기존에는 작은 "paused" 칩 하나로만 표시됐습니다.
- 일시중지 시 레포 이름을 흐리게 처리하고, **"Paused — not readable by the agent"** 라는 평이한 문구(소유자에게는 토글 안내 포함)를 추가했으며, 토글 툴팁의 "included in spawns" 같은 내부 용어를 명확한 결과 설명으로 교체했습니다.

## 작성자의 원래 요청에 대한 답변

> "README 링크와 무관하게 전체 재귀 인덱싱을 켜거나, README 의존 동작을 공식 제약으로 문서화해 달라."

둘 다 필요 없습니다 — **전체 재귀 접근은 이미 존재합니다.** 레포는 통째로 클론되며 README 링크와 무관하게 모든 파일을 경로나 Glob으로 읽을 수 있습니다. 제약은 인덱싱에 있었던 적이 없고, 에이전트가 레포를 안정적으로 *들여다보지* 않았던 데 있었습니다. 수정 1·2가 바로 그 지점을 해결합니다.
