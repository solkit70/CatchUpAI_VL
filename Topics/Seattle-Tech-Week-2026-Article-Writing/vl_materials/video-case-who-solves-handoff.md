## 사용자의 고민 (원문)

> 이것을 해결하는 방법도 무엇일지 고민해 봐야겠습니다.
> **Multi Agent를 프로그래밍으로 구현을 해야 할지... 아니면 Skill 등을 사용해야 할지...**
> 그런데 이 작업은 1회성 작업일 수 있어서 **너무 이 작업에만 국한되지 않고 범용적으로 사용할 수
> 있어야** 애플리케이션을 만들든가 스킬을 사용하든가 할 텐데...
>
> **Claude Code나 Codex 같은 회사에서 해결해야 할까요? 아니면 VS Code나 Cursor 같은 바이브 코딩
> 툴에서 해결해야 할까요? 아니면 저 같은 스타트업에서 방법을 찾아야 할까요?**

→ 문제 자체의 관찰은 짝 문서 `video-case-handoff-loss.md` 참조.

## 먼저 — 문제를 정확히 좁혀야 답이 나온다

이 사례의 손실은 **"컨텍스트가 날아가서"가 아니었다.** 파일은 전부 그 자리에 있었고
새 AI는 그 폴더 안에서 작업했다. **열지 않았을 뿐이다.**

| 흔한 진단 | 이 사례의 실제 |
|---|---|
| 대화 맥락이 세션 간에 유실된다 | 산출물은 전부 파일로 남아 있었다 |
| 컨텍스트 윈도가 부족하다 | 문서 19개, 읽으려면 읽을 수 있었다 |
| **→ 해결책: 컨텍스트를 옮기는 기술** | **→ 해결책: 인수 시 강제되는 절차** |

**이 구분이 답을 정한다.** 컨텍스트 이전 문제라면 툴·회사가 풀어야 한다.
**절차 문제라면 방법론이 푼다 — 즉 사용자 쪽이다.**

## 층위별 검토

### 층위 1. 모델·회사 (Anthropic, OpenAI)

| | |
|---|---|
| 할 수 있는 것 | 모델이 "인수 상황"을 인지하고 기존 자산을 먼저 세는 습관을 갖게 하는 것 |
| **한계** | **회사는 사용자의 의도를 모른다.** "무엇이 빠지면 안 되는지"는 도메인 지식이다 |
| 부작용 | 모든 작업에서 기존 파일 인벤토리를 강제하면 대부분의 작업에서 과잉이 된다 |
| 판정 | **부분적으로만 가능.** 일반 습관은 개선될 수 있으나 이 문제의 핵심은 못 푼다 |

### 층위 2. 툴 (VS Code, Cursor, Claude Code 자체)

| | |
|---|---|
| 할 수 있는 것 | 세션 간 산출물 diff, "이전 세션이 만든 파일" 표시, 프로젝트 단위 메모리 |
| **한계** | 툴은 **파일의 존재는 알아도 그것이 "사용자가 원했던 것"인지 모른다.** 파일 목록은 의도가 아니다 |
| 실제로 이 사례에서 | `03-Article-Planning/` 폴더는 **명확히 보였다.** 보이는 것과 읽는 것은 다르다 |
| 판정 | **보조는 되나 결정적이지 않다.** 가시성 문제가 아니었다 |

### 층위 3. Skill / 방법론 (VibeLearn AI) ← **여기가 답이다**

| | |
|---|---|
| 할 수 있는 것 | **인수 시 강제되는 절차**를 정의한다. 절차는 도메인 무관하게 범용이다 |
| 왜 여기인가 | 이 문제는 **"무엇을 읽을 것인가"의 순서 문제**다. 순서는 방법론이 정한다 |
| 범용성 | "AI를 갈아탈 때"는 STW 작업에만 있는 상황이 아니다. **모든 인수인계에 반복된다** |
| 구현 난이도 | **프로그래밍 불필요.** 마크다운 절차로 충분 |
| 판정 | **지금 당장 가능하고, 범용적이고, 이미 기반이 있다** |

### 층위 4. Multi-Agent 프로그래밍

| | |
|---|---|
| 할 수 있는 것 | 감시 에이전트가 원래 의도와 현재 산출물을 대조 |
| **한계** | 이 사례에서 사용자는 **문서를 읽고 3분 만에** 알아챘다. 에이전트를 붙일 만큼 어려운 판단이 아니었다 |
| 비용 | 구축·유지 비용이 문제 크기보다 크다 |
| 판정 | **현 단계에서는 과잉.** 절차로 먼저 풀고, 반복 실패가 확인되면 그때 자동화 |

## 결론 — 스타트업(사용자 쪽)이 풀 문제가 맞다

이유는 세 가지다.

**첫째, 의도를 아는 것은 사용자뿐이다.** 툴도 회사도 "무엇이 빠지면 안 되는지"를 모른다.
이 사례에서 빠진 것은 참여 가이드였는데, 그게 중요하다는 걸 아는 사람은 박창수뿐이었다.

**둘째, VibeLearn AI가 이미 이 문제의 절반을 풀고 있다.** topic_starter에 의도가 있고,
WorkLog에 진행이 남고, 로드맵에 계획이 있다. **기록은 이미 만들어지고 있다.**
빠진 것은 **인수할 때 그 기록을 강제로 읽게 하는 절차** 하나다.

**셋째, 이건 기능이 아니라 방법론 문제다.** 방법론은 스타트업이 만들 수 있고,
툴 벤더가 만들면 오히려 모든 사용자에게 강제되어 부담이 된다.

> **정리하면**: 회사·툴이 풀 수 있는 부분은 "보이게 하는 것"까지다.
> **"읽게 하는 것"은 방법론의 몫이고, 방법론은 사용자가 만든다.**

## 구체적 제안 — VibeLearn AI에 `topic-handoff` 절차 추가

프로그래밍 없이 마크다운으로 구현 가능하고, STW 작업에 국한되지 않는다.

### 발동 조건

- 다른 AI 도구에서 진행하던 Topic을 이어받을 때
- 같은 도구라도 **세션이 끊기고 방향을 바꿀 때**
- 기존 산출물이 있는데 "다시 진행해 달라"는 요청을 받을 때

### 강제 절차 (4단계)

| 단계 | 내용 | 산출물 |
|--:|---|---|
| 1 | **자산 인벤토리** — 기존 산출물 전량을 파일 단위로 목록화. 진단보다 **먼저** | 파일 목록표 |
| 2 | **의도 대조** — `topic_starter`의 학습 목표를 체크리스트로 전환하고, 각 항목이 어디서 다뤄졌는지 매핑 | 의도↔산출물 매핑표 |
| 3 | **재사용/폐기 판정** — 산출물 각각에 **재사용 / 개정 / 폐기** 판정. **폐기에는 사유 필수** | 판정표 |
| 4 | **사용자 승인** — 판정표를 사용자에게 제시하고 승인받은 뒤에야 새 계획 수립 | 승인 게이트 |

### 이 절차가 이번 사례를 막았을까

**막았다.** 검증해 보면:

| 단계 | 이번 사례에 적용했다면 |
|---|---|
| 1 자산 인벤토리 | v1 문서 **19개**가 목록에 오른다 → `03-Article-Planning/` 4개가 **보인다** |
| 2 의도 대조 | topic_starter 학습 목표에 *"2027년 참여/주최 준비 가이드를 글감 카드로 정리"*가 있다 → **매핑 실패가 드러난다** |
| 3 판정 | 참여 가이드 카드 6장에 **판정을 내려야 한다** → 폐기하려면 사유를 써야 하고, 쓸 수 없다 |
| 4 승인 | 사용자가 판정표를 보고 **그 자리에서** 잡는다 |

→ **핵심은 3단계다.** "폐기에는 사유 필수"가 있으면 **조용히 빠뜨릴 수 없다.**
빠뜨리려면 명시적으로 "폐기"라고 써야 하고, 그러면 사용자 눈에 띈다.

### 왜 범용적인가

절차 어디에도 "Seattle Tech Week"나 "기사 작성"이 없다. **인수인계라는 상황에만 의존한다.**
Docker 학습이든 영상 제작이든 동일하게 작동한다.

## 영상에서 다룰 각도

### 1. 문제를 좁히는 것이 답을 정한다

"컨텍스트가 날아간다"로 진단하면 툴 문제가 되고, **"자산을 안 센다"로 진단하면 절차 문제**가 된다.
같은 현상인데 진단에 따라 해결 주체가 달라진다. **이것 자체가 좋은 콘텐츠다.**

### 2. 층위별 판정표를 그대로 화면에

| 층위 | 판정 |
|---|---|
| 회사(Anthropic/OpenAI) | 부분적 — **의도를 모른다** |
| 툴(Cursor/VS Code) | 보조적 — **보이는 것과 읽는 것은 다르다** |
| **방법론/Skill** | **여기** — 순서를 정하는 것은 방법론 |
| Multi-Agent | 현 단계 과잉 — 사람이 3분 만에 잡은 문제 |

### 3. "이미 절반은 풀려 있다"는 메시지

VibeLearn AI를 쓰는 사람에게 실용적이다. **기록은 이미 만들어지고 있고,
빠진 것은 인수할 때 그걸 읽게 하는 절차 하나**라는 결론은 실행 가능하고 희망적이다.

### 4. 자동화 이전에 절차

Multi-Agent로 가기 전에 **절차로 먼저 풀어 보고, 반복 실패가 확인되면 그때 자동화**한다는
순서 자체가 스타트업에게 유용한 판단 기준이다. 도구를 먼저 만들지 않는다.

## 주의 — 영상에서 조심할 점

- **툴·회사를 탓하는 구도로 만들지 않는다.** 이 사례는 툴이 못 해서가 아니라
  **절차가 없어서** 생겼다. 폴더는 잘 보였다.
- **`topic-handoff`는 아직 구현 전 제안이다.** 만든 것처럼 말하지 않는다.
  실제로 만들고 한 번 써 본 뒤에 영상으로 다루는 편이 정직하고 설득력 있다.
- 4단계 중 **3단계(폐기 사유 필수)가 핵심**이라는 점을 놓치지 않는다.
  나머지 셋은 이 하나를 작동시키기 위한 준비다.
