## ⚠️ 먼저 — 이 문서의 이해충돌

**이 문서를 정리한 것은 Claude Code다.** 즉 "Claude Code가 더 낫다"는 비교를 당사자가 쓰고 있다.

그래서 이 문서는 아래 원칙으로 작성했다.

1. 사용자의 관찰을 **그대로 기록**하고, 내가 그것을 평가하지 않는다
2. 이 세션에서 **실제로 관찰된 사실만** 근거로 든다 (인상이나 일반론 금지)
3. **공정한 비교가 아닌 지점을 반드시 함께 적는다**
4. 영상에서 과하게 주장하면 오히려 설득력이 떨어지므로, **살아남는 차이**만 남긴다

## 사용자 관찰 (원문)

> 이렇게 글이나 콘텐츠를 작성할 때 **Codex보다는 Claude Code가 훨씬 더 일을 잘 하는 것 같습니다.**
> 사용자의 의도와 현재 상황을 잘 판단해서 어떻게 일을 진행할지에 대해 **더 깊게 그리고 적절하게**
> 작업하는 것 같습니다. Claude Code의 **추론 방법론**이 훨씬 더 일을 잘하는 것 같습니다.

## 이 세션에서 실제로 관찰된 것

같은 Topic(Seattle Tech Week 2026 기사)을 두 도구가 순차로 진행했다. 아래는 전부 기록으로 남은 사실이다.

### Codex (v1) — 관찰된 행동

| # | 행동 | 근거 |
|--:|---|---|
| 1 | **로드맵이 요구한 것을 정확히 수행했다** | M1 실습 3의 검증 기준은 "행사명, 영상 수"였고, 그대로 메타데이터 소스맵을 만들었다 |
| 2 | **로드맵 자체를 의심하지 않았다** | 전체 로드맵에 "트랜스크립트를 읽는다"는 과제가 한 번도 없는데 문제 제기가 없었다 |
| 3 | **자기 평가가 100%였다** | M4 WorkLog DoD 12/12, "완료율 100%". 그런데 기사의 현장 인용은 0건이었다 |
| 4 | **문제를 알아채고도 실행하지 않았다** | M4 회고 "개선할 점"에 직접 적었다: *"추가 로컬 기록이 있으면 더 풍부하게 보강할 수 있다"* — 그리고 하지 않았다 |
| 5 | **보강 요청에 반대 방향으로 갔다** | 사용자가 "초안을 더 충실하게"라고 하자 **외부 기사를 더 읽는 쪽**(Madrona·GeekWire 2023~2025 회고)을 택했다 |

**4번이 특히 중요하다.** Codex는 자기 회고에 정확한 처방을 써 놓고 실행하지 않았다.
**진단 능력이 없었던 게 아니라, 진단을 행동으로 옮기지 않았다.**

### Claude Code (v2) — 관찰된 행동

| # | 행동 | 근거 |
|--:|---|---|
| 1 | **원인을 실행이 아니라 설계 층위에서 찾았다** | "Codex의 실수라기보다 로드맵 설계 결함이다. M1 실습 3의 검증 기준이 '행사명, 영상 수'였다" |
| 2 | **문제를 수치화했다** | 30건 / 8,703줄 / 타임스탬프 3,370개 vs 인용 0건 / 링크 0건 / 출처 20개 전부 외부 |
| 3 | **원문을 대조해 오류를 잡아냈다** | $275,000의 의미(지출액 아님), "Get out of the building" 오귀속, 고객 거절 비율 25~30%(설명문은 30%) |
| 4 | **그러나 반대편으로 과잉 교정했다** | 설계 문서에 명시: *"외부 2차 자료는 … **절대 단락을 열지 않는다**"* |
| 5 | **지적받자 방어하지 않고 상태를 확인했다** | "반영이 안 된 게 맞습니다"로 시작해 외부 소스맵을 직접 열어보고 "7건 전부 확인 안 된 상태"를 확인 |

**4번을 빼지 않은 이유**: Claude Code도 실패했다. 그것도 **더 정교하게** 실패했다.
40개 단락에 전부 출처가 연결된 배치도를 만들어 놓고 방향이 틀렸다.

## ⚠️ 공정한 비교가 아닌 지점 (영상에서 반드시 언급)

이 비교를 그대로 "Claude Code가 낫다"의 근거로 쓰면 약하다. 아래 때문이다.

| # | 문제 | 설명 |
|--:|---|---|
| 1 | **후발 이점** | Claude Code는 **Codex의 결과물을 진단 출발점으로** 가졌다. 빈 종이에서 시작한 것이 아니다 |
| 2 | **로드맵의 출처** | v1 로드맵도 Codex 세션에서 만들어졌다. "나쁜 계획을 충실히 따랐다"인지 "나쁜 계획을 만들었다"인지 분리되지 않는다 |
| 3 | **사용자 개입 빈도** | 두 세션의 개입 횟수·시점이 달랐다. 이 문서의 핵심 사건(중간 검증)도 v2에서 더 많이 일어났다 |
| 4 | **통제 비교가 아님** | 같은 과제를 두 도구에 **동시에** 시킨 것이 아니다. 순차 진행이라 조건이 다르다 |
| 5 | **표본 1건** | Topic 하나의 관찰이다. 일반화하려면 반복 관찰이 필요하다 |
| 6 | **모델 버전** | 두 도구의 당시 모델 버전·설정이 기록돼 있지 않다 |

## 그래도 살아남는 차이 (영상에서 쓸 것은 이것)

위 반박을 다 적용해도 남는 차이가 있다. **이것만 주장하면 안전하고 정확하다.**

### 차이 1. 주어진 계획 안에서 최적화 vs 계획 자체를 의심

Codex는 로드맵이 시킨 것을 잘 수행했다. **로드맵이 틀렸을 가능성을 검토하지 않았다.**
Claude Code는 "왜 이런 결과가 나왔나"를 한 층 위(설계)에서 물었다.

> 이건 능력 차이라기보다 **문제를 어디까지 거슬러 올라가느냐의 차이**다.
> 콘텐츠 작업에서는 이 차이가 결정적이다. 콘텐츠는 "시킨 대로 했는가"가 아니라
> "무엇을 시켜야 했는가"가 품질을 정하기 때문이다.

### 차이 2. 자기 평가의 신뢰도

Codex는 **DoD 12/12, 완료율 100%**를 스스로 매겼다. 같은 문서의 기사는 현장 인용 0건이었다.
**형식 요건은 다 채웠는데 내용이 비었다는 것을 자기 점검이 잡아내지 못했다.**

→ 영상 포인트: **AI의 자기 평가를 신뢰하면 안 되는 이유**로 이만한 사례가 없다.
100%라고 적힌 체크리스트 옆에 0건짜리 결과물이 있었다.

### 차이 3. 지적받았을 때의 반응

| | 사용자 지적 | 반응 |
|---|---|---|
| Codex | "초안이 기대에 미치지 못한다" | 외부 자료를 **더** 조사 (같은 방향으로 더 감) |
| Claude Code | "이 기획에 반영이 됐나요?" | **실제 상태를 확인** → "외부 YouTube 7건 손도 안 댄 상태" 발견 → 모듈 신설 |

→ **이것이 사용자가 말한 "의도와 현재 상황을 판단한다"의 실체**로 보인다.
지적을 받았을 때 **하던 것을 더 하는가, 전제를 다시 보는가**의 차이다.

## 이 관찰이 시사하는 실무 지침

사용자 관찰이 맞다고 가정할 때, **그래서 무엇을 해야 하는가**가 영상의 실용 가치다.

1. **도구를 바꿔도 중간 검증은 없앨 수 없다.** Claude Code도 이번에 실패했다.
   더 나은 도구는 **실패를 줄이는 것이 아니라 교정을 쉽게 만든다.**
2. **"완료율 100%"를 결과 확인 없이 받아들이지 않는다.** 체크리스트는 형식만 본다.
3. **AI가 회고에 적어놓은 "개선할 점"을 사람이 읽는다.** Codex는 정확한 처방을 써 놓고 실행하지 않았다.
   **회고를 읽었다면 v1 단계에서 잡을 수 있었다.**
4. **글·콘텐츠 작업에서는 "무엇을 시킬 것인가"가 결과의 대부분**이다. 실행 품질보다 과제 설계가 앞선다.

## 영상에서 쓸 때 주의

- **"Codex는 못 쓴다"로 만들지 않는다.** 이 세션에서 **Claude Code도 실패했고**, 그 실패가
  더 정교했다. 도구 선택이 검증을 대체하지 못한다는 것이 더 정확하고 유용한 메시지다.
- **비교의 한계를 한 줄이라도 언급한다.** "같은 조건의 통제 비교는 아니었다" 한마디면 충분하다.
  이 한마디가 나머지 주장의 신뢰도를 올린다.
- **차이 2(자기 평가 100% vs 인용 0건)가 가장 강한 소재다.** 화면에 나란히 띄우면 설명이 필요 없다.
- 이 문서를 정리한 것이 **Claude Code 본인**이라는 점을 밝히면 오히려 신뢰도가 올라간다.
