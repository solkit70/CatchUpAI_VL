# 007 에이전트 연결 — v1 은 파일 공유, 구조는 열어 둔다

- **날짜 · 모듈**: 2026-09-27 M0 (Live #29 방송 중 결정)
- **상태**: ✅ 채택

## 맥락
이 앱은 사용자의 **첫 멀티 에이전트 시스템**이다. v1 에이전트는 넷(Board · Deadline · Intake · Discovery)이고, PRD 는 「에이전트끼리 직접 부르지 않는다, 파일을 통해서만 이어진다」고 정해 두었다. 방송 중 사용자 의견:

> 「필요하면 에이전트 들끼리 직접 부르지 않게 할 수 있지만 나중에 다시 에이전트들간의 호출이 필요하게 되면 변경할 수 있게 진행해 주세요. 그리고 멀티에이전트 구조도 Supervisor 가 팀 멤버들을 관리하는 방식도 있고, 아니면 각 에이전트들이 동일한 레벨에서 소통하는 방식등도 있습니다. (…) 이런 가능성을 열어두고 진행 해 주세요.」

## 검토한 선택지
| 구조 | 소통 방식 | 이 앱에서 |
|---|---|---|
| **파일 공유 (블랙보드)** | 공유 파일에 쓰고 읽는다 · 직접 호출 없음 | v1 출발점 — 디버깅 쉬움 · 원본이 마크다운으로 남음 |
| Supervisor (관리자 + 팀원) | 관리자 에이전트가 팀원을 부르고 결과를 모음 | 후보 — 「아침 정리」 관리자가 Board·Deadline·Discovery 를 묶는 경우 |
| 동급 (Peer / Network) | 같은 레벨끼리 직접 메시지 | 후보 — Intake 가 중복 판단을 Board 에게 묻는 경우 |
| 계층형 | Supervisor 아래 Supervisor | v1 에 필요 없음 |
| 순차 파이프라인 | 앞 출력이 다음 입력 | 파일 공유의 특수한 경우 (Board → Deadline) |

업계 참고: Anthropic 은 「단순한 구성부터 시작해 필요할 때만 복잡하게」를 권하고, 자사 리서치 시스템에서는 리드 에이전트가 하위 에이전트를 부르는 Supervisor 형(orchestrator-worker)을 쓴다.
- [Building effective agents — Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- [How we built our multi-agent research system — Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)

## 결정
1. v1 은 **파일 공유**로 출발한다. 에이전트끼리 직접 부르지 않는다
2. **바꿀 수 있게** 만든다. `ARCHITECTURE.md` 의 **에이전트 계약 표**(트리거 · 입력 · 출력 · 쓸 곳 · 부를 수 있는 대상)가 유일한 연결 사양이다. 에이전트는 서로의 내부를 모르고 계약만 안다
3. M2 이후 에이전트 모듈마다 ② 업계 방식 조사에서 「이 기능에 맞는 구조」를 다시 본다
4. 구조를 바꿀 때는 새 결정 기록(무엇을 · 왜 파일 공유로 부족했나 · 되돌리는 법)을 남기고 사용자 승인을 받는다

## 이유
처음 만드는 멀티 에이전트 시스템은 단순한 구조가 이해하고 고치기 쉽다. 하지만 구조를 고정하면 나중에 Supervisor 가 필요할 때 전부 다시 짜야 한다. 계약을 한 곳에 두면 연결 방식을 바꿔도 계약 한 줄과 해당 에이전트만 고친다.

## 결과 · 대가
- 대가: v1 에이전트끼리 협상하거나 서로 결과를 검토하지 못한다
- 지키는 것: 구조를 바꿔도 원본은 마크다운 · `items/` 는 사람과 화면만 · 사람 승인 게이트
- 부딪힘 주의: Supervisor · 직접 호출에 새 프레임워크가 필요하면 [003](003-에이전트%20런타임은%20AI4PKM%20오케스트레이터.md)과 부딪힌다. 바로 도입하지 않고 사용자에게 묻는다
- M10 템플릿에 「멀티 에이전트 구조 고르기」 안내로 들어간다
