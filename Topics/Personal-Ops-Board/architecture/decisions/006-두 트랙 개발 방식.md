# 006 두 트랙 개발 방식 — 아키텍처는 만들며 쌓는다

- **날짜 · 모듈**: 2026-09-25 결정 · 2026-09-27 M0 기록
- **상태**: ✅ 채택 · KIRO 공식 문서 확인 완료 (2026-09-27)

## 맥락
처음 계획은 PRD 를 사양으로 두고 모듈을 차례로 만드는 것이었다. 그 사이 2026-09-16 Builders Lounge 5차 모임에서 5차 발표자(샌프란시스코의 한 빌더)가 자신의 개발 방식을 소개했다. KIRO(AWS 의 AI 개발 도구)처럼 **아키텍처 문서를 만들면서 코드를 짜고**, 대화로 나온 결정을 바로 그 문서에 저장하며, 설계 전에 **업계에서 보통 어떻게 하는지**를 먼저 묻는다. 그리고 한 프로젝트가 끝나면 남는 아키텍처 문서 덕에 두 번째 프로젝트부터 빨라진다고 했다.

## 검토한 선택지
| 선택지                 | 장점                   | 단점                                          |
| ------------------- | -------------------- | ------------------------------------------- |
| 사양을 다 쓰고 시작 (폭포수)   | 방향이 분명함              | 쓰다 보면 틀린다. 이 Topic 에서도 2주 동안 스키마 결정이 9번 나왔다 |
| 코드만 쌓기              | 빠름                   | 「왜 이렇게 됐나」가 남지 않음 · 재사용 불가                  |
| **기능 트랙 + 아키텍처 트랙** | 결정의 이유가 남음 · 끝나면 템플릿 | 매 모듈 문서 작업 시간이 든다                           |

## 결정
매 모듈을 한 바퀴로 돈다: ① 요구 찾기 → ② 업계 방식 조사(2026년 9월 기준) → ③ 설계 제안 → 사용자 승인 → ④ 구현·검증 → ⑤ `ARCHITECTURE.md` · `decisions/` 갱신 → ⑥ WorkLog. ⑤ 없이 모듈을 닫지 않는다. 마지막 모듈(M10)에서 아키텍처를 재사용 가능한 템플릿으로 일반화한다.

## 이유
아키텍처를 미리 다 정하지 않는 대신, 정한 것은 그때그때 이유와 함께 남긴다. 업계 방식을 먼저 보면 혼자만의 구조(갈라파고스)를 피한다.

## 결과 · 대가
- 대가: 모듈마다 문서 시간이 든다. 로드맵 시간 배분에 포함했다
- ✅ KIRO 공식 문서 확인 완료 (2026-09-27, 아래)

## KIRO 공식 문서 확인 (2026-09-27 · Live #29)

**KIRO 의 스펙 기반 개발 — 공식 문서 요지**
- 스펙은 기능·버그 수정마다 만드는 구조화된 문서로, 파일 셋이다: `requirements.md`(사용자 스토리 · 인수 기준) → `design.md`(기술 아키텍처 · 시퀀스 다이어그램) → `tasks.md`(추적 가능한 작업). 단계 사이에 **승인 게이트**가 있다 (승인 없이 한 번에 만드는 Quick Spec 은 예외)
- 요구사항은 **EARS 표기**로 쓴다 — 「WHEN [조건/사건] THE SYSTEM SHALL [기대 동작]」. 모호하지 않고 바로 테스트로 옮길 수 있다
- 요구부터 시작(Requirements-First)하거나 설계부터 시작(Design-First)할 수 있다
- 스펙은 계속 고친다 — 요구를 고치면 설계를 맞추고, `tasks.md` 의 Sync Files 로 작업을 갱신한다. 스펙은 코드와 같은 저장소에서 버전 관리한다
- **스펙은 기능마다 여러 개** 둔다 — 코드 전체에 스펙 하나를 두지 말 것
- **Steering 파일**(`.kiro/steering/` 의 `product.md` · `tech.md` · `structure.md`)은 매 대화에 기본으로 들어가는 프로젝트 지식 — 제품 목적 · 기술 스택 · 파일 구조와 아키텍처 결정

**이 Topic 과 비교**

| KIRO | 이 Topic | 같음 / 다름 |
|---|---|---|
| 기능마다 스펙 (requirements · design · tasks) | 모듈마다 한 바퀴 (요구 찾기 · 설계 제안 · 구현) · 로드맵의 모듈별 실습 과제 | ✅ 같음 — 기능 단위로 나눈다 |
| 단계 사이 승인 게이트 | ③ 설계 제안 → 사용자 승인 전에는 코드를 쓰지 않는다 | ✅ 같음 |
| 스펙을 계속 고치고 저장소에서 버전 관리 | `ARCHITECTURE.md` 를 모듈마다 갱신 · 공개 레포 | ✅ 같음 — 「만들며 쌓는다」가 공식 문서에도 있다 |
| Steering (`product.md` · `tech.md` · `structure.md`) | 볼트 `AGENTS.md` · `CLAUDE.md` · 개발 시작 Prompt 「절대 규칙」 · `ARCHITECTURE.md` | ≈ 비슷함 — 역할은 같고 파일 이름·위치가 다르다 |
| `design.md` 는 기능마다 | `ARCHITECTURE.md` 는 앱 전체 하나 + 결정 하나 = 파일 하나(`decisions/`) | ⚠️ 다름 — KIRO 는 결정의 **이유**를 따로 모으는 파일이 없다. 이 Topic 은 ADR 로 이유를 남긴다 (재사용 템플릿의 재료) |
| 요구사항을 EARS 로 쓴다 | WorkLog 「오늘 정한 요구」에 한국어 EARS + 검증 결과 | 🔄 변형 적용 — ADR 008 |
| 작업 목록 `tasks.md` + 병렬 실행 | 로드맵 실습 과제 · WorkLog 체크리스트 | ≈ 비슷함 |

**후속 결정**: 이 제안은 9/27 ADR 008에서 채택했고 10/2 표 승인에서도 유지했다. 요구 찾기 결과를 WorkLog에 EARS 한 줄로 적고 같은 줄에 검증 결과를 연결한다. → [ADR 008의 결정](008-요구는%20EARS%20한%20줄로도%20적는다.md#결정)
