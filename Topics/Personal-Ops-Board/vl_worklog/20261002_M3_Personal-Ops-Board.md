## M3 이관 준비 재점검 (2026-10-02)

최신 인덱서 결과는 task 72개 유효, 오류 0, warning 16이다. warning은 `project` 누락 10건과 `source` 누락 6건으로, 13개 task의 선택 필드만 비어 있다(완료 9, 대기 3, 할 일 1). 새로 승인된 세 task에서는 warning이 생기지 않았다. 이 항목들은 입력 오류가 아니며 임의의 링크를 만들어 채우지 않았다. 다음 설계 검토에서 정보성 수용 또는 보완 대상을 묶어서 정할 수 있다. 이전에 A-001에 기록했던 파싱 실패도 현재 인덱서에서는 재현되지 않는다. 다만 Task Board 행과 연결 item의 범위 차이는 별도 확인 전까지 보류한다.

Task Board의 직접 작성 사용처는 GDR과 GWR이며, 둘 다 기존 파일을 직접 갱신한다. POB prompt와 M2 renderer는 `items/`를 읽고 별도 `priority-board.md`만 쓴다. 생성 view는 날짜·약속·프로젝트·보류의 네 tier 구역과 완료·닫음·점검 영역을 사용해 기존 Task Board의 세 섹션과 구조가 다르다. 따라서 현 상태에서 POB 출력을 Task Board로 덮으면 누락·구조 변경 위험이 있다. 판정표의 보류 48행과 처리된 일 30개 기록은 여전히 현재 Task Board에 있고, 30개 완료 기록의 읽기 전용 보관본, 원본 백업/복구 순서, 보류 항목을 생성물에 보존할 방식은 마련되지 않았다. GDR/GWR 및 전환기 지침도 아직 기존 Task Board를 쓰도록 되어 있어, 소유권 전환 게이트는 통과하지 않았다. 실패 주입 복구 검증도 남아 있다.

## 자체 점검 및 검토 축소 결정 (2026-10-02)

Task Board의 `처리 중인 일`에서 직접 연결한 item 23개, Backlog 본문에서 직접 연결한 item 5개의 경로가 모두 존재함을 확인했다. 최신 인덱스에서는 72개 task가 모두 유효하고 오류가 없다. 이전에 파싱 오류로 기록했던 A-001 item도 현재 파싱되지만, 행과 item의 남은 범위가 일치하는지 확인되지 않아 판정은 보류로 둔다. 사용자는 B-001과 A-025가 같은 task라고 확인했고, A-011은 해야 할 일이 아니라고 확인했다. 사용자가 이미 확인한 제목 후보는 다시 묻지 않았다.

초기에는 검토 부담을 줄이기 위해 미검토 행을 보존하고 멈추기로 했으나, 사용자가 M3를 마치기 위해 행별 수동 검토를 재개하도록 지시했다. 따라서 이전 중단 결정은 현재 유효하지 않으며, Backlog B-024부터 차례대로 확인한다. M4 사전 조사에서 GDR·GWR의 `2026-09-27` 전환기 종료 문구가 이미 지난 날짜인 것을 확인했다. 실제 GDR·GWR 프롬프트 수정은 M3 검토 및 변경안 검토 후에 한다.

## 설계 제안 — 검토 대기

1. **단계 분리**: (A) 읽기 전용 대조·사람 판정(active + backlog), (B) 승인된 신규/수정 제안 생성, (C) 사용자별 승인에 따른 item 반영, (D) 기존 Board 생성물 전환을 별도 단계로 둔다. 각 단계는 앞 단계의 승인 기록을 입력으로 받는다.
2. **대조 식별자**: Task Board 행에 원문 순서 기반의 안정된 ID를 부여하고, 미리보기 생성 시 행 내용 fingerprint를 저장한다. 원문이 바뀌면 이전 판정을 자동 재사용하지 않고 재검토 표시한다.
3. **수동 판정만 적용**: 제목 정확/유사도는 후보 목록으로만 쓴다. Board의 세 섹션과 체크박스 문자는 보존하고, 기존 `items.status`로 자동 변환하지 않는다. 완료·보류·제외 사유도 사람이 선택한다.
4. **아이템 제안**: `new_proposal`/`update_proposal`만 `inbox/`에 초안을 생성한다. 업데이트는 기존 파일 전체를 덮지 않고 제안 diff로 표현한다. 승인 전에는 `items/` 쓰기를 금지한다.
5. **진단 게이트**: 원본 파싱 실패는 해소/명시적 보류가 되기 전 전환을 막는다. 2026-10-02 확인된 선택 필드 warning 11건은 사용자 결정으로 정보성 수용했다. 이 11개 파일·코드 조합은 상세 경로와 함께 보드에 표시하고, 그 밖의 새 warning은 미분류 상태로 검토한다.
6. **별도 전환 승인**: 기존 Board를 생성물로 바꾸는 일은 이관 승인과 별도다. 처리 중인 일과 Backlog는 행별 판정·반영하며, 기존 `처리된 일` 기록은 별도 읽기 전용 보관본으로 옮겨 새 Board에서 연결한다. 먼저 GDR·GWR·TIU·Weekly Progress 등 관련 프롬프트/워크플로의 Board 읽기·쓰기 위치를 조사하고, 소유권 충돌이 해결된 뒤 백업과 롤백 절차를 사용자에게 제시한다.
7. **보안·범위**: 비교 결과와 제안은 비공개 `AI/Tasks/` 아래에 둔다. 공개 Topic WorkLog에는 실제 행 제목·사람·업무 세부를 옮기지 않고, 집계·설계만 기록한다.

## 업계 방식 조사

Kiro Feature Specs는 요구 → 설계 → 작업의 단계를 두고 복잡하거나 낯선 변경에 검토 지점을 둔다. Requirements-First는 요구를 검토·확정한 뒤 설계와 작업으로 넘어간다. 이 M3는 기존 개인 task 원본을 옮기는 위험이 있으므로, 이 방식을 적용해 판정과 쓰기·전환을 승인 가능한 작은 경계로 나누는 것이 적합하다고 판단했다. [Feature Specs](https://kiro.dev/docs/specs/feature-specs/) · [Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first/)

## 미결정 사항

- `exclude`와 `hold`의 정확한 의미 및 판정 사유 선택값
- 기존 Task Board 세 섹션의 체크박스·완료·Backlog 의미를 신규 항목의 기본값에 매핑할지 여부
- 처리된 30개 기록을 보존할 읽기 전용 보관 위치·형식과 생성 Board에서 연결할 위치
- 새로운 인덱서 warning이 생겼을 때 누구의 검토로 수용하거나 보완할지
- GDR/GWR/TIU/Weekly Progress의 현재 Board 쓰기 사용처와 M2의 남은 비파괴 회귀 확인
- M3 범위에서 승인 UI 없이 파일 기반 판정표를 쓸지, 향후 M6 UI까지 수동 대조를 유지할지

이 문서는 **설계 초안**이다. 위 수용 기준·판정 용어를 사용자가 검토하고 승인하기 전까지 migration 코드, inbox proposal, Task Board 또는 item 원본 변경을 수행하지 않는다.

## M4 사전 영향 조사 (2026-10-02)

읽기 전용으로 GDR, GWR 및 `daily-roundup-routine` skill의 Task Board 쓰기 계약을 확인했다. GDR은 매일 변경이 있을 때 `Task Board.md`를 갱신하고, GWR은 주간 계획에서 새로 이어지는 task를 반영한다. 두 경로 모두 M3/M4 인계가 적용되기 전에는 같은 변경을 `items/`에도 이중 기록하라고 명시한다. POB renderer는 기존 Task Board 경로를 출력 대상으로 거부하며, 현재 M2 보기는 4개 tier와 완료·닫음·점검 구역으로 렌더되어 기존 3개 섹션과 동일한 모양이 아니다.

따라서 M4에서 GDR/GWR 쓰기를 `items/`로 바꾸기 전에 M3의 미결 제안·보류를 처리하거나 생성 보드에서 보존할 방식과 전환 기준을 확정해야 한다. M4 변경안은 (1) 사용자가 확정한 status/다음 행동만 item frontmatter·본문에 반영, (2) 중복·모호·스키마 밖 변경은 사용자 확인 대기, (3) 기존 Task Board 직접 쓰기를 끄기 전에 POB index/board 재생성·링크·세 섹션 보존 검증, (4) 테스트 실패 시 원본과 이전 view 유지, (5) 검증된 GDR/GWR 1회 실행 뒤에만 이중 동기화 지침 제거 순서로 준비한다. 이번 조사에서는 GDR/GWR prompt나 운영 파일을 수정하지 않았다.

업계 방식 조사에서는 Kiro의 Requirements-First가 요구사항을 검토·확정한 뒤 설계와 작업으로 진행하는 단계형 승인 방식을 확인했다. Anthropic은 필요 이상으로 복잡한 자율 에이전트보다 평가 가능한 단순 조합형 workflow에서 시작할 것을 권한다. 따라서 M4는 프롬프트 쓰기 권한 전환을 먼저 작게 제안하고, 결정적 인덱서·렌더러를 이용한 shadow 검증 뒤 운영 workflow를 바꾸는 순서가 적합하다. ([Kiro Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first/) · [Anthropic: Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents))

합성 shadow 회귀를 추가했다. 임시 `items/`의 task 상태를 완료로 변경한 입력을 실제 인덱서와 렌더러 CLI에 넣어 유효 인덱스·완료 구역 출력을 확인하고, 같은 실행 전후 루트 Task Board 바이트가 동일한지 검증한다. POB 회귀는 33건 통과했다. 이 검증은 도구 연결을 합성 데이터로 확인한 것이며 GDR/GWR의 실제 운영 실행이나 소유권 전환은 포함하지 않는다.

## M4 조건부 workflow 지침 반영 (2026-10-02)

사용자가 GDR/GWR task 기록을 `items/` 중심으로 전환하는 변경안을 승인했다. GDR·GWR prompt, `daily-roundup-routine` skill, 루트 AGENTS/CLAUDE, 비공개 migration ledger에 PRE-HANDOFF와 POST-HANDOFF 동작을 나눠 기록했다. POST-HANDOFF는 M3 완료, 별도 사용자 cutover 승인, pre-cutover M4 shadow 검증 성공이 ledger에 모두 기록된 경우에만 선택한다. 전환 후에는 확인된 `items/`만 갱신하고 index 오류나 허용 목록 밖 경고에서 중단한 뒤, 정상일 때만 보드를 재생성·점검한다. 운영 실행에서 실패하거나 task가 빠지면 수동 Task Board를 보존하고 PRE-HANDOFF로 돌아가 이중 동기화를 재개한다.

현재 ledger 상태는 PRE-HANDOFF다. M3 항목 검토와 생성 Board의 세 섹션·이력 보존 검증이 남아 있어, 이번 prompt 업데이트 자체로 운영 소유권이나 Task Board 쓰기 흐름은 바뀌지 않았다. 실제 Daily/Weekly Roundup 운영 실행은 아직 검증하지 않았다.
