# Claude Code에서 막힌 정보 수집을 Codex가 자동화한 과정

**작성일**: 2026-07-19  
**최신 확인**: 2026-07-24  
**용도**: 향후 영상 소재 및 VibeLearn AI 프로세스 회고  
**Topic**: Seattle Tech Week 2026

## 한 줄 요약

처음 Claude Code 작업에서는 Luma 화면에 보이는 이벤트 목록과 개별 이벤트 세부 정보를 안정적으로 연결하지 못해 사용자의 화면 캡처에 의존했다. 이후 Codex 작업에서는 Luma 웹페이지가 내부적으로 호출하는 공개 JSON API를 찾아 전체 이벤트 데이터를 직접 수집하면서, 화면 캡처 없이 5일치 전체 일정과 링크를 자동으로 정리할 수 있었다.

이번 사례는 한마디로 **Codex Win**이다. Claude Code가 화면 기반 정보 수집의 한계에 걸렸던 지점에서, Codex는 웹앱의 데이터 흐름을 추적해 자동화 가능한 해결책을 찾아냈다.

## 처음 Claude Code 작업에서 한계가 있었던 이유

Claude Code는 Seattle Tech Week 2026 이벤트가 모여 있는 Luma 허브 페이지는 찾았다. 그러나 허브 페이지에 보이는 각 이벤트의 세부 정보, 시간, 장소, 등록 상태, 개별 링크를 안정적으로 추출하는 데 실패했다. 사용자가 보기에는 페이지에 정보가 보이지만, AI 에이전트 입장에서는 그 정보가 정적인 HTML 문서에 들어 있는 것이 아니라 JavaScript로 동적으로 불러와지는 데이터일 수 있다.

이런 페이지에서는 일반적인 검색이나 페이지 텍스트 읽기만으로는 충분하지 않다. 화면에는 카드 목록이 보이지만, 실제 데이터는 브라우저 안에서 API 호출을 통해 렌더링된다. 따라서 AI가 "페이지를 찾았다"는 것과 "그 페이지의 모든 이벤트 데이터를 구조화해서 가져왔다"는 것은 전혀 다른 문제다.

또 다른 한계는 이벤트별 세부 페이지 탐색이다. 허브 화면의 카드에서 각 이벤트 링크를 하나씩 찾아 들어가야 하고, 들어간 뒤에도 시간, 장소, 상태, 태그를 다시 추출해야 한다. 이벤트가 200개 이상이면 수작업 링크 추적 방식은 금방 병목이 된다. 결국 사용자가 7/27 화면 캡처를 제공했고, Claude Code는 그 캡처 기반으로 보이는 행사들을 정리한 뒤 개별 링크를 나중에 보강하는 방식으로 우회했다.

## 사용자가 제공한 우회 방법

사용자는 Luma 허브에서 7/27 행사 목록 화면을 캡처해 Claude Code에 전달했다. 이 방식은 화면에 보이는 정보를 사람이 한 번 안정적으로 "고정"해 주는 효과가 있었다. AI는 캡처 안의 텍스트를 읽고 이벤트 제목, 시간, 장소 같은 정보를 표로 만들 수 있었다.

하지만 이 방법은 확장성이 낮다. 7/27 하루는 처리할 수 있지만, 7/28~7/31까지 같은 과정을 반복하려면 날짜별 화면 캡처가 계속 필요하다. 또한 이벤트 상태가 바뀌면 다시 캡처해야 하고, 링크 매칭도 별도 검색에 의존해야 한다. 즉, 사람이 AI에게 데이터를 전달하는 방식이지, AI가 데이터 원천에 직접 접근하는 자동화 방식은 아니었다.

## Codex에서 해결한 방법

Codex에서는 문제를 "화면에 보이는 텍스트를 읽는 작업"이 아니라 "Luma가 이벤트 데이터를 어디서 가져오는지 찾는 작업"으로 바꾸었다. Luma 페이지의 JavaScript 번들과 네트워크 호출 구조를 확인해, 허브가 내부적으로 사용하는 공개 API 엔드포인트를 찾아냈다.

확인된 핵심 정보는 다음과 같다.

| 항목 | 값 |
|---|---|
| Calendar ID | `cal-7YGhWSN0o5k0LsQ` |
| API endpoint | `https://api.luma.com/calendar/get-items?calendar_api_id=cal-7YGhWSN0o5k0LsQ&period=future` |
| 페이지네이션 | `pagination_limit`, `pagination_cursor`, `has_more`, `next_cursor` |
| 2026-07-19 수집 결과 | 전체 237개 이벤트, AI 태그 74개 |
| 2026-07-24 재확인 결과 | 현재 예정 행사 242개, AI 태그 77개, `has_more=false` |

이 API를 호출하자 각 이벤트의 제목, 시작 시간, 종료 시간, 장소, 태그, 등록 상태, Luma URL을 구조화된 JSON으로 받을 수 있었다. 이후 페이지네이션을 따라가며 전체 5일치 이벤트를 가져왔고, AI 태그가 붙은 이벤트를 선별해 `events-auto.md`로 저장했다. 2026-07-24에는 같은 Luma 공개 캘린더를 다시 확인해 현재 예정 행사 수가 242개로 늘어난 것을 기록했고, 이 전체 후보를 AI와 함께 분석해 실제 참가 가능한 일정으로 추려냈다.

## 무엇이 달라졌나

가장 큰 차이는 AI가 정보를 얻는 위치다. Claude Code 단계에서는 화면 또는 검색 결과를 읽는 방식이었다. Codex 단계에서는 웹앱이 사용하는 데이터 통로를 찾아 구조화된 원천 데이터에 접근했다.

| 구분 | Claude Code 초기 방식 | Codex 해결 방식 |
|---|---|---|
| 접근 대상 | Luma 화면, 검색 결과, 사용자 캡처 | Luma 공개 JSON API |
| 데이터 형식 | 화면 텍스트, OCR, 수동 링크 매칭 | 구조화된 JSON |
| 확장성 | 날짜별 캡처 필요 | 전체 일정 자동 수집 |
| 정확성 | 화면에 보이는 정보와 검색 결과에 의존 | API의 시간, 장소, 태그, 상태, 링크 사용 |
| 병목 | 이벤트별 세부 링크 추적 | 페이지네이션 처리 |
| 결과 | 7/27 중심 정리 | 7/27~7/31 전체 행사 자동 수집, 2026-07-24 기준 예정 242개·AI 77개 확인 |

## 영상에서 사용할 수 있는 메시지

이 사례는 "AI Agent가 못한다"가 아니라 "어떤 레벨의 문제로 정의했는가"가 성능을 좌우한다는 사례다. 처음 문제는 "이 웹페이지에 있는 이벤트들을 정리해 줘"였다. 이 요청은 사람에게는 자연스럽지만, AI에게는 동적 웹페이지, 숨겨진 API, 페이지네이션, 링크 매칭, 상태 변경이라는 여러 하위 문제가 섞인 요청이다.

Codex에서 해결된 이유는 요청을 더 깊게 재정의했기 때문이다. 화면을 읽는 대신 "이 서비스가 데이터를 가져오는 원천을 찾아라"로 문제를 바꾸자, 수작업 캡처와 링크 검색이 필요 없어진다. 이것은 AI 활용에서 중요한 패턴이다. 결과물을 시키는 것보다, 데이터가 흐르는 구조를 찾게 하면 자동화 수준이 달라진다.

주간 영상에서는 이 숫자를 명확한 사례로 사용할 수 있다. "Seattle Tech Week 2026에는 현재 예정 행사만 242개가 있었고, 그중 AI 태그가 붙은 행사도 77개였다. 이 많은 후보를 사람이 하나씩 고른 것이 아니라, Codex로 Luma 데이터 원천을 찾아 전체 후보를 구조화하고, AI와 함께 관심사·오프라인 가치·캘린더 충돌 기준으로 추려 실제 일정으로 만들었다"는 흐름이다.

## 영상 제작 방향

이 영상은 "AI Agent가 모든 것을 알아서 끝냈다"는 과장된 사례가 아니라, **일상에 AI를 실제로 적용하면 어디까지 시간을 줄일 수 있고 어디서부터는 아직 사람이 결정해야 하는가**를 보여주는 실험으로 만든다. Seattle Tech Week 2026에는 예정 행사만 242개가 있었고, AI 태그가 붙은 행사도 77개였다. 이 많은 행사 중에서 실제로 참석하고 싶은 행사를 찾고, 내용을 읽고, 시애틀과 Bellevue 사이 이동 시간까지 감안해 일정을 세우고, Google Calendar에 넣는 일을 사람이 혼자 했다면 시간과 에너지가 매우 많이 들었을 것이다.

이번 실험에서 AI가 가장 크게 줄여 준 부분은 행사 정보를 리뷰하고 내용을 파악하는 시간이다. AI는 Luma 공개 데이터에서 행사 제목, 시간, 장소, 태그, 등록 상태, 링크를 구조화했고, 사용자의 기존 관심사와 작업 기록을 바탕으로 관심 가질 만한 후보를 먼저 추려 보고했다. 사용자는 AI가 추린 후보만 보고 행사 내용, 장소, 이동 동선, 일정 충돌을 판단한 뒤 신청 여부를 결정했고, 선택한 일정은 Google Calendar에 등록하도록 지시했다. 이 과정에서 사용자가 평소 작업 내용과 인사이트를 모두 로컬 컴퓨터의 Markdown 파일로 저장해 두었기 때문에, AI는 단순히 공개 행사 목록만 본 것이 아니라 사용자의 관심사, 프로젝트, 과거 판단 기준까지 함께 참고할 수 있었다.

영상에서 강조할 지점은 **기록이 AI의 판단 품질을 높인다**는 것이다. 사용자가 작업하면서 남긴 `md` 파일, WorkLog, Rundown, Daily Roundup, Topic 산출물은 AI가 "이 사람이 무엇에 관심이 있는지"를 추론하는 근거가 된다. 그래서 AI는 단순히 인기 있어 보이는 행사를 추천한 것이 아니라, Build with AI, AI Agent, VibeLearn, Catch Up AI, 지역 AI 생태계, 오프라인 네트워킹과 연결되는 행사를 우선해 보고할 수 있었다.

다만 이 실험은 AI Agent의 한계도 함께 보여준다. AI가 행사 후보를 분석하고 일정 계획을 세우는 데는 큰 도움을 줬지만, Luma 행사 페이지에 직접 들어가서 사용자를 대신해 `Register`, `Request to Join`, `Join Waitlist`를 안정적으로 완료하는 수준까지는 자동화하지 못했다. 아직 AI Agent가 웹사이트에 로그인하고, 승인 흐름을 처리하고, 사용자의 개인정보와 신청 버튼을 안정적으로 다루는 기술은 일반 사용자가 안심하고 쓸 만큼 보편화되어 있지 않다. 사용자가 언급한 OpenClaw/OpenCUA 계열 도구나 Hermes 같은 서비스, 또는 Codex 계열의 일부 브라우저/웹 자동화 기능이 이런 방향을 지원하려고 하지만, 현재는 안정성 검증, 설치, 플랜, 권한 설정, 실패 대응이 복잡해 일반적인 생활 도구로 쓰기에는 부담이 크다.

따라서 이 영상의 결론은 "AI가 나 대신 모든 참가 신청을 했다"가 아니다. 결론은 **AI를 잘 쓰면 많은 정보를 빠르게 읽고, 내 기록을 바탕으로 후보를 추리고, 내가 결정할 수 있는 형태로 정리하고, 결정된 일정을 실행 계획으로 옮기는 데 큰 도움을 받을 수 있다**는 것이다. 사용자는 AI 일상 적용 실험을 할 때 시청자가 비교적 쉽게 따라 할 수 있고, 실험 과정과 그 과정에서 얻은 인사이트가 실제 생활에 도움이 되는지를 기준으로 삼는다. 이 영상은 그 기준에 맞는 사례로, 일반 시청자도 자신의 컨퍼런스, 세미나, 지역 행사, 여행 일정, 학습 계획에 비슷하게 적용해 볼 수 있는 수준의 워크플로를 보여준다.

### 영상의 핵심 메시지

- Seattle Tech Week 2026에는 현재 예정 행사 242개, AI 태그 행사 77개가 있었다.
- 사람이 혼자 모든 행사 정보를 읽고, 관심 후보를 추리고, 장소와 이동 시간을 계산하고, 캘린더에 넣는다면 시간과 에너지가 많이 든다.
- AI를 쓰면 행사 정보 리뷰, 내용 파악, 후보 선별, 일정 충돌 검토가 크게 빨라진다.
- 사용자의 작업 기록이 모두 로컬 Markdown 파일로 남아 있었기 때문에, AI는 사용자의 관심사와 프로젝트 맥락을 참고해 더 적절한 후보를 추천할 수 있었다.
- AI Agent가 행사 등록까지 완전히 자동화한 것은 아니다. 신청 버튼 클릭, 로그인, 승인 흐름 처리는 아직 일반 사용자에게 안정적으로 맡기기 어렵다.
- 실용적인 결론은 "AI가 모든 것을 대신한다"가 아니라 "AI가 정보 과부하를 줄이고, 사람이 결정할 수 있는 형태로 정리해 준다"이다.

- 시애틀과 Bellevue 사이 이동 시간이 약 30분 걸리므로, 단순히 좋은 행사만 고르는 것이 아니라 실제 동선을 고려해야 했다.
- AI가 추린 후보를 사용자가 보고, 행사 내용·장소·시간·승인 상태·동선을 감안해 최종 선택했다.
- AI Agent가 Luma에 직접 로그인해 모든 행사 신청을 완전히 대신한 것은 아니다.

### 톤과 주의점

- 과장 금지: "AI가 알아서 다 했다"라고 말하지 않는다.
- 현실적인 실험으로 말한다: "내가 직접 해 보니 어디가 빨라졌고, 어디는 아직 사람이 해야 했다"는 톤을 유지한다.
- 시청자가 따라 할 수 있는 수준으로 설명한다: 고급 웹 자동화나 불안정한 에이전트 설치를 전제로 하지 않는다.
- OpenClaw/OpenCUA, Hermes, Codex 계열 웹 자동화 가능성은 "이런 시도가 있지만 일반 사용자가 안정적으로 쓰기에는 아직 복잡하다"는 맥락으로만 언급한다.
- 핵심 문장은 "AI는 행사 신청을 대신해 준 마법사가 아니라, 242개 행사 속에서 내가 결정할 수 있는 후보를 빠르게 정리해 준 의사결정 보조자였다"로 잡는다.

### 영상 제작 AI에게 줄 직접 지시문 초안

```markdown

핵심 메시지는 "AI가 모든 것을 대신한 것이 아니라, 242개 행사 속에서 내가 실제로 결정할 수 있는 후보를 빠르게 추려 준 의사결정 보조자였다"입니다.

- AI에게 Google Calendar 등록까지 지시했지만, Luma 행사 페이지에서 직접 신청/승인/대기 등록을 안정적으로 자동 처리하는 것은 아직 일반 사용자에게 보편화된 수준이 아니다.
```

## 사용자의 인사이트와 연결

이 사례는 사용자의 "AI Agent는 100마일짜리 4차선 고속도로 중 5마일만 10차선으로 넓힌 것"이라는 비유와도 연결된다. Claude Code가 페이지를 찾는 구간은 빠르게 지나갔지만, 이벤트별 세부 정보 수집과 링크 매칭이라는 다음 95마일에서 병목이 생겼다. 단순히 첫 5마일의 속도, 즉 페이지 검색이나 텍스트 요약 능력만 빨라져서는 전체 워크플로가 자동화되지 않는다.

Codex가 한 일은 5마일을 더 빠르게 달린 것이 아니라, 병목이 생긴 구간의 도로 구조를 다시 찾은 것이다. 화면 캡처라는 우회도로 대신 API라는 본선을 발견하면서, 전체 일정 수집이 반복 가능한 자동화 작업으로 바뀌었다. 이 차이가 AI Agent 워크플로 설계에서 중요하다.

## 향후 재사용 가능한 자동화 패턴

1. 먼저 사용자가 보는 화면과 AI가 접근 가능한 데이터가 같은지 확인한다.
2. 동적 웹페이지라면 HTML 텍스트만 읽지 말고 JavaScript 번들과 네트워크 호출을 확인한다.
3. 공개 API가 있으면 화면 캡처 대신 API에서 구조화된 데이터를 수집한다.
4. 페이지네이션, cursor, limit 같은 반복 수집 구조를 확인한다.
5. 원천 데이터를 저장한 뒤, 선별과 추천은 별도 단계로 분리한다.
6. 행사처럼 상태가 바뀌는 정보는 최종 결정 직전에 다시 확인한다.

## 결론

처음 실패의 원인은 AI의 요약 능력 부족이 아니라, 데이터 접근 방식의 한계였다. Claude Code는 사용자가 보는 Luma 화면을 안정적인 데이터 소스로 바꾸지 못했고, 그래서 캡처와 수동 링크 보강이 필요했다. Codex는 Luma가 내부적으로 쓰는 공개 JSON API를 찾아 데이터 수집 방식을 바꾸었고, 그 결과 현재 기준 242개 예정 행사와 77개 AI 태그 이벤트를 확인한 뒤 실제 참가 일정으로 선별하는 흐름까지 자동화할 수 있었다. 이번 건은 명확히 **Codex Win**으로 기록할 만하다.
