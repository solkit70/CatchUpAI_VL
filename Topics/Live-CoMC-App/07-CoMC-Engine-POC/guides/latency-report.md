## 목표와 결과

로드맵 목표: **발화 종료 → 화면 2.5초 / → 음성 4초**

| | 목표 | 실측(중앙) | 실측(최악) | 판정 |
|---|---|---|---|---|
| 화면 | 2,500ms | **12,230ms** | 12,644ms | ❌ 목표의 4.9배 |
| 음성 | 4,000ms | — | — | **미확정** |

**음성 목표를 재지 않은 이유**: M6 TTS 실측(첫 청크 588ms)은 *파일이 만들어지기까지*이고
스피커에서 소리가 나기까지가 아니다. 가상 케이블 버퍼는 M6 오디오 라우팅을 구성한 뒤에야
잴 수 있다. 재지 않은 것을 잰 척하지 않는다.

## 격차의 원인 — 셋으로 분해된다

측정: [../src/run_pipeline.py](../src/run_pipeline.py) ·

### ① 프로세스 기동 + import (약 3.7초)

파일 기반 6단계를 **매 발화마다 6개 프로세스**로 돌리고 있다. 각 프로세스가
인터프리터를 새로 띄우고 라이브러리를 다시 import 한다.

| | 소요 |
|---|---|
| 인터프리터 기동만 | 145ms |
| + jsonschema | 427ms |
| + openai SDK | 2,321ms |

③⑤⑥ 단계는 실제 작업이 거의 없는데도 각 400~560ms 가 든다. 그게 전부 기동 비용이다.
④ 는 여기에 openai SDK import 가 얹혀 약 2.4초.

### ② 연결 설정 — 첫 호출에만 약 3초

한 프로세스 안에서 같은 호출을 3회 반복했더니 이렇게 나왔다.

```
근거 2건 / 3문장   1회차 5,097ms   2·3회차 ~2,000ms
```

첫 호출에 TLS 핸드셰이크·커넥션 풀 초기화가 붙는다. **매 발화마다 새 프로세스를 띄우면
모든 호출이 '첫 호출'이 되어 이 3초를 매번 지불한다.**

### ③ 근거 풀 크기 (2건 → 15건에 +1.3초)

프로세스 기동 비용을 뺀 순수 LLM 시간. 조건당 3회 중앙값.

| 조건 | 중앙 | 최악 | 입력 토큰 |
|---|---|---|---|
| 근거 2건 / 3문장 | 2,124ms | 5,097ms | 1,239 |
| 근거 2건 / 5문장 | 2,246ms | 2,255ms | 1,239 |
| 근거 15건 / 3문장 | 3,507ms | 4,723ms | 2,079 |
| 근거 15건 / 5문장 | 3,537ms | 4,453ms | 2,079 |

- **근거 2건 → 15건: +1,291ms** ← 지배적
- **문장 3개 → 5개: +122ms** ← 거의 영향 없음

출력 길이를 줄여 지연을 잡으려는 흔한 최적화가 **이 파이프라인에서는 헛수고**다.
줄여야 할 것은 답변 길이가 아니라 **근거 풀**이다.

M5 마이크로벤치마크에서 2.6초로 잰 것과 파이프라인에서 5.7~7.7초로 잰 것의 차이가
여기서 설명된다 — 그때는 근거 2건이었고 지금은 15건이며, 그때는 연결이 살아 있었다.

## 사전 캐시 효과는 측정되지 않았다

로드맵은 ①② 를 방송 전에 미리 빌드해 지연을 줄이는 것을 요구했다. 실제로 재 보니:

```
cold (①~⑥ 전부 실행)   중앙 10,561ms
warm (③~⑥ 만 실행)     중앙 12,230ms      ← 오히려 느림
```

**효과가 음수로 나왔다.** ①② 가 절약하는 것은 약 800ms 인데, ④ 의 LLM 편차가
±2,000ms 라 묻힌다. 사전 캐시가 무의미하다는 뜻은 아니고, **이 측정 방법으로는
보이지 않는다**는 뜻이다. 지금 구조에서는 다른 두 요인이 너무 커서 그 밑의 효과를 가린다.

→ ①②를 미리 하는 것 자체는 여전히 옳다(방송 중에 할 이유가 없다).
   다만 **지연 대책으로서의 우선순위는 낮다.**

> 🔴 **2026-08-31 정정 2건**
>
> 1. **케이블 314ms 는 과대계상이다.** MME 경로로 잰 값이었고, WASAPI 로는 63~124ms 다.
>    전체 예산에서 **약 250ms 를 빼야 한다** → [근거](../../09-Desktop-Shell-and-Overlay/guides/panic-stop-benchmark.md)
> 2. **1번 대책(단일 장기 프로세스)의 절감폭은 warm 기준 3.2초다.** 여기 적힌 6.7초는
>    `cold` 기준이다 → [M9 실측](../../09-Desktop-Shell-and-Overlay/guides/daemon-latency-report.md)

## 결론 — 무엇을 고쳐야 하는가

우선순위대로.

| # | 대책 | 예상 절감 | 어디서 |
|---|---|---|---|
| 1 | **단일 장기 실행 프로세스** — 파일 계약은 유지하되 프로세스는 하나 | ~6.7초 (기동 3.7 + 연결 3.0) | **M9 셸** |
| 2 | **근거 풀 축소** — `--max-evidence` 를 낮추고 관련도 상위만 | ~1.3초 | M8 (관련도 판정 강화) |
| 3 | 컨텍스트 사전 캐시 | ~0.8초 (측정 한계 이하) | 이미 가능 |

1번이 압도적이다. **이것은 파일 기반 설계를 버리라는 뜻이 아니다** —
각 단계가 JSON 을 읽고 쓰는 계약은 사고 추적에 필수적이고 그대로 둔다.
바꿀 것은 *프로세스 경계*이지 *파일 경계*가 아니다.

1번을 적용하면 발화당 비용은 LLM 호출(2.1~3.5초) + 단계 오버헤드(수십 ms)로 줄어든다.
근거 풀을 2건 수준으로 좁히면 **화면 2.5초 목표는 사정권**에 들어온다.
다만 최악값(근거 2건에서도 2,255ms)이 목표에 바짝 붙으므로 여유는 없다.
