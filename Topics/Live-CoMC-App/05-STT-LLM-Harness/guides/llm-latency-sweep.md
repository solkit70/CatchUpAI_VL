## 왜 쟀나

M5에서 3사 LLM 지연이 **10.8~21.6초**로 나왔다. 같은 파이프라인의 STT는 1.2초였다.
전체의 90% 이상이 ⑥ LLM 응답 단계에 있다는 뜻이고, M7(Co-MC 엔진 POC)의
목표 지연이 여기에 통째로 걸려 있다. 지연 대책을 다른 단계에 쓰면 헛수고다.

가설은 하나였다 — **3사 모두 추론이 켜진 채로 호출되고 있다.**

## 무엇을 재고 무엇을 안 쟀나

| 측정 | 재는 이유 |
|---|---|
| 총 지연 | 이 파이프라인에서 유일하게 의미 있는 지연 |
| 추론 토큰 | 지연의 원인을 직접 설명하는 숫자 |
| 계약 준수 | effort 를 낮춘 대가가 형식 파괴로 나타나는지 |
| 발화문 자체 | 계약이 잡지 못하는 **내용** 저하를 눈으로 보기 위해 |

**TTFT(첫 토큰 지연)는 재지 않았다.** ⑦ 안전 검증 게이트가 JSON 전체를 받아
근거 대조까지 끝낸 뒤에야 발화가 허용된다. 첫 토큰이 아무리 빨리 와도 그 시점에
할 수 있는 일이 없다. 스트리밍으로 TTFT 를 줄이는 흔한 최적화가 이 구조에서는
아무것도 앞당기지 못한다.

→ 같은 논리가 TTS 에서는 **뒤집힌다**. ⑧ 단계에 들어온 텍스트는 이미 게이트를
통과했으므로 첫 오디오 청크가 도착하는 즉시 재생할 수 있다. 그래서 M6 TTS 측정에서는
첫 청크 지연이 실질 지표다. 같은 "첫 조각 지연"이 어느 단계냐에 따라 의미가 정반대다.

측정 조건: 동일 프롬프트·동일 근거 2건, 수준당 2회, 재시도 없음(`max_retries=0`).
재시도가 섞이면 "한 번 호출의 지연"이 아니라 "재시도 포함 지연"이 되어 비교가 흐려진다.

## 읽은 것

### 1. 지연은 추론 토큰이다 — 다른 요인이 아니다

OpenAI 가 이 관계를 그대로 보여준다. 추론 토큰 1440 → 0 으로 갈 때 지연이
15.2초 → 2.6초로 떨어진다. 출력 토큰도 1728 → 290 으로 함께 줄지만, 실제 발화문의
길이는 거의 그대로다 — 줄어든 1400여 토큰은 **사용자에게 도달하지 않는 사고 과정**이었다.

Gemini 도 같다. 기본값에서 사고 토큰 1141개를 쓰는데 답변 본문은 311토큰이다.
**기본값이 곧 high 에 가깝다**는 뜻이다. `thinking_level=low` 를 명시하면 사고가
아예 사라지고 4.1초가 된다.

### 2. Claude 는 effort 에 거의 반응하지 않는다

7.0초 ~ 7.7초. 전 구간 변동이 10% 이내이고 이건 2회 측정의 편차 범위와 겹친다.
**Opus 5 는 thinking 이 기본 adaptive** 라서, 모델이 이 작업에 필요한 만큼만 이미
쓰고 있었다고 읽는 것이 자연스럽다. 근거가 2건뿐이고 답이 2~3문장인 과제에서는
더 줄일 사고가 애초에 없다.

파라미터가 무시된 것이 아니라는 점은 따로 확인했다. `output_config.effort` 에
없는 값(`nonsense-level`)을 보내면 서버가 400 과 함께 유효 목록을 돌려준다.
요청이 도달해 검증까지 받고 있다.

> ⚠️ 설치된 `anthropic` SDK 가 0.75.0 이라 `output_config` 를 명시 인자로 받지 못한다
> (`TypeError`). `extra_body={"output_config": {...}}` 로 우회했고, 서버가 받는 JSON 은
> 동일하다. SDK 1.x 로 올리면 정식 인자로 바꿀 수 있으나 `httpx2` 전환 등 파괴적
> 변경이 딸려 오므로 별도 작업으로 미뤘다 → 백로그.

**thinking 을 끄는 선택지는 쓰지 않았다.** Claude 어댑터는 strict tool use 기반인데,
Opus 5 에서 thinking 을 끄면 도구 호출이 `tool_use` 블록 대신 **본문 텍스트로 새는**
실패 모드가 있다. 그 경우 호출은 200 으로 성공하고 도구는 실행되지 않으며 오류도 나지 않는다 —
방송 중이라면 조용히 침묵하는 형태로 나타났을 것이다. effort 를 낮추는 쪽이 안전하고
비용도 같이 준다.

### 3. 품질은 떨어지지 않았다 — 방송에는 오히려 낫다

계약 통과 여부만으로 결론 내리면 안 된다. 스키마는 형식만 본다. 실제 발화문을
나란히 놓고 봤다 ([llm_effort_quality.py](../examples/llm_effort_quality.py)).

```
openai (기본값)  추론 1664tok · 2문장
  [0] 3번 파트는 FDE 영상 제작 과정을 다루고요, 한국어 28분 1초와 영어 27분 11초 두 편을 공개했어요.
  [1] 또 조사 문서는 42개고, GitHub에 전부 공개돼 있어요.

openai (minimal) 추론 0tok · 3문장
  [0] 오늘 3번 파트는 FDE 영상 제작 과정을 다룹니다.
  [1] 한국어 28분 1초, 영어 27분 11초 두 편을 공개했고요.
  [2] 또 조사 문서 42개가 있으며 GitHub에 전부 공개돼 있습니다.
```

제공된 근거 2건을 양쪽 모두 빠짐없이 썼고, 누락된 정보가 없다. 오히려 minimal 쪽이
**한 문장을 한 호흡에 읽을 수 있는 길이**로 끊어 놓았다 — TTS 로 넘길 때 유리한 형태다.
M1 계약이 "문장당 한 호흡"을 요구한 이유가 여기서 맞아떨어진다.

다만 이 시험 질문은 **쉬운 축**이다. 근거가 2건뿐이고 커버리지가 `defined` 이며
안전 판단이 필요 없다. 추론이 0인 상태에서 어려운 경로 — 커버리지 `undefined`,
근거가 서로 충돌, 안전 정책 경계선 — 가 어떻게 되는지는 이 측정이 답하지 못한다.
→ **M8(안전 게이트 시나리오 확장)에서 어려운 질문 세트로 다시 재야 한다.**

### 4. 폴백 순서를 바꿔야 한다

M3 설계와 M5 구현은 `claude → openai → gemini` 순서를 썼다. 지연 기준으로 보면
튜닝된 상태에서 이 순서는 **가장 느린 것을 1순위에 둔 것**이 된다.

| 순위 | 프로바이더 | 설정 | 중앙 | 최악 |
|---|---|---|---|---|
| 1 | openai | `reasoning_effort=minimal` | 2.6s | 2.8s |
| 2 | gemini | `thinking_level=low` | 4.1s | 4.6s |
| 3 | claude | 기본값 | 7.2s | 7.8s |

방송에서는 중앙값보다 **최악값**이 중요하다. 한 번의 긴 침묵이 스무 번의 빠른 응답을
지운다. 최악값 기준으로도 순서는 같다.

Claude 를 뺄 이유는 없다. 편차가 가장 작고(6.7~7.8초, 폭 1.1초) 튜닝 없이 그 성능이므로
**마지막 보루로 적합하다**. OpenAI 는 기본값 편차가 12.2~18.1초로 가장 크다 —
튜닝하지 않으면 가장 위험한 선택이었다는 뜻이기도 하다.

### 5. M7 전제 — 목표 지연은 달성 가능하다

첫 오디오가 나가기까지의 경로를 M5·M6 실측으로 이어 붙이면:

| 구간 | M5 시점 | 튜닝 후 |
|---|---|---|
| ⑤ STT | 1.2s | 1.2s |
| ⑥ LLM | 15.2s (openai 기본값) | 2.6s (minimal) |
| ⑧ TTS 첫 청크 | — | 0.7s (edge-tts) |
| **첫 발화까지** | **~17s** | **~4.5s** |

17초는 방송에서 사고에 가깝다. 4.5초는 진행자가 한 마디 얹으면 덮이는 길이다.
**M7 을 파일 기반 6단계로 진행해도 된다는 근거가 확보됐다.**

### 6. 대기 필러는 여전히 필요하지만, 요구가 달라진다

M5 회고에서 진행자가 제안한 대기 필러는 유효하다. 4.5초 침묵도 라이브에서는 길다.
다만 설계 요구가 바뀐다.

- 17초를 메우려면 **여러 개의 필러와 자연스러운 이어붙이기**가 필요했다
- 4.5초는 **짧은 한 마디 하나**로 덮인다

문구 제약은 M5 결론 그대로다. ⑦ 게이트가 차단하는 것이 정상 동작이므로,
필러는 **확인은 약속하되 답변은 약속하지 않아야** 한다
(`"네, 확인해 볼게요"` ○ / `"답변 드릴게요"` ×). 지키지 못할 약속은 침묵보다 나쁘다.

→ 트리거 시점·중복 방지·차단 시 후속 문구는 M6 오디오 라우팅에서 확정한다.

## 남은 것

- [ ] 어려운 질문 세트(커버리지 미정·근거 충돌·안전 경계)에서 minimal 재측정 → **M8**
- [ ] `llm_registry.json` 의 `fallback_order` 를 `openai → gemini → claude` 로 변경하고
      프로바이더별 기본 effort 를 레지스트리에 등재 → **M7 진입 시**
- [ ] `anthropic` SDK 1.x 업그레이드 후 `extra_body` 우회 제거 → 백로그
- [ ] Qwen 은 LLM 프로바이더로 등재돼 있지 않다. TTS 로만 쓰는 것이 맞는지 판단 필요
