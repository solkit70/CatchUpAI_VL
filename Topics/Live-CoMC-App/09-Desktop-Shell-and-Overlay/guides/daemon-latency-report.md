# 단일 장기 프로세스 — 지연 실측 리포트

**측정일**: 2026-08-31 · **회차 샘플**: Live21 · **각 조건 5회**
**질문 문장**: `오늘 3번 파트에서 뭘 다루나요?`

## 무엇을 재려고 했나

M7 지연 리포트가 대책 세 개를 우선순위대로 내놓았다. 그중 1번과 2번을 M9에서 실측한다.

| # | 대책 | M7 예상 절감 | 이 리포트 |
|---|---|---|---|
| 1 | **단일 장기 실행 프로세스** | ~6.7초 | ✅ 실측 |
| 2 | **근거 풀 축소** | ~1.3초 | ✅ 실측 |
| 3 | 컨텍스트 사전 캐시 | ~0.8초 | 이미 적용됨 (warm 조건) |

## 결과

**모든 수치는 같은 날 같은 조건에서 잰 것이다.** 과거 측정치와 섞지 않았다 —
LLM 응답 시간은 날마다 흔들리므로, 구조 변경의 효과와 네트워크 변동을 섞으면
아무것도 증명하지 못한다.

| 조건 | 중앙값 | 최악 | 최선 | 근거 |
|---|---:|---:|---:|---:|
| **기존** — subprocess 6개 | **9,084ms** | 13,034ms | — | 14건 |
| **데몬** — 단일 프로세스 | **5,886ms** | 9,081ms | 5,370ms | 14건 |
| **데몬 + 근거 3건** | **4,521ms** | 6,236ms | **2,581ms** | 3건 |
| **데몬 + 근거 2건** | **4,369ms** | 5,638ms | 3,561ms | 2건 |

### 단계별로 보면 어디가 사라졌는지 분명하다

| 단계 | 기존 (중앙) | 데몬 (중앙) | 변화 |
|---|---:|---:|---|
| ③ 의도 분류 | 214ms | **3ms** | −211 |
| ④ 답변 생성 (LLM) | 8,549ms | **5,875ms** | −2,674 |
| ⑤ 검증·게이트 | 210ms | **3ms** | −207 |
| ⑥ 출력 렌더 | 194ms | **4ms** | −190 |
| **①② 사전 캐시** | 878ms | **11~33ms** | −845 |

**③⑤⑥은 사실상 0이 됐다.** 이 세 단계는 원래도 계산량이 거의 없었고,
측정된 200ms는 전부 **파이썬 기동 + import 비용**이었다. 프로세스를 안 띄우니 사라졌다.

### ④가 2.7초 줄어든 이유

④는 LLM을 실제로 호출하는 단계라 네트워크 왕복이 대부분이다. 그런데도 2,674ms 줄었다.
**클라이언트 재사용** 때문이다.

```
기존   매 호출마다  import openai → OpenAI() 생성 → TLS 핸드셰이크 → 요청
데몬   최초 1회만   import openai → OpenAI() 생성 → TLS 핸드셰이크
       그 뒤로는                              커넥션 풀 재사용 → 요청
```

`llm_providers.build`를 메모이즈해 `OpenAI()` 객체가 살아 있게 했다.
벤치 로그의 `프로바이더 build 호출 5회 중 실제 생성 1회`가 그 증거다.

M7이 "연결 설정 3.0초"라고 부른 것의 실체가 이것이었다.

## M7 예측과 대조

| 대책 | M7 예상 | 실측 | 판정 |
|---|---:|---:|---|
| 단일 장기 프로세스 | ~6.7초 | **3.2초** | ⚠️ **절반** |
| 근거 풀 축소 | ~1.3초 | **1.4초** | ✅ **거의 정확** |

**1번이 예상의 절반인 이유는 기준선이 다르기 때문이다.** M7의 6.7초는 `cold`
조건(①~⑥ 전부 발화 시점 실행) 기준이었고, 이 리포트의 기준선은 `warm`
(①②는 방송 전 완료)이다. **①②를 미리 해 두는 것만으로 이미 상당 부분을 벌고
있었고**, 데몬은 그 위에서 3.2초를 더 벌었다.

두 대책을 합치면 **9,084ms → 4,369ms, 52% 감소**다.

## 그래서 목표는 달성했나

**아직 아니다.**

| 목표 | 값 | 현재 (근거 3건) | 판정 |
|---|---:|---:|---|
| 화면 | 2,500ms | 중앙 4,521ms | ❌ **1.8배 초과** |
| 화면 (최선값) | 2,500ms | **2,581ms** | ⚠️ 아슬하게 미달 |
| 음성 | 4,000ms | 화면 + 케이블 314ms + TTS | ❌ |

**의미 있는 변화는 병목이 하나로 좁혀졌다는 것이다.**

```
기존   껍데기 3.2초  +  LLM 5.9초        ← 두 군데를 다 손봐야 했다
지금   껍데기 0.01초 +  LLM 4.5초        ← LLM 하나만 남았다
```

③⑤⑥이 합쳐서 **10ms**다. 여기서 더 깎을 것이 없다.
**남은 4.5초는 전부 LLM 왕복이고, 그것만으로 이미 목표를 넘는다.**

## 근거를 더 줄여도 안 줄어든다

| 근거 | 중앙값 | 직전 대비 |
|---:|---:|---|
| 14건 | 5,886ms | — |
| 3건 | 4,521ms | −1,365ms |
| 2건 | 4,369ms | **−152ms** |

**14 → 3에서 대부분을 벌고, 3 → 2는 거의 효과가 없다.** 프롬프트가 이미 충분히
짧아져 입력 토큰이 병목이 아니게 된 것이다. 근거를 더 줄이면 **답변 품질만 깎이고
속도는 안 는다.**

→ **근거 상한은 3건이 합리적 지점**으로 보인다. 다만 이 값은 질문 한 종류로 잰 것이라,
질문 유형을 넓혀 재확인이 필요하다.

## 다음에 손댈 곳

병목이 LLM 왕복 하나로 좁혀졌으므로, 남은 수단도 그쪽에 있다.

| 후보 | 기대 | 위험 |
|---|---|---|
| **스트리밍 출력** | 첫 글자까지의 시간을 재정의한다. 전체 완료를 기다리지 않고 화면에 흘리면 **체감 지연이 크게 줄어든다** | 검증·게이트를 문장 단위로 돌려야 한다. **M8 안전 게이트 설계를 다시 봐야 한다** |
| 더 작은 모델 | 왕복 단축 | 게이트 통과율이 떨어지면 무의미하다. M8 effort 관문을 다시 통과해야 함 |
| 대기 필러 | 지연을 못 줄이지만 **덮는다** | M6 설계대로 1.5초만 덮는다. 4.5초는 못 덮는다 |

**스트리밍이 유일하게 구조를 바꾸는 수단이다.** 다만 M8이 세운 안전 게이트는
*답변 전문을 받아서 검증한 뒤 내보내는* 구조라, 스트리밍과 정면으로 충돌한다.
**"검증 전에는 한 글자도 내보내지 않는다"는 원칙을 지키면서 스트리밍하는 방법**이
있는지가 다음 질문이다.

## 재현 방법

```bash
cd 09-Desktop-Shell-and-Overlay/examples/engine

# 데몬 (기본 근거)
python engine_daemon.py --live 21 --repeats 5

# 데몬 + 근거 축소
python engine_daemon.py --live 21 --repeats 5 --max-evidence 3

# 기존 방식 기준선
cd ../../../07-CoMC-Engine-POC/src
python run_pipeline.py --live 21 --repeats 5 --mode warm
```

> ⚠️ **LLM 호출은 유료다.** 5회씩 3조건이면 15회 호출이다. 반복 횟수를 올리기 전에
> 무엇을 확인하려는지 먼저 정한다.
