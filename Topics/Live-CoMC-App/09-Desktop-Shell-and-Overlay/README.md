# M9 - 데스크톱 셸 + OBS 오버레이 통합

**상태**: ✅ **실습 1~5 전부 완료** / Electron 셸만 미착수
**예상 학습 시간**: 12h · **소요**: 약 6h
**Topic**: Live-CoMC-App

## 요약

M9는 M7이 만든 파일 기반 6단계 파이프라인을 **실전에서 쓸 수 있는 형태**로 바꾸는 모듈이다.
로드맵의 실습은 다섯 개인데, M7 지연 리포트가 **실습 1(단일 장기 프로세스)을 최우선**으로
지목했으므로 그것부터 했다.

**결과 두 가지**

- **발화당 9,084ms → 4,369ms (52% 감소)** — 실습 1
- **패닉 스톱 최악 112ms** (목표 200ms) — 실습 4. 그리고 **M6 의 케이블 314ms 가 오측정**임을 발견
- **글로벌 핫키 15개** — 실습 2. 키를 스스로 눌러 검증하는 `--selftest` 포함
- **볼트 읽기 전용 강제** — 실습 5. 런타임에서 쓰기를 차단, 검증 9항목 통과
- **OBS 오버레이** — 실습 3. SSE 로 즉시 반영. **실사용에서 권위값 결함 1건 발견·수정**

## 이 모듈에서 확인된 것

### 1. 껍데기가 병목이었다는 M7의 진단은 맞았다

③⑤⑥ 단계가 각각 200ms 안팎이었는데, **계산량이 아니라 전부 파이썬 기동 + import
비용**이었다. 프로세스를 안 띄우자 **3ms로 떨어졌다.**

| 단계 | subprocess | 데몬 |
|---|---:|---:|
| ③ 의도 분류 | 214ms | **3ms** |
| ⑤ 검증·게이트 | 210ms | **3ms** |
| ⑥ 출력 렌더 | 194ms | **4ms** |

### 2. "연결 설정 3.0초"의 실체는 LLM 클라이언트 재생성이었다

M7이 원인 미상으로 남겨 둔 3.0초는 **`OpenAI()` 객체를 매번 새로 만들면서
커넥션 풀과 TLS 세션이 매번 버려진 것**이었다.

`llm_providers.build`를 메모이즈하는 것만으로 ④가 **8,549ms → 5,875ms**가 됐다.
LLM 왕복 자체는 그대로인데 2.7초가 사라졌다.

### 3. 근거 축소는 3건에서 멈춘다

| 근거 | 중앙값 | 직전 대비 |
|---:|---:|---|
| 14건 | 5,886ms | — |
| 3건 | 4,521ms | **−1,365ms** |
| 2건 | 4,369ms | −152ms |

**14 → 3에서 다 벌고, 3 → 2는 거의 없다.** 더 줄이면 답변 품질만 깎인다.

### 4. 패닉 스톱은 여유 있게 통과했다 — 그리고 M6 오측정을 찾았다

핫키 → 무음까지 **최악 112ms** (목표 200ms).

재는 김에 **시작 지연**도 같이 쟀더니 **71ms** 였다. M6 이 *"줄일 수 없는 고정 비용"*
이라고 적은 **314ms** 와 4배 넘게 벌어진다.

원인은 **장치 선택**이었다. M6 스크립트가 `ci[0]`(첫 매칭)을 쓰는데 이 환경의 첫 매칭이
**MME** 다 — Windows 에서 지연이 가장 큰 경로다. 같은 케이블을 WASAPI 로 열면
`sd.play` 124ms, 저지연 스트림 63ms 다.

→ [패닉 스톱 실측 리포트](guides/panic-stop-benchmark.md)

### 6. 핫키는 라이브러리 없이 Win32 로 해결됐다

`keyboard`·`pynput` 이 없었는데 **설치할 필요가 없었다.** `RegisterHotKey` 가 더 맞는 도구다.

| | `keyboard` 류 | `RegisterHotKey` |
|---|---|---|
| 동작 | 전역 훅 — **모든 키 입력을 가로챈다** | **그 조합만** 받는다 |
| 권한 | 관리자 필요할 때 있음 | 불필요 |
| 설치 | pip | **표준 라이브러리(ctypes)** |

방송 중에 도는 프로그램이 **모든 키 입력을 훔쳐보게** 만들 이유가 없다.

검증은 `keybd_event` 로 **키를 실제로 눌러서** 했다. 사람이 누를 필요 없이
`--selftest` 하나로 등록·전달·상태 반영까지 확인된다.

**M7 권위값 원칙을 코드로 지켰다** — 파트 전환은 반드시 `set_current_part(..., by="hotkey")`
를 거치고, `current_part_id` 에 직접 대입하는 줄은 이 파일에 존재하지 않는다.

### 7. 볼트 보호는 "조심하기"가 아니라 "못 하게 하기"로 만들었다

M2 App Boundary 의 제외 3번은 *"볼트 파일 쓰기 — 앱은 읽기 전용"* 이다.
그런데 **쓸 일이 없다**는 것과 **쓸 수 없다**는 것은 다르다.

사고는 세 경로로 난다.

1. **실수** — 디버깅하다 임시 파일을 볼트에 쓴다
2. **라이브러리** — 우리가 안 부른 코드가 캐시를 남긴다. 어디에 쓰는지 모른다
3. **경로 조작** — `../../` 가 섞인 경로가 볼트 밖에서 안으로 들어온다

**1번은 리뷰로 잡히지만 2·3번은 못 잡는다.** 그래서 런타임에서 막았다.

```python
with guard():
    ...엔진 실행...     # 이 안에서는 볼트 문서에 못 쓴다
```

`builtins.open` 과 `Path.open` 을 감싸 볼트 경로 쓰기 시도를 예외로 만든다.
**우리 코드든 남의 코드든 상관없다.**

> ⚠️ **보안 경계가 아니라 안전장치다.** 작정하고 우회하면 `os.open`·`ctypes`·서브프로세스로
> 뚫린다. 목적은 악의를 막는 것이 아니라 **사고를 막는 것**이다 —
> 이 앱의 위협 모델은 공격자가 아니라 **새벽 두 시의 나**다.

앱 자신의 산출물 폴더(`Topics/Live-CoMC-App/`)는 쓰기를 허용한다.
그건 방송 중 참조하는 "문서"가 아니라 학습 산출물이다.

### 8. 자기 검증이 통과한 코드가 실사용에서 틀렸다

오버레이가 다 만들어지고 자기 검증도 통과했는데, **핫키로 파트를 바꾸니 화면이
안 따라왔다.**

```
핫키 → session_state.current_part_id = 5   ← M7 이 정한 권위값 (화면이 안 봄)
⑥ 렌더 → overlay.json.part_id = 3          ← 마지막 발화 스냅샷 (화면이 이걸 봄)
```

서버가 `part_id` 를 `overlay.json` 에서 읽고 있었다. 그 파일은 ⑥ 단계가 **발화를
렌더할 때만** 갱신된다. 실전이었다면 **진행자가 다음 파트를 말하는데 화면에는
이전 파트 번호가 떠 있다.**

`--selftest` 는 페이지가 뜨는지, 상태를 주는지, 파일 변경이 전달되는지를 봤고
**전부 통과했다.** 그런데 **어느 파일이 권위값인지는 안 봤다.**

> **동작 검증과 의미 검증은 다르다.** 파이프가 뚫려 있는지는 확인했지만,
> 그 파이프에 **맞는 물이 흐르는지**는 확인하지 않았다.

→ [상세와 수정](guides/overlay-setup.md#-실사용-검증에서-잡힌-결함--파트가-안-바뀌었다)

### 5. 병목이 하나로 좁혀졌다 — 그리고 그것만으로 목표를 넘는다

```
기존   껍데기 3.2초  +  LLM 5.9초
지금   껍데기 0.01초 +  LLM 4.5초      ← 화면 목표 2.5초를 LLM 혼자 초과
```

**여기서 더 깎을 껍데기가 없다.** 다음 수단은 LLM 왕복 자체를 건드리는 것뿐이고,
현실적인 후보는 **스트리밍**이다. 다만 M8이 세운 *"검증 전에는 한 글자도
내보내지 않는다"* 는 원칙과 정면으로 충돌한다. → [리포트의 「다음에 손댈 곳」](guides/daemon-latency-report.md#다음에-손댈-곳)

## 설계 판단

### 파일 계약은 그대로 두고 프로세스 경계만 바꿨다

M7 리포트의 문장을 그대로 따랐다.

> 이것은 파일 기반 설계를 버리라는 뜻이 아니다. 각 단계가 JSON을 읽고 쓰는 계약은
> 사고 추적에 필수적이고 그대로 둔다. 바꿀 것은 *프로세스 경계*이지 *파일 경계*가 아니다.

```
이전  [py] ① → [py] ② → [py] ③ → [py] ④ → [py] ⑤ → [py] ⑥     프로세스 6개
이후  [py ─── ① → ② → ③ → ④ → ⑤ → ⑥ ─── 계속 살아 있음]      프로세스 1개
```

### 스테이지를 리팩터링하지 않고 `main()`을 그대로 불렀다

각 스테이지를 함수로 쪼개는 방법도 있었다. 그러나 그건 **6개 파일을 전부 개편**하는
일이고, M7·M8에서 검증한 동작이 바뀔 위험이 있다.

대신 `sys.argv`를 갈아끼우고 `main()`을 부른다. 지저분하지만 **검증된 코드 경로를
한 줄도 건드리지 않는다.** M9의 목적은 지연 절감이지 리팩터링이 아니다.

> 나중에 스테이지를 함수로 정리할 때가 오면, 그때는 **이 벤치가 회귀 테스트**가 된다.

### 측정은 같은 날 같은 조건에서만 비교했다

과거 M7 수치와 섞지 않았다. LLM 응답 시간은 날마다 흔들리므로, **구조 변경의 효과와
네트워크 변동을 섞으면 아무것도 증명하지 못한다.** 기준선을 오늘 다시 쟀다.

그 결과 M7 예상(6.7초 절감)과 실측(3.2초)이 갈렸는데, **원인은 기준선 차이**였다 —
M7은 `cold`, 이번은 `warm` 기준이다. 예상이 틀린 게 아니라 재는 자리가 달랐다.

## 실행

```bash
cd examples/engine

python engine_daemon.py --live 21 --repeats 5                    # 벤치
python engine_daemon.py --live 21 --repeats 5 --max-evidence 3   # 근거 축소
python engine_daemon.py --live 21 --serve                        # stdin 대기

python panic_stop.py --repeats 10                                # 패닉 스톱 실측
python hotkeys.py --live 21                                      # 핫키 대기
python hotkeys.py --live 21 --selftest                           # 핫키 자동 검증
python vault_guard.py --selftest                                 # 볼트 가드 검증
python overlay_server.py                                         # 오버레이 서버
```

### 핫키 배치

| 조합 | 동작 |
|---|---|
| `Ctrl+Alt+←` / `→` | 이전 / 다음 파트 |
| `Ctrl+Alt+1`~`9` | 해당 파트로 직접 |
| `Ctrl+Alt+L` / `R` / `M` | LIVE / REVIEW / MUTE |
| **`Ctrl+Alt+Space`** | **패닉 스톱** |

`--serve`는 **한 줄 = 발화 하나**로 받고 JSON 한 줄을 돌려준다.
M9 실습 2(글로벌 핫키)와 Electron 셸이 붙을 자리다.

## 다음

**Electron 셸** — 로드맵의 원래 실습 1이다. 급하지 않다. 핵심 기능(엔진·핫키·패닉·

M8 의 *"검증 전에는 한 글자도 내보내지 않는다"* 와 충돌한다. **M10 으로 넘어가기 전에
정리해야 할 설계 질문.**
