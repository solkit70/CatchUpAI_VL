## 무엇을 재려고 했나

기본 프로바이더를 취향이 아니라 데이터로 정하기 위한 측정이다.
문장 3종 × 프로바이더 3종 × 5회 = 45회 합성.

| 문장 | 내용 | 왜 이 문장인가 |
|---|---|---|
| `plain` | "오늘 3번 파트는 FDE 영상 제작 과정을 다룹니다." (29자) | 기준선 |
| `mixed` | 숫자·영어 약어 혼합 (35자) | 이 파이프라인의 실제 발화가 이렇게 생겼다 |
| `long` | 4문장 연결 (91자) | RTF 가 길이에 따라 무너지는지 |

문장은 M5 `llm_compare` 가 실제로 만든 답변 초안에서 가져왔다. 만들어낸 예문이 아니라
⑥ 단계가 ⑧ 단계에 넘기는 문장 그 자체다.

**ElevenLabs 는 측정하지 못했다.** 키가 없다. 어댑터는 작성했고 프리플라이트가
자동으로 제외한다. 키가 생기면 `python tts_probe.py` 한 번으로 편입된다.

## 측정 조건

- 오디오를 **재생하지 않았다**. 진행자가 라이브 방송 중이라 스피커 출력이 방송에 섞이고
  M4 에코 게이트 측정 조건까지 오염된다. 파일로만 쓰고 ffprobe 로 길이를 쟀다
- 따라서 **주관 청취 품질은 이 문서에 없다**. 방송 종료 후 `audio/compare/` 를 들어서 채운다
- 첫 청크 = 재생을 시작할 수 있는 시점 / 완료 = 합성이 끝난 시점

## 결과

### 지연

| 프로바이더 | 문장 | 첫청크(중앙) | 첫청크(최악) | 완료(중앙) | RTF | 조기 시작 이득 |
|---|---|---|---|---|---|---|
| **edge** | plain | **588ms** | 628ms | 1,054ms | 0.213 | 466ms |
| **edge** | mixed | **588ms** | 627ms | 2,537ms | 0.253 | 1,949ms |
| **edge** | long | **606ms** | 620ms | 1,049ms | 0.051 | 443ms |
| openai | plain | 1,548ms | 2,575ms | 1,838ms | 0.391 | 290ms |
| openai | mixed | 1,624ms | 2,236ms | 2,233ms | 0.216 | 609ms |
| openai | long | 1,456ms | 1,534ms | 3,365ms | 0.175 | 1,909ms |
| qwen | plain | 2,827ms | 3,359ms | 2,828ms | 0.638 | **없음** |

| qwen | long | 6,170ms | 6,626ms | 6,172ms | 0.309 | **없음** |

RTF(실시간 계수) = 합성 시간 / 오디오 길이. 전부 1.0 미만이라 세 곳 모두 실시간 발화가 가능하다.
**RTF 로는 셋을 구분할 수 없다.** 구분은 첫 청크에서 난다.

### 비용

1시간 방송에서 AI 발화 100회 × 평균 80자 = 8,000자 가정.

| 프로바이더 | $/1k자 | 8,000자 | 근거 |
|---|---|---|---|
| edge | $0.0000 | $0.000 | 확인됨 (무료) |
| openai | $0.0006 | $0.005 | ⚠ **하한값** |
| qwen | — | — | 미확인 |

**openai 값이 하한인 이유**: `gpt-4o-mini-tts` 는 텍스트 입력 $0.60/1M자 **+ 오디오 출력
$12.00/1M 토큰** 이중 요금이고, 음성 엔드포인트 응답은 오디오 토큰 수를 돌려주지 않는다.
문자 수만으로는 총비용이 확정되지 않는다. 단일 문자 단가가 필요하면
`tts-1`($0.015/1k자) 또는 `tts-1-hd`($0.03/1k자)를 쓰면 된다.
([출처](https://developers.openai.com/api/docs/pricing), 2026-08-23 확인)

**qwen 을 비운 이유**: 3자 출처들이 $0.013~$0.028/1k자로 서로 다르게 적고 있어
어느 하나를 고를 근거가 없다. Alibaba Cloud Model Studio 콘솔의 공식 가격을 확인해야 한다.
추측 단가를 넣으면 비용 리포트가 조용히 틀린다 — M5에서 정한 원칙 그대로다.

## 읽은 것

### 1. 무료가 가장 빠르다 — 이 결과가 로드맵 전제를 뒤집는다

edge-tts 의 첫 청크는 15회 전부 **522~628ms** 안에 들어왔다. 문장 길이와 무관하다.
openai 보다 2.6배 빠르고 편차는 더 작다. 게다가 무료다.

로드맵 M6 실습 4는 **"유료를 기본값으로 쓰다가 비용 상한을 넘으면 무료로 강등"** 구조를 가정했다.
실측은 그 전제를 지지하지 않는다. 가장 빠른 것이 이미 무료이기 때문이다.

→ 필요한 것은 강등이 아니라 **반대 방향**이다.

```
로드맵 가정   유료(기본) ──비용 초과──> 무료
실측 결과     무료(기본) ──실패/지연──> 유료(승격)
```

서킷 브레이커 자체는 만들었고 강등도 실제로 확인했다(아래 3번). 다만 **어느 방향으로
쓸 것인지가 실측으로 바뀌었다.** 승격 로직은 M7 통합에서 붙인다.

### 2. edge 의 유일한 약점은 SLA 가 없다는 것

무료 서비스이므로 보장이 없다. 실제로 걸렸다.

앞선 2회 반복 측정에서 `plain` 한 회차의 첫 청크가 **8,073ms** 로 튀었다
(같은 조건 다른 회차는 744ms). 이후 5회 반복 측정 15회에서는 재현되지 않았다.

**총 21회 중 1회(약 5%), 최악 8.07초.** 방송에서 8초 침묵은 사고다.
100회 발화라면 산술적으로 5회쯤 나온다는 뜻이고, 그건 무시할 수 없다.

이 한 건이 "edge 를 기본값으로 쓰되 감시가 필요하다"의 근거다. 재현되지 않았다고
없던 일로 처리하면 안 된다 — 드물게 크게 튀는 것이 방송에서는 가장 나쁜 성질이다.

### 3. openai 는 같은 문장을 매번 다르게 읽는다

오디오 길이가 회차마다 달랐다.

```
openai plain 길이   4.608 / 4.800 / 4.704 / 4.704 / 5.400 초   ← 최대 0.79초 차이
edge   plain 길이   4.944 / 4.944 / 4.944 / 4.944 / 4.944 초   ← 완전 동일
```

edge 는 결정적이고 openai 는 생성적이다. 방송 타이밍 설계에서 이 차이가 걸린다.

- **미리 합성해 두는 발화**(대기 필러 등)에는 영향이 없다. 한 번 만들어 재사용하므로
- **실시간 답변**에는 영향이 있다. 합성하기 전에는 몇 초짜리가 나올지 알 수 없어,
  "이 발화가 끝나는 시점"을 예측해 다음 동작을 예약할 수 없다

qwen 도 비결정적이다(plain 길이 4.0~5.84초, 편차가 openai 보다 크다).

### 4. Qwen 은 이 경로에서 조기 시작이 불가능하다

첫 청크와 완료가 **1~2ms 차이**로 붙어 있다. 세 문장 전부 그렇다.
그리고 첫 청크가 텍스트 길이에 비례해 늘어난다(2.8초 → 3.9초 → 6.2초).

이 어댑터가 쓰는 HTTP 경로(`MultiModalConversation`, `stream=False`)가 오디오 바이트가
아니라 **다운로드 URL** 을 돌려주기 때문이다. 합성이 다 끝나야 URL 이 나온다.

⚠️ **이것은 Qwen 의 한계가 아니라 이 경로의 한계다.** DashScope 는 WebSocket 스트리밍
경로를 따로 제공하고 Flash 티어는 첫 패킷 300ms 수준으로 알려져 있다. 여기서 HTTP 경로를
쓴 것은 RemotionStudio 에서 운영 검증된 형태를 그대로 옮겼기 때문이다.
스트리밍 경로 검증은 별도 과제다 — 검증되면 순위가 바뀔 수 있다.

### 5. 완료 시간은 첫 청크보다 훨씬 불안정하다

edge `mixed` 완료 시간: 1,122 / 1,231 / 2,537 / 2,924 / 3,598ms — 3배 이상 벌어진다.
반면 같은 회차들의 첫 청크는 522~627ms 로 촘촘하다.

스트리밍 프로바이더에서는 **첫 청크만 안정적이면 된다**. 첫 청크 이후는 재생하면서
받으면 되고, RTF 가 0.25 수준이라 재생 속도가 수신 속도를 따라잡지 못한다.
완료 시간의 편차를 보고 프로바이더를 고르면 잘못된 결론에 도달한다.

→ 이것이 첫 청크와 완료를 처음부터 나눠 잰 이유다. 하나로 뭉쳤으면 edge 를 탈락시켰을 것이다.

## 결정

**기본 프로바이더: edge-tts** (`ko-KR-SunHiNeural`)

| 근거 | |
|---|---|
| 첫 청크 588ms | 2위(openai 1,548ms)의 38% |
| 최악값 628ms | 15회 측정 내 |
| 결정적 출력 | 같은 문장 = 같은 길이 |
| 비용 $0 | 확인된 유일한 단가 |
| 여성 음성 | 진행자(남성)와 구분 — `voice_policy` 충족 |

**2순위(승격 대상): openai** (`gpt-4o-mini-tts` / `nova`)
정식 API 라 SLA 가 있고 첫 청크 1.5초로 방송에 쓸 만하다. edge 가 튀거나 실패할 때 올라간다.

**3순위: qwen** — HTTP 경로로는 조기 시작이 안 된다. WebSocket 경로 검증 후 재평가.

**클론 보이스는 기본값으로 쓰지 않는다.** RemotionStudio 자산에 진행자 클론 보이스가
있지만 이 파이프라인에는 넣지 않았다. 시청자가 사람 발화와 AI 발화를 구분할 수 없게 되기 때문이다 —
M1 "커버리지 없으면 침묵"과 같은 뿌리의 원칙이다. 목소리 성별을 진행자와 다르게 둔 것도
같은 이유이고, 가장 값싼 구분 신호다.
