## 어디서 나온 과제인가

M5 세션에서 진행자가 제안했다. 응답을 기다리는 동안 AI가 미리 준비한 말을 하게 하자는 것.
방향은 맞지만 **문구가 안전 설계와 충돌할 수 있다**는 점이 그때 함께 지적됐고,
트리거·중복 방지·문구 변형은 M6로 넘겼다. 이 문서가 그 몫이다.

## 요구가 오늘 바뀌었다

같은 세션에서 잰 [LLM 지연 스윕](../../05-STT-LLM-Harness/guides/llm-latency-sweep.md) 결과가
필러의 설계 요구를 바꿔 놓았다.

| | M5 시점 | 지연 튜닝 후 |
|---|---|---|
| 첫 발화까지 | ~17초 | ~4.5초 |
| 필러에 필요한 것 | 여러 마디 + 자연스러운 이어붙이기 | **짧은 한 마디 하나** |
| 실패 시 인상 | 어색한 독백 | 짧은 뜸 |

17초를 메우려면 필러가 사실상 **하나의 발화**가 되어야 했다. 그건 위험하다 —
내용이 있어야 하고, 내용이 있으면 근거가 필요하고, 근거가 없으면 M1의
"커버리지 없으면 침묵" 원칙을 필러가 어긴다.

4.5초는 다르다. **내용 없는 한 마디로 덮인다.** 필러가 정보를 전달할 필요가 없어졌고,
그래서 안전 원칙과 충돌하지 않는 설계가 가능해졌다.

→ 지연을 줄인 것이 필러를 쉽게 만들었다. **필러는 지연 대책이 아니라 지연 대책의 보완재다.**
   순서를 뒤집어 필러부터 만들었다면 훨씬 위험한 물건이 나왔을 것이다.

## 절대 제약 — 답변을 약속하지 않는다

파이프라인은 `⑥ LLM → ⑦ 안전 검증 게이트 → ⑧ 발화` 순서이고,
**⑦이 차단하는 것이 정상 동작**이다. 근거를 못 찾으면 말하지 않는 것이 이 시스템의 설계다.

그런데 필러는 ⑥이 끝나기 **전에** 나간다. 즉 필러를 말하는 시점에는
그 뒤에 답변이 나올지 침묵이 올지 아직 모른다.

```
"답변 드릴게요"  →  ⑦ 차단  →  침묵
                        지키지 못한 약속. 시청자에게는 고장으로 읽힌다
```

침묵 자체보다 **약속 뒤의 침묵**이 훨씬 나쁘다. 그냥 조용하면 "안 들었나 보다"지만,
답한다고 해놓고 조용하면 "망가졌다"가 된다.

**규칙: 확인은 약속하되 답변은 약속하지 않는다.**

| | 예시 | 왜 |
|---|---|---|
| ○ | "네, 확인해 볼게요" | 확인은 실제로 한다. 결과가 무엇이든 거짓이 아니다 |
| ○ | "잠깐 찾아볼게요" | 위와 같음 |
| ○ | "그 부분 한번 볼게요" | 위와 같음 |
| ✗ | "답변 드릴게요" | ⑦이 차단하면 거짓이 된다 |
| ✗ | "알려드릴게요" | 위와 같음 |
| ✗ | "좋은 질문이네요" | 내용 판단이다. 근거 없이 질문을 평가하고 있다 |

마지막 항목은 덜 분명하지만 같은 범주다. 질문을 아직 처리하지도 않은 상태에서
"좋은 질문"이라고 말하는 것은 근거 없는 발화다.

## 후속 문구도 함께 준비돼야 한다

필러는 짝이 있어야 완성된다. 차단됐을 때 아무 말도 하지 않으면
필러가 남긴 기대가 그대로 방치된다.

```
필러      "네, 확인해 볼게요"
  ↓
⑦ 통과   → 답변 발화
⑦ 차단   → "그건 근거를 못 찾았습니다"      ← 이 문구가 없으면 필러를 쓰면 안 된다
```

차단 문구는 **사과하지 않는다.** "죄송하지만"을 붙이면 차단이 실패처럼 들리는데,
차단은 이 시스템의 정상 동작이다. 담백하게 사실만 말한다.

## 트리거 조건

필러는 항상 나가면 안 된다. 빠른 응답에 필러가 겹치면 말이 두 번 나온다.

```
⑤ STT 완료
   ↓
   타이머 시작 ──── T_filler 경과 전에 ⑧ 준비됨 → 필러 생략
   ↓
   T_filler 경과 → 필러 발화 (⑥ 아직 진행 중)
```

### T_filler = ~~0.9초~~ → **1.14초** (2026-09-06 M10 정정)

> 🔴 **2026-09-06 정정.** 아래 0.9초는 **케이블 314ms**를 전제로 계산된 값인데,
> M9가 그 314ms가 오측정임을 밝혀냈다 — 장치를 `ci[0]`(첫 매칭)으로 고르는 바람에
> MME가 걸린 값이었고, **WASAPI 저지연 스트림 실측은 63ms**다.
> 같은 의도("1.2초에 소리가 나야 한다")를 63ms 위에서 다시 계산하면 **1.14초**다.
>
> ```
> 정정 전  1.2s - (로드 8ms + 케이블 314ms) = 0.88s → 0.9초
> 정정 후  1.2s - (로드 8ms + 케이블  63ms) = 1.129s → 1.14초
> ```
>
> 0.9초를 그대로 두면 **의도보다 0.25초 일찍 소리가 난다** — 진행자가 말을 마치기 전에 필러가 겹칠 수 있다.
> → 근거: [패닉 스톱 리포트](../../09-Desktop-Shell-and-Overlay/guides/panic-stop-benchmark.md) ·
> 결정: [스트리밍 vs 안전 게이트](../../10-Live-Rehearsal-Capstone/guides/streaming-vs-safety-gate.md)

처음에 1.2초로 잡았던 값을 **0.9초로 당긴다.** 이유는 하나다 —
**필러도 케이블 지연 314ms를 먹는다.** 트리거 시각과 들리는 시각이 다르다.

```
트리거 t=0.9s ──[ 로드 8ms + 케이블 314ms ]──> 실제로 들림 t≈1.2s
```

원래 의도했던 "1.2초에 소리가 나야 한다"를 지키려면 0.9초에 걸어야 한다.
케이블 지연은 [audio-routing-setup.md](audio-routing-setup.md) 에서 5회 측정에
312~321ms로 매우 일관되게 나왔고, 스트림을 미리 열어도 줄지 않는(308ms) 고정 비용이다.

### 전체 예산 — 필러가 덮어야 하는 침묵의 실제 길이

발화 종료(t=0)부터 AI 음성이 들리기까지를 구간별 실측으로 쌓으면 이렇다.

| 구간 | 출처 | 소요 | 누적 |
|---|---|---|---|
| ⑤ STT | M5 gpt-4o-transcribe | 1,160ms | 1,160ms |
| ⑥ LLM | M6 openai minimal | 2,600ms | 3,760ms |
| ⑦ 안전 게이트 | M7 문자열 대조 | ~0ms | 3,760ms |
| ⑧ TTS 합성 (파일 전체) | M6 edge | 1,584ms | 5,344ms |
| 로드·리샘플 | M6 실측 | 8ms | 5,352ms |
| ⑨ 케이블 → 발성 | **M6 라우팅 실측** | **314ms** | **5,666ms** |

**스트리밍으로 첫 청크(588ms)부터 내보내면** ⑧이 588ms로 줄어 누적 **4,662ms**.

### 여기서 나오는 결론 2가지

**① M7 목표(발화종료 → 음성 4초)를 아직 못 맞춘다.**
파일 기반 5.7초, 스트리밍 4.7초로 **둘 다 초과**다. 목표를 고치든 구조를 고치든
선택이 필요하다 — M7 실습 6에서 다룬다.

**② 필러가 성립하려면 TTS 스트리밍이 필요하다.**
필러("네, 확인해 볼게요", 약 1.5초)는 t≈1.2초에 시작해 t≈2.7초에 끝난다.

- 스트리밍(4.66초) → 필러 종료 후 침묵 **약 2.0초**
- 파일 기반(5.67초) → 필러 종료 후 침묵 **약 3.0초**

둘 다 짧지 않다. **필러 하나로는 못 덮는다.** 선택지는 셋이고 M7에서 정한다.

- 필러를 더 길게 (다만 길수록 내용 없는 말이 길어진다)
- LLM 지연을 더 줄인다 (2.6초가 현재 최선)
- 목표 4초를 현실에 맞게 올린다

**어느 쪽이든 "필러를 넣으면 해결된다"는 애초의 기대는 성립하지 않는다.**
필러는 첫 1.5초를 덮을 뿐이고, 나머지 2~3초는 그대로 남는다.

> 🔴 **2026-09-06 정정 — 위 결론 ②는 뒤집혔다.**
>
> *"필러가 성립하려면 TTS 스트리밍이 필요하다"* 고 적었는데, M10에서 다시 계산해 보니 **반대**였다.
> 스트리밍은 첫 소리를 ≈2.6초에 내고, 필러는 ≈1.20초에 낸다 — **필러가 1.4초 더 빠르다.**
> LLM이 첫 문장을 뱉는 시간 자체를 스트리밍이 줄여 주지 않기 때문이다.
>
> | 방식 | 첫 소리 |
> |---|---:|
> | 필러 (T_filler 1.14초) | **≈1.20초** |
> | 문장 단위 스트리밍 | ≈2.6~3.1초 |
> | 파일 기반 (현재) | ≈5.03초 |
>
> **스트리밍이 당기는 것은 "끝나는 시각"이고, 체감 지연은 "시작하는 시각"의 문제다.**
> 따라서 스트리밍은 채택하지 않고 필러로 간다. 필러 종료 후 남는 침묵 ≈2.3초가
> 리허설에서 사고로 인식되면 그때 문장 단위 증분 게이트를 재검토한다.
>
> 갱신된 예산표(M9 데몬 실측 4,369ms + 케이블 63ms 반영):
>
> | 구간 | 이 문서 최초 | M9 실측 반영 |
> |---|---:|---:|
> | ⑤~⑦ STT·LLM·게이트 | 3,760ms | **4,369ms** |
> | ⑧ TTS 첫 청크 | 588ms | 588ms |
> | 로드·리샘플 | 8ms | 8ms |
> | ⑨ 케이블 | 314ms | **63ms** |
> | **누적** | 4,670ms | **5,028ms** |
>
> → 전문: [스트리밍 vs 안전 게이트](../../10-Live-Rehearsal-Capstone/guides/streaming-vs-safety-gate.md)

## 중복 방지

필러가 반복되면 필러 자체가 소음이 된다.

1. **세션당 연속 반복 금지** — 같은 문구를 연달아 쓰지 않는다. 목록을 돌려 쓰되
   직전에 쓴 것은 제외한다
2. **한 질문에 하나** — 필러가 나간 뒤에는 그 질문이 끝날 때까지 다시 나가지 않는다.
   답변이 더 늦어져도 두 번째 필러를 얹지 않는다. 두 번 말하면 "기다리게 해서 미안"이라는
   신호가 되고, 그건 문제를 강조하는 꼴이다
3. **진행자 발화 중 금지** — 진행자가 말하는 중이면 필러를 내보내지 않는다.
   M4 에코 게이트와 같은 원칙 — AI 음성이 사람 음성 위에 겹치면 안 된다

## 어느 프로바이더로 합성하나

필러는 **미리 합성해 둔다.** 실시간 합성하면 필러 자체가 지연을 만든다 —
덮으려던 침묵에 TTS 지연이 더해지는 자기모순이 된다.

| | 필러 | 답변 |
|---|---|---|
| 문구 | 고정 (소수의 목록) | 매번 다름 |
| 합성 시점 | **방송 시작 전 미리** | 실시간 |
| 비용 | 사실상 0 (재사용) | 발화당 발생 |
| 프로바이더 | 답변과 **같아야 한다** | 실습 2 결과로 결정 |

프로바이더를 같게 두는 이유는 목소리 일관성이다. 필러와 답변의 목소리가 다르면
한 사람이 말하다 다른 사람이 이어받는 것처럼 들린다.

→ **서킷 브레이커가 강등되면 필러도 함께 강등돼야 한다.** 미리 합성한 필러를
프로바이더별로 각각 준비해 두고, 활성 프로바이더에 맞춰 고른다.
이 요구가 실습 4의 강등 로직에 추가로 걸린다 — M7 통합 시 확인할 것.

## 필러 목록 (초안)

`filler_catalog.json` 로 관리한다. 문구를 코드에 박지 않는 이유는
레지스트리 원칙과 같다 — 방송 중에 문구만 바꿔야 할 일이 생긴다.

| 상황 | 문구 | 비고 |
|---|---|---|
| 대기 | "네, 확인해 볼게요." | 기본 |
| 대기 | "잠깐 찾아볼게요." | |
| 대기 | "그 부분 한번 볼게요." | |
| 차단 | "그건 근거를 못 찾았습니다." | 사과 없음 |
| 차단 | "그건 오늘 다루는 내용에 없네요." | 커버리지 미정일 때 |
| 실패 | "지금은 답을 준비하지 못했습니다." | 전 프로바이더 실패 → HITL |

세 번째 범주(실패)는 ⑦ 차단과 다르다. 차단은 "근거가 없다"이고
실패는 "시스템이 답을 못 만들었다"이다. 시청자에게 같은 말로 뭉뚱그리면
근거 없는 질문과 시스템 장애가 구분되지 않는다.
