## 📚 진행 내용

### 0. 선행 작업 2건 — 재작업 방지

**순서**: 가장 먼저. 나중에 하면 앞 실습 결과를 다시 재야 한다.

**① 폴백 순서 변경.** M3 설계의 `claude → openai → gemini` 를
`openai → gemini → claude` 로 바꾸고 `default_effort` 를 레지스트리에 등재했다
(openai=minimal, gemini=low, claude=null). `llm_probe.py` 가 런타임 레지스트리로
전달하고 `llm_compare.py` 가 그것을 읽도록 연결했다.

효과가 바로 나왔다.

| | 변경 전 | 변경 후 |
|---|---|---|
| openai | 11,909ms | **3,469ms** |
| gemini | 10,121ms | **3,895ms** |
| claude | 7,525ms | 7,252ms |

3사 모두 스키마·근거 대조를 통과했다. 실습 3에서 이 설정을 그대로 쓴다.

**② `spoken.provider` 추가.** M3 `output.schema.json` 의 `spoken` 에
`text`/`voice`/`audio_path`/`spoken_at` 만 있고 프로바이더 필드가 없었다.
M3 설계 당시엔 TTS 가 하나였으니 당연하다. 지금은 M6 서킷 브레이커가 런타임에
교체하므로, voice id 로 역추정하면 **사후 분석 때 "어느 발화가 강등 이후였는지"를
가릴 수 없다.** 필수 필드로 추가하고 M3 검증 샘플도 함께 갱신했다.

### 1. 실습 1 — 골격

**순서**: 2번째.

`data/`(Rundown 샘플 2편 + safety_policy 사본) · `src/`(common + 6개) ·
`output/` · `tests/` · `guides/` 를 만들었다.

골격 4개(03~06)는 비었지만 **계약을 docstring 에 확정해 두었다.** 다음 세션이
"무엇을 읽어 무엇을 쓰는가"를 다시 조사하지 않게 하는 것이 골격의 목적이라고 봤다.

`common.py` 에는 M6에서 데인 것을 반영했다 — `safety_policy.json` 사본이 M3 원본과
다르면 해시로 감지해 경고한다. M6 문제 3(런타임 레지스트리가 원본보다 낡아 비용 표가
조용히 틀림)과 같은 구조의 함정이기 때문이다. 스키마는 아예 사본을 두지 않고
M3 원본을 직접 읽는다.

### 2. 실습 2 — ①② 단계 구현

**순서**: 3번째. 이 세션의 본체.

```
Live20   파트 5개(번호 4 + 무번호 1) · 커버리지 17항목 · status_map 11개 · 근거 23건
Live21   파트 3개 · 금칙 2 · 조건부 1 · 커버리지 5항목 · status_map 11개 · 근거 15건
```

로드맵 검증 기준("두 회차 모두 status_map 최소 5개")을 양쪽 다 충족했다.

Live21 결과가 M1 `forbidden-sections.md` 가 손으로 확인한 3종과 **정확히 일치**한다 —
보류 인사이트·주간 영상 후보는 `excluded_sections`, 대기 목록은 `conditional_sections`.
M1에서 문서로 정리한 것이 코드에서 그대로 재현됐다.

`02` 에서 신경 쓴 것은 `forbidden_removed` 다. 스키마상 `const: true` 인 불변식
플래그인데, **참이라고 적는 것과 참인 것은 다르다.** 조립이 끝난 뒤 근거 풀을
금칙 헤딩과 대조해 실제로 확인하고, 새면 중단한다.

### 3. 실습 3 — 의도 분류와 답변 생성

**순서**: 4번째.

의도 분류를 **규칙 기반**으로 만들었다. LLM 을 한 번 더 부르면 지연이 두 배가 되는데,
오늘 아침에 effort 를 낮춰 확보한 이득을 그대로 반납하는 셈이기 때문이다.
intent 는 6개짜리 닫힌 집합이고 한국어 명령 어형은 정형적이라 규칙으로 충분했다.

M5 20문장 세트로 재사용 검증했다.

```
분류 20건 · answer_question 12 · stop 2 · repeat 1 · summarize 1 · advance 1
          · out_of_scope 1 · unknown 2
```

`04_compose_answer` 는 **생성 전 차단 4종**을 먼저 통과해야 LLM 을 부른다 —
out_of_scope / unknown / 제어 명령 / 모호성 플래그. safety_policy 의 모호성 3규칙이
`block_generation: true` 이므로, 만들어 놓고 뒤에서 거르는 것이 아니라 만들기 전에 멈춘다.
만들어 둔 답은 언젠가 새어 나간다.

12번 문장("질문 세 개만 요약해줘")에서 `quantity_mismatch` 가 정확히 걸렸다 —
요청 3개 vs Live21 3부 화이트리스트 2개. M3에서 설계한 규칙이 실물에서 처음 작동했다.

### 4. 실습 4 — 안전 게이트와 렌더

**순서**: 5번째.

`05_verify_and_gate` 는 LLM 을 쓰지 않는다. M2 App Boundary 의 "절대 하지 말아야 할 일"에
*안전 검증 게이트 — 검증을 LLM 자기평가에 위임하는 것*이 명시돼 있다. 전부 문자열 대조다.

통과만 확인하면 게이트를 꺼도 같은 결과가 나오므로 `--tamper` 모드를 만들었다.
근거를 위조하고 근거를 지워서 게이트가 실제로 잡는지 본다.

```
정상    4/4 문장 유지 · pass=True
위조    2/4 문장 유지 · evidence_not_found 1건 · no_evidence 1건
```

M4에서 에코 게이트를 off/on 으로 나눠 잰 것과 같은 이유다.

`06_render_output` 은 overlay/spoken 을 **파일까지 분리**했다. OBS Browser Source 와
TTS 는 서로 다른 프로세스가 폴링하므로 한 파일을 둘이 읽게 하면 한쪽 오류가 다른 쪽을 멈춘다.

### 5. 실습 5 — 권위값/추정값 분리

**순서**: 6번째.

`current_part_id`(권위) 와 `suggested_part_id`(시각 추정) 를 나눴다.
검증은 테스트로 했다 — [test_part_authority.py](../07-CoMC-Engine-POC/tests/test_part_authority.py)
8개 항목 전부 통과.

가장 마음에 드는 검사는 **소스 코드 검사**다. `refresh_suggestion()` 함수 본문에
`current_part_id` 대입이 없는지 문자열로 확인한다. 문서로 "하지 마라"고 쓰는 것보다
실수로 넣기 어렵게 만드는 편이 낫다.

`clock` 을 권위 소스로 넣으면 `SystemExit` 이 난다. 시계는 권위가 없다.

### 6. 실습 6 — 지연 측정

**순서**: 7번째. 이 세션에서 가장 많이 배운 곳.

리포트: [latency-report.md](../07-CoMC-Engine-POC/guides/latency-report.md)

```
목표  화면 2,500ms
실측  화면 12,230ms (중앙) / 12,644ms (최악)   ← 목표의 4.9배
```

목표를 크게 못 미쳤는데, **원인을 셋으로 분해한 것이 결과 자체보다 중요하다.**

| 원인 | 크기 |
|---|---|
| 프로세스 기동 + import | ~3.7초 |
| 연결 설정 (첫 호출) | ~3.0초 |
| LLM 호출 | 2.1~3.5초 |

앞의 둘이 6.7초다. 매 발화마다 6개 프로세스를 새로 띄우기 때문에 생긴다.

## 🐛 문제 해결 로그

### 문제 1: `is_final` 규칙이 실물과 맞지 않았다 ← 가장 중요

M3 스키마는 `is_final` 을 "status 가 '최종본'으로 판정되면 true" 로 설명한다.
그대로 구현하려다 볼트를 전수 조사했더니 **Rundown 14편 중 '최종본' 표기가 0건**이었다.

```
status 필드 없음                     10편 (Live11~Live20)
"📺 방송 완료 — ..."                 Live21
"✅ 방송 완료 (...)"                  Live22
"✅ 전 파트 커버리지 확정 (...)"        Live23, Live24
```

설명대로 구현했으면 **"방송 투입 가능" 신호가 영원히 꺼진 채**로 있었을 것이고,
그건 코드가 도는데도 아무 일도 안 하는 종류의 실패다. 실물 어형
(`최종본`/`확정`/`방송 완료`)으로 판정하도록 고치고 이유를 코드 주석에 남겼다.

문서에 적힌 규칙과 데이터가 어긋날 때, **데이터가 맞다.**

### 문제 2: 커버리지를 가진 무번호 파트가 있다

Live20 의 `## 주간 영상 (시간 미정)` 은 커버리지 줄을 가진 방송 구간인데
M1 정규식 `^## (\d+(?:\.\d+)?)부:` 에 걸리지 않는다. 케이스 표에도 없다.

그냥 넘겼으면 **그 구간의 발화 허용 항목 2건이 통째로 사라진다** — 말해도 되는 것을
말하지 못하게 되는 실패다. 금칙 섹션 누락(말하면 안 되는 걸 말함)의 반대 방향인데,
방송 품질로는 둘 다 사고다.

`part.is_numbered` 를 스키마에 추가하고, 커버리지 줄이 따라오는 H2 만 파트로
승격시키는 방식으로 처리했다. `## 방송 순서 (초안)` 같은 헤딩까지 파트가 되면 안 되므로
헤딩만으로는 판정하지 않고 **커버리지 줄이 실제로 오는지 보고 나서** 승격시킨다.

### 문제 3: 대시(—)는 지시문 신호가 아니었다

M1 케이스 7("지시문은 커버리지 줄 맨 끝에 자유 문장으로 붙는다")을 대시 기준으로
구현했더니 Live20 2부에서 오탐이 났다.

```
Live20 2부 ④ "로드맵 우선 설계 — 시작은 신중하게, 재개는 간편하게"   ← 항목 제목의 부제
Live21 3부 ② "...업데이트 — 이 두 개를 메인으로 진행하고, ... 이어간다"  ← 진짜 지시문
```

같은 줄에 `③Codex Win — 화면 읽기에서...` 도 있다. **항목 제목에 대시가 흔하다.**
대시를 신호로 쓰면 부제를 발화 목록에서 잘라 내 문제 2와 같은 실패가 된다.

두 실물을 가르는 것은 대시가 아니라 **운영 동사**였다 — 지시문은 항목을 *어떻게 다룰지*
말하고, 부제는 항목이 *무엇인지* 말한다. `진행하/이어간다/메인으로/시간이 남으면` 같은
어형으로 판정하도록 고쳤다. 실물 2건에서 도출한 규칙이라 아직 좁다.

### 문제 4: 볼트 루트 경로가 한 단계 어긋났다

`TOPIC.parents[2]` 로 두었더니 `Ingest` 를 볼트 루트로 잡아, 링크된 문서가
**전부 `missing_file`** 로 떨어졌다. 파일은 다 있었다.

증상이 "문서가 없다"로 보이는 게 고약했다 — 실제로는 "경로가 틀렸다"였고,
둘은 대응이 완전히 다르다. `status_map` 이 전부 같은 값으로 나오는 게 이상해서
잡았다. 한 종류 값만 나오면 의심할 것.

### 문제 5: stderr 인코딩을 빼먹어 오류를 읽을 수 없었다

`sys.stdout.reconfigure` 만 하고 stderr 를 빼먹어서, 오류 메시지가
`파트 '9' 없음` 로 나왔다. **정작 사고가 났을 때 원인을 못 읽는
상태**였다. 정상 경로만 확인하고 넘어갔으면 못 봤을 문제다.

### 문제 6: 사전 캐시 효과가 **음수**로 나왔다

로드맵은 ①②를 방송 전에 미리 빌드해 지연을 줄이라고 했다. 재 봤더니:

```
cold (①~⑥ 전부)   중앙 10,561ms
warm (③~⑥ 만)     중앙 12,230ms   ← 오히려 느림
```

처음엔 측정이 틀린 줄 알았다. 아니었다 — ①②가 아끼는 것은 약 800ms 인데
④의 LLM 편차가 ±2,000ms 라 그 밑에 묻힌 것이다.

**"효과가 없다"가 아니라 "이 측정으로는 보이지 않는다"** 이고, 둘은 다르다.
전자로 적으면 나중에 사전 캐시를 안 하게 된다. 사전 캐시 자체는 여전히 옳다 —
방송 중에 할 이유가 없는 일이다. 다만 지연 대책으로서의 우선순위가 낮을 뿐이다.

### 문제 7: 근거 풀 크기가 지연을 좌우한다 (출력 길이가 아니라)

파이프라인의 ④ 가 5.7~7.7초인데 M5 마이크로벤치마크는 2.6초였다. 조건당 1회씩
재 봤더니 관계가 지저분했다(10건 5.7s / 15건 7.7s / 15건 6.0s). LLM 편차 때문이다.

조건당 3회로 다시 재고, **프로세스 기동 비용을 빼기 위해 한 프로세스 안에서** 반복했다.

```
근거 2건 → 15건  (문장 5 고정)   +1,291ms
문장 3개 → 5개   (근거 2 고정)   +  122ms
```

**출력 길이를 줄여 지연을 잡으려는 흔한 최적화가 여기서는 헛수고다.**
줄여야 할 것은 답변 길이가 아니라 근거 풀이다.

### 문제 8: 첫 호출에만 3초가 붙는다

같은 조건을 한 프로세스 안에서 3회 반복했더니 1회차만 5,097ms 이고
2·3회차는 ~2,000ms 였다. TLS 핸드셰이크·커넥션 풀 초기화 비용이다.

**매 발화마다 새 프로세스를 띄우면 모든 호출이 '첫 호출'이 되어 이 3초를 매번 낸다.**
이것이 M9 가 단일 장기 실행 프로세스여야 하는 이유다. 파일 계약을 버리라는 뜻이 아니라
**프로세스 경계만 바꾸라는** 뜻이다 — 파일 계약은 사고 추적에 필수적이고 그대로 둔다.

### What could be improved (개선할 점)

- **문서에 적힌 규칙을 먼저 의심하지 않았다.** `is_final` 을 그대로 구현하려다
  우연히 전수 조사를 했고 0건임을 알았다. 안 했으면 조용히 틀린 채로 남았다.
  **규칙을 구현하기 전에 그 규칙이 실물에서 몇 번 참인지 세는 것**이 먼저다
- 대시 기준 지시문 판정(문제 3)은 M1 케이스 표를 그대로 믿고 만든 것이다.
  케이스 표에 "Live21 3부"라는 **단일 사례**만 있었는데 그걸로 일반화했다.
  사례가 하나면 규칙이 아니라 관찰이다
- 볼트 루트 경로(문제 4)는 `parents[2]` 를 세어 보지 않고 적었다. 30초면 확인할 것이었다
- 정상 경로만 돌려 보고 넘어갈 뻔했다(문제 5). **오류 경로를 한 번은 밟아 봐야**
  오류 메시지가 읽히는지 알 수 있다

### Insights (인사이트)

**말하면 안 되는 것을 막는 것과, 말해도 되는 것을 지키는 것은 같은 무게다.**
이 파이프라인은 금칙 섹션 차단에 설계가 집중돼 있는데, 오늘 나온 실패 두 건
(무번호 파트 누락, 대시 오탐)은 **반대 방향**이었다 — 허용된 항목을 잘라 내는 것.
방송에서는 둘 다 사고다. 말하면 안 되는 걸 말하면 신뢰를 잃고,
말해도 되는 걸 못 말하면 쓸모를 잃는다.

**문서와 데이터가 어긋나면 데이터가 맞다.** `is_final`(문제 1)이 그랬다.
M3 스키마는 성실하게 작성됐지만 예시로 든 '최종본'이라는 표기가 볼트에 한 번도
존재한 적이 없었다. 설계 문서는 **작성 시점의 가정**을 담고 있고, 그 가정이 검증됐다는
보장은 없다. M6에서 "유료→무료 강등" 전제가 뒤집힌 것과 같은 종류다.

**한 종류 값만 나오면 의심하라.** `status_map` 이 전부 `missing_file` 이었을 때
"링크가 다 깨졌나" 보다 "내 판정이 다 틀렸나"를 먼저 봤어야 했다.
전부 같은 결과는 데이터의 성질이 아니라 코드의 성질일 때가 많다.

**골격의 가치는 파일이 아니라 계약에 있다.** 03~06을 빈 함수로 두면서 docstring 에
입력·출력·스키마·주의사항을 확정해 두었다. 다음 세션이 "이 단계가 뭘 읽더라"를
다시 조사하는 데 쓸 시간을 지금 없앤 것이다. 빈 파일만 만드는 골격은 폴더 구조일 뿐이다.

**지연 목표를 못 맞춘 것보다, 원인을 못 나눈 채 넘어가는 것이 나쁘다.**
12.2초는 목표의 4.9배다. 여기서 "느리네요"로 끝냈으면 M9에서 같은 벽을 다시 만났을 것이다.
셋으로 쪼개고 나니 **고칠 것이 LLM 이 아니라 프로세스 경계**라는 게 드러났다.
기동 3.7초 + 연결 3.0초는 아키텍처를 바꾸면 통째로 사라지지만, 코드를 아무리 다듬어도
줄지 않는다. 측정의 값어치는 숫자가 아니라 분해에 있다.

**흔한 최적화가 이 파이프라인에서는 헛수고인 경우가 계속 나온다.** 오늘만 두 번이다 —
아침에는 LLM 첫 토큰 지연(TTFT)이 무의미했고(⑦ 게이트가 전체 JSON을 봐야 하므로),
오후에는 출력 길이 줄이기가 무의미했다(+122ms). 둘 다 "일반적으로 맞는 방법"인데
이 구조에서는 아니었다. **최적화는 일반론이 아니라 병목 측정에서 나와야 한다.**

**차단을 설계의 실패가 아니라 기능으로 만들면 코드가 단순해진다.**
④ 는 생성 전 차단 4종을 통과해야 LLM 을 부른다. 만들어 놓고 거르는 구조였다면
"만들었지만 안 쓴 답"을 어디에 둘지, 로그에 남길지, 재시도할지를 전부 정해야 했다.
만들기 전에 멈추니 그 질문들이 아예 생기지 않는다.

**부재에 대한 주장은 인용으로 뒷받침될 수 없다.** 커버리지 밖 질문에 모델이
"문서에 명시되어 있지 않습니다"라고 답했고, 내용으로는 완벽했다. 그런데 그 문장에도
`claim_map` 이 붙어 있고 게이트는 통과시킨다 — 인용이 실재하기 때문이다.
**"없다"를 증명하는 인용은 존재할 수 없다.** claim-evidence 모델의 구조적 빈틈이고,
지금은 무해하지만 M8에서 다뤄야 한다.
