## 📚 진행 내용

### 1. 설계 전제가 틀렸다 — VoiceMeeter 는 필요 없다

설계 문서는 **VoiceMeeter Banana + VB-CABLE 두 개 설치**를 전제했다. 근거는 이것이었다.

> "앱이 마이크를 직접 잡으면 OBS 와 배타 모드로 충돌할 수 있다.
>  VoiceMeeter 를 거치는 이유의 절반이 이 충돌 회피다."

`audio_routing_probe.py --shared-test` 로 같은 MV7 에 InputStream 두 개를 동시에 열어 봤다.

```
장치: [24] Microphone (Shure MV7)  (Windows WASAPI, 48000Hz)
스트림 A 열림
스트림 B 열림  ← 동시 열기 성공
피크 레벨  A=0.0317   B=0.0317
```

**WASAPI 공유 모드에서 마이크는 여러 앱이 동시에 열 수 있다.** 배타 충돌은 일어나지 않았다.
설치 하나가 줄었고, 방송 중 살아 있어야 할 구성요소도 하나 줄었다.

**추측으로 넣은 구성요소를 실측이 걷어냈다.** 설계 단계에서 "충돌할 수 있다"고 적은 것을
확인 없이 그대로 두었으면 필요 없는 소프트웨어를 상주시킬 뻔했다.

### 2. 가상 케이블 후보 비교 — MOTIV 는 앱 의존, VB-CABLE 은 드라이버

장치 목록에 `MOTIV Mix Virtual Input/Output` 이 이미 있었다. Shure 드라이버가 제공하는
가상 오디오 쌍이라 VB-CABLE 없이 될 것처럼 보였다. 톤을 넣어 확인했다.

```
재생 → MOTIV Mix Virtual Input
캡처 ← MOTIV Mix Virtual Output
440Hz 3초 → 캡처 피크 0.0000   ✗ 무음
```

**MOTIV 가상 쌍은 드라이버만으로 이어지지 않는다.** MOTIV Mix 앱(200MB Electron)이
실행 중이어야 믹서를 거쳐 연결된다.

VB-CABLE 을 선택했다. 근거 셋.

1. 드라이버 레벨 루프백이라 **앱이 필요 없다** — 방송 중 살아 있어야 할 프로세스가 하나 적다
2. 설정 지점이 적다 (OBS 에서 장치만 지정)
3. 진행자가 리소스 문제로 MOTIV Mix 를 방송 중에 켜지 않는다 —
   라우팅 때문에 다시 상주시키면 원래 피하려던 부담이 돌아온다

M2 App Boundary 의 "앱이 폭주해도 방송은 산다"와 같은 방향이다.

설치 후 톤 통과 시험:

```
재생 → [25] CABLE Input (VB-Audio Virtual Cable)
캡처 ← [30] CABLE Output (VB-Audio Virtual Cable)
440Hz 3초 → 캡처 피크 0.2500 (넣은 진폭과 동일) · 최대 성분 440.2Hz
✓ 성립
```

넣은 주파수가 그대로 나온 것을 스펙트럼으로 확인했다. 파일 재생이었으면
"뭔가 소리가 났다"까지만 알 수 있었을 것이다.

### 3. 재생 지연 실측 — 314ms

설계 문서가 "다음 세션의 유일한 신규 구현"으로 지목한 것.
`tts_compare.py` 가 잰 588ms 는 **파일이 만들어지기까지**이고 소리가 나기까지가 아니다.

VB-CABLE 이 드라이버 루프백이므로 **재생하면서 동시에 캡처**하면 실제 발성 시각을
샘플 단위로 잡을 수 있다. `playback_latency.py` 를 만들어 5회 측정했다.

| 구간 | 중앙값 |
|---|---|
| ① 합성 (요청→파일, edge) | 1,584ms |
| ② 로드·리샘플 (파일→메모리) | 8ms |
| ③ **케이블 (재생 호출→실제 발성)** | **314ms** |
| **전체 (요청→소리)** | **1,910ms** |

312~321ms 로 편차가 3ms 수준이다. 예산에 상수로 넣을 수 있는 값이다.

### 4. 314ms 를 줄일 수 있는가 — 가설을 세우고 틀렸다

M7 에서 "프로세스 기동 3.7초 + 연결 설정 3.0초 → 단일 장기 프로세스여야 한다"는
결론이 나왔으므로, 오디오 스트림도 같을 것이라 보고 **미리 열어 둔 OutputStream** 과
비교했다.

```
sd.play() (매번 새 스트림)   중앙 314ms   범위 304~343ms
미리 연 OutputStream         중앙 308ms   범위 303~317ms
```

**가설이 틀렸다.** 차이가 잡음 수준이다. 314ms 는 스트림 기동 비용이 아니라
**WASAPI 공유 모드 + 가상 케이블 경로의 고유 버퍼**다. OBS 와 장치를 공유해야 하므로
exclusive 모드로 줄일 수도 없다. **줄일 수 없는 고정 비용으로 예산에 넣는다.**

### 5. 필러 설계를 실측으로 갱신

두 가지가 바뀌었다.

**① `T_filler` 1.2초 → 0.9초.** 필러도 케이블 314ms 를 먹는다.
트리거 시각과 들리는 시각이 다르다는 것을 놓치고 있었다.

**② 전체 예산을 쌓아 보니 목표를 못 맞춘다.**

| 구간 | 출처 | 소요 | 누적 |
|---|---|---|---|
| ⑤ STT | M5 | 1,160ms | 1,160ms |
| ⑥ LLM | M6 openai minimal | 2,600ms | 3,760ms |
| ⑦ 게이트 | M7 문자열 대조 | ~0ms | 3,760ms |
| ⑧ TTS 합성 | M6 edge (파일 전체) | 1,584ms | 5,344ms |
| 로드·리샘플 | 오늘 | 8ms | 5,352ms |
| ⑨ 케이블→발성 | **오늘** | **314ms** | **5,666ms** |

스트리밍(첫 청크 588ms)이면 4,662ms. **M7 목표(발화종료→음성 4초)를 둘 다 초과.**

그리고 **"필러를 넣으면 해결된다"는 기대가 성립하지 않는다.**
필러(약 1.5초)를 넣어도 그 뒤에 2.0~3.0초 침묵이 남는다.
필러는 첫 1.5초를 덮을 뿐이다.

### 6. OBS 구성 — 방송 설정을 건드리지 않는 격리

OBS 출력 모드가 `Simple` 이었다. **Simple 모드는 오디오 트랙 분리를 지원하지 않는다.**
고급 모드 전환이 필요한데, 그러면 인코더·비트레이트가 고급 모드의 별도 값으로 바뀌어
**다음 방송 직전에 당황할 수 있는 변경**이 된다.

그래서 기존 프로필을 건드리지 않고 분리했다.

| 용도 | Profile | Scene Collection |
|---|---|---|
| 평소 방송·미팅 | `Untitled` (Simple, 화면 캡처 6개) | `Untitled` |
| Co-MC 실험 | `CoMC-Test` (고급, 트랙 1+2) | `CoMC-Test` |

`CoMC-Test/basic.ini` 를 직접 작성했다(`RecTracks=3` = 트랙1+2).
GUI 메뉴를 여러 단계 거치는 것보다 실수가 적다. 기존 프로필은 129줄 그대로,
`Mode=Simple` 유지를 확인했다.

소스 2개를 추가하고 장치를 `device_id` 로 대조해 어느 쪽이 무엇인지 확정했다
(화면의 `Audio Input Capture` / `2` 라는 이름만으로는 알 수 없다).

- `진행자 마이크` → `{...dd87a1e2...}` = Microphone (Shure MV7) → 트랙 1
- `AI 음성` → `{...579b552f...}` = CABLE Output → 트랙 2, 모니터링 Enabled

모니터링 출력은 `Headphones (Shure MV7)` 로 지정했다. 이유는 아래 문제 2 참조.

## 🐛 문제 해결 로그

### 문제 1: VB-CABLE 설치 프로그램이 Windows 기본 장치를 바꾼다 ← 미해결

설치 후 확인해 보니 이렇게 돼 있었다.

```
기본 출력 = CABLE Input    ← 모든 시스템 소리가 케이블로 샌다
기본 입력 = CABLE Output   ← 다른 앱이 마이크를 열면 MV7 대신 케이블을 잡는다
```

OBS 믹서의 `AI 음성` 미터에 -18dB 신호가 잡히던 원인이 이것이었다.

**이대로면 온라인 미팅에서 소리가 안 들리고 마이크도 안 잡힌다.**
`CABLE Input` 은 앱이 명시적으로 지정할 때만 쓰는 장치이고, 기본값이 되면 안 된다.
OBS 는 `CABLE Output` 을 직접 지정하고 TTS 코드도 이름으로 찾으므로
기본 장치일 필요가 전혀 없다.

**세션 종료 시점에 되돌리지 못했다** — 다음 세션 시작 시 최우선 확인 항목.

교훈: **설치 프로그램이 시스템 기본값을 바꿀 수 있다는 것을 설치 전에 안내했어야 했다.**
설치 후에 발견해서 진행자가 모르는 채 미팅에 들어갈 뻔했다.

### 문제 2: 모니터링을 스피커로 두면 에코 게이트 판정이 무의미해진다

OBS 모니터링 장치가 `Default` 였다. 기본 출력이 스피커면 이런 경로가 생긴다.

```
AI 음성 → CABLE Output → OBS 모니터링 → 스피커 → 🎤 MV7 이 다시 주워담음
```

M4 에서 에코 게이트를 만든 바로 그 문제다. 그리고 이 세션 초반에 설계 문서에
*"라우팅 후엔 TTS 가 헤드폰으로만 가니 에코 게이트가 불필요해질 수 있다"* 고 적었는데,
**그 결론은 모니터링이 헤드폰일 때만 성립한다.** 스피커면 에코 경로는 그대로 살아 있다.

`Headphones (Shure MV7)` 로 지정했다. 마이크 본체의 헤드폰 단자라 유선이고,
Galaxy Buds2 Pro 였다면 블루투스 지연 150~300ms 가 **케이블 314ms 위에 더해져**
오늘 잰 예산이 무너졌을 것이다.

### 문제 3: WASAPI 공유 모드는 장치 믹스 포맷을 요구한다

edge-tts 는 24kHz mp3 를 주는데 VB-CABLE 엔드포인트는 48kHz 다.
`Invalid sample rate [PaErrorCode -9997]` 로 실패했다.

캡처 장치의 `default_samplerate` 를 기준으로 리샘플링해 해결했다.
**변환 비용(8ms)도 실제 파이프라인에 존재하는 비용이므로 로드 구간에 포함해 쟀다** —
빼면 실측이 아니라 이상치가 된다.

### 문제 4: OBS 설정 파일을 통째로 출력하다 자격증명을 노출했다

`Untitled/basic.ini` 를 읽어 출력했는데 `[YouTube]` 섹션에 OAuth 토큰이 평문으로 있었다.

```
RefreshToken=1//069GuLmp...   ← 만료되지 않는다. 채널 방송 권한이 이 한 줄에 있다
Token=ya29.a0AdMD6Eh...       ← ExpireTime 상 2025-04 만료 (무해)
```

OBS 의 기본 저장 방식이라 진행자 잘못은 아니다. 다만 **설정 파일을 통째로 읽기 전에
자격증명 섹션을 걸렀어야 했다.** 신설 프로필에는 복사하지 않았다.

교훈: **남의 앱 설정 파일은 전체 출력하지 않는다.** 필요한 섹션만 뽑아 본다.

## 💡 Daily Retrospective

### What went well (잘된 점)

- **설계 전제를 그대로 따르지 않고 먼저 쟀다.** VoiceMeeter 설치가 불필요하다는 것을
  10분 만에 판별했다. 문서를 신뢰하되 실측으로 확인하는 순서가 맞았다
- **톤으로 검증한 것.** 파일 재생이었으면 "소리가 났다"까지만 알았을 텐데,
  주파수를 알고 넣으니 "내가 넣은 신호가 나왔다"를 스펙트럼으로 증명할 수 있었다
- 기존 OBS 프로필을 건드리지 않은 것. 방송 설정은 진행자의 생업 도구다

### What could be improved (개선할 점)

- **설치 프로그램의 부작용을 미리 조사하지 않았다.** VB-CABLE 이 기본 장치를 바꾸는 것은
  널리 알려진 동작인데, 설치 후에 발견했고 세션 종료까지 되돌리지 못했다
- **설정 파일을 통째로 출력했다.** 자격증명이 있을 수 있는 파일이라는 것을 먼저 생각했어야 했다
- OBS 트랙 배정을 검증용으로만 안내했다. 진행자가 "그럼 방송에 AI 목소리가 나가나요"라고
  묻고 나서야 송출 트랙과 녹화 트랙이 다르다는 것을 설명했다.
  **검증용 배치와 실전 배치가 다르다는 것을 처음에 말했어야 했다**

### Insights (인사이트)

**추측으로 넣은 구성요소는 실측하면 빠질 수 있다.** VoiceMeeter 는 "충돌할 수 있다"는
가정 위에 올라가 있었고, 재 보니 충돌이 없었다. 설계 문서의 확신에 찬 문장일수록
근거가 실측인지 추론인지 구분해야 한다.

**가상 케이블이라고 다 같지 않다.** MOTIV 는 앱이 믹서를 돌려야 이어지고 VB-CABLE 은
드라이버가 잇는다. 겉보기 장치 목록은 똑같이 생겼다. **"장치가 보인다 ≠ 소리가 흐른다"** 는
M5 의 "`models.list()` 에 있다 ≠ 호출 가능하다"와 같은 형태의 함정이다.

**314ms 는 줄일 수 없다.** 스트림을 미리 열어도 그대로였다. M7 에서 프로세스 기동 비용을
줄인 경험이 있어 같은 수를 기대했는데 통하지 않았다. **같은 종류의 해법이 항상 통하지는 않는다.**

**필러로는 못 덮는다.** 전체 예산을 쌓아 보니 침묵이 4.7~5.7초이고 필러는 1.5초짜리다.
"필러를 넣으면 해결된다"는 M5 시점의 기대가 실측 앞에서 무너졌다.
남은 선택지는 셋 — 필러를 늘리거나, LLM 을 더 줄이거나, 목표 4초를 고치거나. M7 에서 정한다.

**트랙 분리와 실시간 차단은 다른 문제다.** 설계 문서는 "트랙을 나누면 AI 트랙만 내릴 수 있다"고
적었는데, 실제 라이브에서 쓰는 조작은 **믹서의 소스 뮤트**다. 트랙 분리는 녹화본을
나중에 나누기 위한 것이다. 목적이 둘인데 하나로 적어 두었다.
