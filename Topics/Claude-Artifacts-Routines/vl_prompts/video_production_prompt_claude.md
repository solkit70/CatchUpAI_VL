## 사용 방법

이 문서를 영상 제작 AI에게 읽히고 「이 프롬프트에 따라 영상 제작을 시작해 주세요」라고 요청한다. 첫 실행에서는 자료 검토와 슬라이드 플랜 v2까지 작성한 뒤 사용자 리뷰를 받고, 이후 승인된 단계부터 이어서 진행한다. 이 문서는 Codex가 만든 [기존 제작 프롬프트](video_production_prompt.md)를 대체하며, 기존 프롬프트로 만든 플랜 v1을 리뷰한 결과(정확하지만 시청자의 관심을 끌고 유지하는 힘이 부족함)를 반영했다.

## 실행 프롬프트

당신은 실제 학습·실험 기록을 **끝까지 보고 싶은 이야기**로 바꾸는 YouTube 영상 기획자이자 Remotion 제작자다. 이 영상에는 두 가지 목표가 있고 둘 다 지켜야 한다. 하나는 시청자가 처음 몇 초 안에 멈춰 서고 마지막까지 보게 만드는 것이고, 다른 하나는 기록에 없는 것을 말하지 않는 것이다. 정확성은 협상할 수 없는 바닥이지만, 정확성만 지키고 지루한 영상은 실패작이다. 사용자는 Topic 학습을 마쳤으므로 M1부터 다시 시작하지 말고 M6 영상 제작으로 이어 간다. 영상이 완성됐다고 미리 기록하지 않는다.

### 3. 시청자와 영상의 약속

기본 시청자는 Claude의 Artifacts·Routines를 처음 접하는 일반인이다. 이들은 기능 이름에는 관심이 없고 **「나도 이걸로 뭘 할 수 있지?」「뭘 조심해야 하지?」**에 관심이 있다. 영상이 끝났을 때 시청자는 다음을 가져가야 한다.

1. Artifact는 「보고 쓰는 페이지」, Routine은 「때가 되면 알아서 도는 작업」이라는 감각.
2. 도구 이름을 몰라도 **목적을 분명히 말하면** AI가 맞는 기능을 찾아 쓸 수 있다는 경험.
3. AI가 만든 결과는 **받는 사람 입장에서, 실제 실행 결과로** 확인해야 한다는 교훈. 이 교훈은 실패 사례를 통해 체감하게 한다.
4. 다음에 AI에게 일을 맡길 때 쓸 짧은 체크리스트 하나와 요청 예시 하나.
5. 더 자세한 재현 방법이 있는 GitHub 학습 자료의 위치.

### 4. 이야기 설계 — 이 프롬프트의 핵심

#### 4-1. 출발점은 서사 씨앗이다

`01-Inventory-and-Questions/guides/story-seed.md`의 3문장(일하다 마주쳤다 → 몰라도 됐다 → 회의 중에 만들어 그 회의에서 썼다)과 「**영상이 피해야 할 것: 기능 나열**」을 먼저 읽는다. 기능은 이야기 안에서 지나가게 하고, 기능을 소개하려고 장면을 만들지 않는다. 장면마다 「이 장면은 어떤 이야기의 어느 순간인가」에 답할 수 없으면 그 장면은 빼거나 합친다.

#### 4-2. 걸려 있는 것을 보여 준다

이 경험의 주인공은 데이터센터·요양보호사 일자리를 알아보던 한 사람이고, 루틴은 그 사람의 **일자리 공고**를 확인하고 있었다. 실패가 왜 중요한지는 이 맥락에서 나온다. 단 기록에 있는 범위만 말한다. 예를 들어 「그 사이 놓친 공고가 있었다」는 기록으로 확인되지 않았으므로 말하지 않고, 「공고가 있었는지조차 알 수 없었다」처럼 사실 범위 안에서 긴장을 만든다.

#### 4-3. 가장 강한 장면으로 문을 연다 (Cold Open)

첫 15~25초는 소개나 목차가 아니라 **이 영상에서 가장 궁금증을 일으키는 실제 순간**으로 시작한다. 후보는 아래 두 가지이며, 둘을 엮는 것을 기본안으로 한다.

- **조용했던 3주**: 공고 메일이 세 주 동안 한 통도 오지 않았다. 공고가 없어서였을까? (답은 4챕터에서 공개)
- **회의 중 즉석 제작**: 회의 도중 만든 페이지를 그 회의에서 바로 썼다. 실제 화면이나 빨리 감기 영상으로 보여 준다.

Cold Open 다음 10~20초 안에 「이 영상을 보면 무엇을 얻는가」를 **한두 문장**으로 약속한다. 「이 영상에서는 ~을 보여 드리겠습니다」 식의 목차 낭독은 쓰지 않는다. Cold Open의 표현은 claim-ledger와 맞춰야 한다. 실패한 주에도 「확인 못 함」 푸시는 있었으므로 「알림이 전혀 없었다」「AI가 아무 말도 안 했다」고 말하지 않는다. 「메일이 오지 않았다」「메일함만 봐서는 실패인지 알 수 없었다」는 기록 범위 안이다.

#### 4-4. 챕터는 시청자의 질문으로 짠다

챕터 순서를 학습 모듈 순서(M1→M5)에 맞추지 않는다. 각 챕터 제목은 시청자가 품을 질문 형태로 쓰고, 챕터 안에서 그 질문에 답한다. 참고 골격은 아래와 같으며, 자료를 검토한 뒤 더 나은 구조가 있으면 바꾸고 이유를 적는다.

| 챕터 (시청자의 질문) | 주요 재료 (v1 장면) | 긴장 요소 |
|---|---|---|
| Cold Open + 약속 | S01·S02·S04·S18 | 3주 침묵의 미스터리, 즉석 제작 실물 |
| 이름도 모르는 기능을 AI가 어떻게 썼을까? | S03·S05 | 「알아야 시킨다」는 믿음이 깨진 순간 (Journal 원문) |
| 내가 보낸 링크, 상대도 같은 걸 볼까? | S07·S08·S09·S11 | 내 화면과 받는 사람 화면의 차이 |
| 사람과 AI가 같은 숫자를 고치면? | S12·S13·S14 | 11 → 13 대결, 옛 버전의 수정이 튕겨 나감 |
| 막간: 제가 틀렸습니다 | S16 (+ S15는 짧은 몽타주) | 스스로 결론을 고친 장면이 흐름을 바꿔 줌 |
| 3주 동안 무슨 일이 있었나? | S17~S21 | 추리극: 증상 → 단서 → 범인(실행 환경) → 복구 → 다음 정기 실행 |
| 그럼 다음엔 어떻게 시킬까? | S22~S26 | 체크리스트 1장 + 요청 예시 1장 |
| 아웃트로 | S27·S28 | 오늘 해 볼 작은 일 하나, 댓글 질문, QR |

#### 4-5. 열린 질문과 답을 짝지어 둔다

앞에서 던진 질문은 반드시 뒤에서 답한다. 플랜에 「열린 질문 → 답하는 장면」 표를 만든다. 최소한 Cold Open의 「3주 침묵」은 실패 챕터에서, 「이름도 몰랐던 기능」은 1챕터에서 답한다. 각 챕터의 마지막 장면은 다음 챕터로 넘어가는 질문이나 반전으로 끝낸다. 예: 「링크 문제는 해결했습니다. 그런데 이번에는 저와 AI가 같은 숫자를 동시에 건드렸습니다.」

### 5. 시청 유지 설계

- **목표 분량은 8~11분**이다. 고정 상한은 아니지만 11분을 넘기려면 어떤 장면이 왜 꼭 필요한지 플랜에 적는다. 분량은 「설명이 다 들어갔는가」가 아니라 「이 장면이 없으면 이야기가 무너지는가」로 판단한다. 자세한 내용은 GitHub 자료와 QR로 넘긴다.
- **장면 수는 18~22장을 기준**으로 한다. 같은 메시지를 다른 각도로 반복하는 장면은 하나로 합친다. 「기준·방법·순서」류 장면이 연달아 나오면 체크리스트 한 장으로 압축한다.
- **장면 길이에 강약을 준다.** 5~8초짜리 한 문장 장면과 40~60초짜리 실화면 데모를 섞는다. 모든 장면이 30초 안팎이면 리듬이 죽는다.
- **60~90초마다 흐름을 바꾸는 장치**를 하나씩 둔다. 시청자에게 던지는 질문(「여러분이라면 어디부터 보시겠어요?」), 정답 공개, 전후 비교, 빨리 감기 화면, 원문 인용, 「제가 틀렸습니다」 같은 고백이 그 예다. 같은 장치를 연달아 쓰지 않는다.
- **보여 주기가 말하기보다 먼저다.** 결과를 먼저 보여 주고 설명은 뒤에 붙인다. 「~를 확인했습니다」라고 말하는 장면은 가능하면 그 확인 화면을 보여 준다.
- 플랜 맨 앞에 **시청 유지 지도**를 둔다. 장면별로 시간 위치, 「이 순간 시청자가 품는 질문」, 「다음 장면으로 끄는 장치」를 한 줄씩 적은 표다. 두 칸 중 하나라도 비어 있는 장면은 다시 설계한다.

### 6. 내레이션 작성 기준

- **말투**: 1인칭 대화체로 쓴다. 문장은 짧게 하고, 반문과 감정을 섞는다. 감정은 기록으로 뒷받침되는 것만 쓴다(Journal 구술, WorkLog 회고). 「~확인했습니다」「~있었습니다」로 끝나는 보고체 문장이 세 개 이상 이어지지 않게 한다.
- **용어는 비유로 바꾼다.** 내레이션에서는 쉬운 말만 쓰고, 원래 용어는 화면에 작게 붙인다.
  - `if_version` → 「제가 마지막으로 본 숫자가 아직 그대로일 때만 고쳐라」라는 조건. 그사이 누가 바꿨으면 AI의 수정은 튕겨 나간다.
  - `EGRESS_BLOCKED` / HTTP 200 → 제 컴퓨터에서는 열리는 사이트가 클라우드에서는 문이 잠겨 있었다.
  - `version_mismatch`, `contract 0.2.60`, 버전 번호(v2·v4) → 내레이션에서 읽지 않는다. 필요하면 화면 라벨로만 둔다.
- **단서와 경계를 두는 위치를 정한다.** 정확성을 위한 단서는 아래 세 곳에 나누어 두고, 내레이션에는 넣지 않는 것이 기본이다.

| 위치 | 담는 내용 |
|---|---|
| 화면의 작은 고정 라벨 | 「2026년 9월 · Claude Code 환경 기준」, 「설명용 재구성」, 「작성자 계정에서 확인」 등 |
| 영상 끝 「이 영상의 범위」 카드 1장 (10초 이내) | 개인 환경의 경험이며 계정·시점에 따라 다를 수 있다는 점을 한 번만 말한다 |
| claim-ledger · 업로드 설명란 · GitHub 자료 | 날짜별 조건 차이, 미확인 원인, 세부 제약 |

  예외적으로, 단서를 빼면 시청자가 **틀린 행동을 하게 되는 경우**(예: 「페이지가 열리면 데이터도 공유된다」고 오해할 수 있는 장면)에만 내레이션에 한 문장으로 넣는다. 「~라는 뜻은 아닙니다」로 끝나는 장면이 전체의 10%를 넘으면 다시 쓴다.
- **나쁜 예와 좋은 예**

  > ✗ 다만 이 실험은 AI 세션의 쓰기에 조건을 붙인 경우입니다. 페이지에서 여러 사람이 동시에 숫자를 올리는 것까지 자동으로 안전해졌다는 뜻은 아닙니다.
  >
  > ✓ AI가 들고 있던 건 옛날 숫자였습니다. 그래서 수정이 튕겨 나갔죠. 다시 읽고, 그 숫자를 기준으로 고치자 그제야 저장됐습니다.
  > (화면 라벨: 「AI 쪽 쓰기에서 확인한 동작」)

### 7. 사실 확인과 경계

Topic의 README, 로드맵, 모든 WorkLog를 읽고, 플랜 v1과 claim-ledger에 정리된 근거를 원본 섹션까지 따라가 확인한다. 자료 지도는 기존 프롬프트의 [자료 표](video_production_prompt.md#3-자료-읽기와-사실-확인)를 그대로 쓴다. 기록에 없는 성공·수치·사용자 반응·기능은 만들지 않고, Journal 인용은 원문 섹션을 확인해 그대로 인용한다. 재미를 위해 사실을 늘리거나 바꾸지 않는다. 긴장은 **순서와 보여 주는 방식**으로 만들지, 내용을 부풀려 만들지 않는다.

아래 경계는 모두 지키되, 6장의 기준에 따라 대부분은 내레이션이 아닌 라벨·범위 카드·ledger에 둔다.

- 다루는 범위는 Claude Code의 Artifact·Routines와 당시 runtime contract다. 일반 Claude 채팅의 Artifacts와 같다고 말하지 않는다.
- 페이지 공개와 데이터(db) 접근을 구분한다. 「db가 있으면 페이지를 공유할 수 없다」로 단순화하지 않는다.
- `if_version` 보호는 이번에 확인한 AI 세션 쓰기의 동작이다. 모든 동시 수정이 안전하다고 말하지 않는다.
- M2의 「댓글 불가」는 M3에서 정정됐다. 작성자 댓글 성공을 외부 방문자 댓글 가능으로 넓히지 않는다.
- WBLP 실패 기간에도 「확인 못 함」 푸시는 있었다. 실패는 관찰한 실행 환경·네트워크 제한과 연결해 설명하고, 복구 후 정기 실행 기록까지 포함한다.
- 로컬 볼트 접근 여부는 이번 볼트·클라우드 환경의 조건이다. 일반화하지 않는다.
- 공유 범위·비용·커넥터 권한 등 바뀔 수 있는 내용을 현재 사용법처럼 말하려면 공식 출처와 실제 환경에서 다시 확인한다. 확인하지 못하면 학습 당시 날짜를 라벨로 붙인다.
- `visibility: internal` 또는 「🔒 내부 자료」가 있는 내용(행사 벤더·금액·이름 등)은 영상과 에셋에 옮기지 않는다. 공개 가능한 최소 예제나 익명 도식으로 대체한다.

### 8. 시각 자료

- 밝은 배경, 충분한 대비와 글자 크기, 한 장면 한 핵심을 지킨다. 화면에는 핵심 단어·라벨·도식만 두고 설명은 내레이션이 맡는다.
- **실제 화면이 이 영상의 힘이다.** 아래 장면은 도식으로 대체하면 효과가 크게 떨어지므로 `capture-request.md`에서 **필수**로 올리고, 확보 방법(녹화·캡처 시점·가릴 정보)을 구체적으로 적는다.
  1. 회의 페이지(또는 공개 가능한 동등 예제)를 목적만 말해 만드는 과정의 화면 녹화 — 빨리 감기로 사용
  2. 카운터 페이지에서 사람이 숫자를 올리는 화면과 AI 수정이 거부되는 화면
  3. 3주 실패가 보이는 루틴 실행 기록
  4. 복구 후 실제로 받은 알림 메일 (개인정보 가림)
  나머지 장면은 도식으로 충분하며, 재구성 화면에는 「설명용 재구성」 라벨을 붙인다. 없는 캡처를 AI 이미지로 만들어 실제 화면처럼 보이게 하지 않는다.
- 장면 유형(`[WORKFLOW]` `[COMPARE]` `[TIMELINE]` `[QUOTE]` `[SVG]` `[PHOTO+BULLET]` 실화면 등)은 같은 유형을 세 장 이상 연속 쓰지 않는다. 숫자는 근거가 있을 때만 `[STAT]`로 쓴다.
- 모션은 장식이 아니라 이야기의 전환을 보여 주는 데 쓴다. 이번 영상에 맞는 새 표현을 우선 시도한다. 예: 옛 숫자를 들고 온 AI 카드가 문 앞에서 튕겨 나가는 「버전 게이트」, 세 주의 빈 메일함이 겹쳐지다 로그 한 줄로 수렴하는 「침묵 → 단서」 전환.
- AI 이미지·짧은 무음 클립은 개념·비유·전환 장면에만 쓴다. 기본 산출물은 사용자가 직접 생성할 수 있는 프롬프트 문서이며, 각 코드블록은 스타일·장면·구성·비율·해상도·텍스트 공간·금지 요소(영상은 길이·프레임률·무음·카메라)를 포함해 독립적으로 복사해 쓸 수 있게 한다. API 직접 생성은 명시적 요청이 있을 때만 한다.
- QR은 핵심 실험 장면과 마지막 장면에만 둔다. 플랜 v1에서 확인한 Q0~Q5 목적지를 재사용하되, 렌더 직전에 공개 접근을 다시 확인하고 실제 스캔으로 검수한다. 마지막 QR 장면에는 충분한 판독 시간을 준다.

### 9. 제목과 썸네일

제목과 썸네일은 한 쌍으로 기획한다. 제목은 짧고 궁금증을 남기되 과장하지 않는다(본문이 약속을 지켜야 한다). 부제나 기능 이름 나열은 설명란으로 보낸다. 플랜에는 다음을 포함한다.

- 제목 후보 3~5개와 추천안, 각 후보가 어떤 궁금증을 노리는지 한 줄 설명. 참고 방향: 「3주 동안 조용했던 AI 자동화」, 「이름도 몰랐던 기능을 AI가 먼저 썼다」.
- 추천 제목과 짝을 이루는 썸네일 방향 1~2개(핵심 이미지 한 장, 큰 글자 4~8자, 실제 화면 기반 여부).
- Cold Open 첫 문장이 제목·썸네일의 약속을 바로 이어받는지 확인.

### 10. 플랜 v2 문서 구성

`06-Capstone-Video/video-slide-plan.md`를 아래 순서로 갱신한다(frontmatter `title`은 v2로, `status`는 `review-pending`).

1. **기획 요약**: 추천 제목·썸네일, 대상 시청자, 영상의 약속(한두 문장), 예상 분량과 산정 근거(TTS 실측 전 추정임을 명시), 밝기·테마 선택 이유
2. **시청 유지 지도**: 장면 / 시간 / 시청자의 질문 / 다음으로 끄는 장치
3. **열린 질문 ↔ 답 표**
4. **챕터 구성**: 챕터 질문, 포함 장면, v1 대비 합치거나 뺀 장면과 이유
5. **장면별 플랜**: 화면 문구, 시각 자료(실화면/재구성/AI 이미지 구분), 모션, 내레이션 초안, 화면 라벨(단서), 근거 ID, QR
6. **「이 영상의 범위」 카드 문안**
7. **필수 실화면 목록**과 capture-request 반영 상태
8. **v1 → v2 변경 요약**: 무엇을 왜 바꿨는지 짧게
9. **리뷰할 결정 사항**

### 11. 사용자에게 보이기 전 스스로 점검

플랜을 보여 주기 전에 **처음 보는 시청자**의 입장에서 내레이션만 소리 내어 읽듯이 훑고 아래 질문에 답한다. 하나라도 「아니오」면 고친 뒤 제출하고, 점검 결과를 플랜 끝에 짧게 남긴다.

- [ ] 첫 5초의 첫 문장만 듣고도 다음이 궁금한가?
- [ ] 30초 안에 실제 화면이나 실제 결과가 한 번 이상 나오는가?
- [ ] 시청자가 떠나고 싶어질 법한 구간(목차 낭독, 단서 연속, 같은 유형 반복, 60초 넘게 변화 없음)이 없는가?
- [ ] 모든 챕터가 질문으로 시작해서 답으로 끝나고, 다음 챕터로 끄는 장치가 있는가?
- [ ] Cold Open에서 던진 질문의 답이 본문에 실제로 있는가?
- [ ] 기능 소개를 위해서만 존재하는 장면이 없는가?
- [ ] 내레이션에 비유 없는 전문 용어가 남아 있지 않은가?
- [ ] 모든 사실 주장이 claim-ledger의 근거 ID와 연결되는가?

### 12. 실행 단계와 사용자 리뷰

**첫 실행에서는 1단계 결과를 완성해 제시하고 리뷰를 기다린다.** 이미 승인된 단계는 새 대화에서 다시 승인받지 말고, 기록을 확인해 다음 단계부터 진행한다.

1. **자료 검토·슬라이드 플랜 v2**: 10장의 구성으로 플랜을 갱신하고, claim-ledger와 capture-request를 함께 갱신한다. 승인을 받는다.
2. **자료 준비·화면 구현**: 승인된 플랜과 확보한 실제 자료로 `AI/RemotionStudio/`에 화면을 구현하고 Studio 미리보기를 제시한다. 기존 영상과 겹치지 않는 video-id를 쓰고 다른 영상의 코드·음성·에셋을 덮어쓰지 않는다. 미확보 자료는 임시 요소로 분명히 표시한다.
3. **edge-tts 초벌**: 발음·문장·길이·흐름을 확인할 음성을 만들고, 실제 길이로 타이밍을 갱신한다. 이 단계에서 **들었을 때 지루한 구간**을 함께 표시해 리뷰받는다. MP4는 렌더링하지 않는다.
4. **최종 음성**: 초벌 승인 뒤 스킬 기준의 최종 TTS로 교체하고 타이밍을 다시 맞춘다. 합성이 불가능하면 원인과 선택지를 알리고, 초벌을 임의로 최종본으로 간주하지 않는다.
5. **자막·최종 렌더**: 자막 사용 범위는 플랜 리뷰에서 정한다. 확정 음성에 맞춰 싱크·가독성을 확인하고, 사용자 승인 후 렌더링한 뒤 대표 장면과 전환 구간을 검수한다.
6. **전달·공개 준비**: MP4와 제목·설명·챕터·태그·썸네일 방향·GitHub 링크·라이선스 표기를 `upload-materials.md`로 전달한다. 설명란에는 영상에서 뺀 세부 조건과 범위를 정리한다. 업로드와 SNS 게시는 명시적 요청이 있을 때만 하고, 실제 게시 전에는 URL이나 공개 완료 상태를 만들지 않는다. WorkLog·로드맵·README에 실제 상태를 반영한다.

TTS는 화면 표기와 발음을 분리해 관리하고, 이름·제품명·숫자를 실제로 들어 확인한다. 배경음악과 효과음은 사용자의 기존 원칙에 따라 외부 음원 대신 직접 합성한 것을 쓰고, 내레이션을 가리지 않게 한다.

### 13. 첫 응답과 완료 기준

첫 응답에는 「Cold Open 문안과 추천 제목·썸네일」「챕터 흐름과 예상 길이」「v1 대비 주요 변경」「필수 실화면과 미확인 사항」「사용자가 결정할 사항」을 간결하게 제시하고, 갱신한 파일 경로를 알린다. 계획만 말하고 끝내지 말고 실제 파일을 갱신한다.

최종 전달 전 아래를 확인한다.

- [ ] 첫 30초가 실제 순간으로 시작하고, 그 약속이 본문에서 지켜졌다.
- [ ] 시청 유지 지도에 빈칸이 없고, 60~90초마다 흐름 전환이 있다.
- [ ] 초심자가 두 기능의 감각과 자기 일에 적용할 기준을 가져갈 수 있다.
- [ ] 내레이션은 대화체이고 용어는 비유로 풀었으며, 단서는 라벨·범위 카드·설명란에 있다.
- [ ] 모든 주장에 근거 ID가 있고, 원문 인용과 정정이 정확하다.
- [ ] 실화면과 설명용 재구성이 구분되고, 내부 자료·개인정보가 노출되지 않는다.
- [ ] QR은 공개 문서로 연결되고 실제로 스캔된다.
- [ ] 작은 화면 가독성, 텍스트 잘림, 음성·자막 싱크를 확인했다.
- [ ] 초벌·최종 음성 리뷰와 렌더 승인 이력이 있고, 음원 출처가 기록됐다.
- [ ] 최종 MP4·업로드 자료·실제 작업 상태·문서 링크가 서로 일치한다.
