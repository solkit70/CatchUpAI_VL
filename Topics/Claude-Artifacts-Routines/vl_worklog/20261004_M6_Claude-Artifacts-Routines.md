## 진행 내용

### 자료와 근거 정리

Topic의 README·로드맵·M1부터 M5까지 WorkLog와 주요 실습 문서를 읽고, 사용자의 9/1·9/3 Journal 원문을 확인했다. Git 원격과 main을 확인하고 공개 raw 파일6개의 HTTP200 응답을 받았다. Artifact·Routines 공식 문서와 공개 플레이북 페이지도 읽어 정의·제품 범위·현재 댓글 설명을 교차 확인했다.

### 슬라이드 플랜

발견 → 공유 → 사람·AI 데이터 충돌 → 루틴 실패와 복구 → 자신의 일에 적용의 흐름으로 28장을 구성했다. 분량을 먼저 제한하지 않고 원고의 공백 제외3,251자와 판독 시간을 근거로 약12~15분을 추정했으며, 14분18초는 임시 배치값이다. 실제 TTS 길이가 나오는 단계에서 조정한다.

### 캡처 상태

Topic에서 png·jpg·jpeg를 찾지 못했다. 과거 캡처가 있었다는 기록과 현재 원본 파일 보유 상태를 분리했다. 원본 없이 과거 UI를 꾸며내지 않고, 필요한 화면8건과 표시를 붙인 기록 재구성 대안을 정리했다.

### 사용자 리뷰 → 프롬프트 교체 → 플랜 v2 (Claude Code)

사용자가 v1을 리뷰하고 「정보 전달은 되지만 관심을 끌고 끝까지 유지하는 힘이 부족하다」고 판단했다. 분석해 보니 원인은 플랜보다 프롬프트에 있었다. 기존 프롬프트는 정확성 규칙이 대부분이었고, 관심 끌기에 대한 지시는 Hook 한 줄뿐이었다. 또 분량 상한 없이 장면 순서를 미리 정해 줬다. 그래서 [Claude 버전 제작 프롬프트](../vl_prompts/video_production_prompt_claude.md)를 새로 만들었다. 이 프롬프트에는 Cold Open, 시청자의 질문으로 짠 챕터, 열린 질문과 그 답의 짝, 단서를 두는 위치(라벨·범위 문장·근거 대장), 비유 중심 내레이션, 8~11분 목표, 제출 전 자체 점검이 들어 있다.

같은 근거로 [플랜 v2](../06-Capstone-Video/video-slide-plan.md)를 다시 짰다. 결과는 22장, 약 10~11분(공백 제외 2,776자)이다. 3주 실패를 Cold Open으로 옮겼고, 시청자 퀴즈 2회·고백 장면·추리극 구조를 넣었다. 내레이션 속 단서는 7곳에서 1곳으로 줄였다. 루틴 audit을 다시 읽다가 v1이 쓰지 않은 사실 두 가지를 찾았다. 하나는 복구 직후 「그동안 받지 못했던 공고 4건」이 메일로 왔다는 것이고(C29 신규), 다른 하나는 회의 페이지가 로그인하지 않은 창에서 「빈 화면」이었다는 실제 함정이다. 근거 대장에는 v2 장면 대응표를 추가했다. 캡처 요청에는 필수 실화면 R1~R4를 정했다.
