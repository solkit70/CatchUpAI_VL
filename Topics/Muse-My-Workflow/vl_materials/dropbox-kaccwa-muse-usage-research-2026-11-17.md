# 로컬 KACCWA 폴더 → Dropbox → Muse 활용 방식 연구 정리

**테스트일:** 2026-11-17 (화) · **검증 재확인일:** 2026-11-18 (수) 오전
**정리 업데이트:** 2026-11-18 — 전체 다운로드 논의, Obsidian 그래프 검색 검증, PC-off 활용법·리스크 정리 추가
**대상:** 사용자 로컬 PC의 "워싱턴주 한인 상공회의소(KACCWA)" 폴더 → Dropbox `/KACCWA` → Muse
**목적:** PC를 끈 상태에서 외부에 있는 AI(Muse)가 로컬 데이터를 참조해 답할 수 있는지, 실제 행사 상황에서 테스트

업로드는 사용자가 직접 한 것이고, Muse는 업로드에 관여하지 않았다. Muse가 한 일은 업로드된 뒤의 **확인·열람**뿐이다.

## 2. Muse가 Dropbox에 실제로 한 일 (호출 내역)

Muse는 Dropbox를 **전체 동기화가 아니라, 필요할 때마다 파일 단위로 API 호출**하는 방식으로 썼다. 11/17에 `/KACCWA` 대상으로 실행한 호출은 아래 5건이 전부다.

| # | 도구 | 대상 | 결과 |
|---|---|---|---|
| 1 | `list_folder` (루트, 업로드 전) | Dropbox 루트 | KACCWA 없음 확인. M4 테스트 폴더만 존재 |
| 2 | `list_folder` (recursive) | `/KACCWA` | 폴더 48개·파일 186개 목록(메타데이터) 조회. **파일 내용은 읽지 않음** |
| 3 | `fetch` | `/KACCWA/20261013_Startups/2026-10-13 한국 선정 5개사 참가자 연락처.txt` | 텍스트 추출해 읽음. 연락처 파일 존재 및 내용 확인 |
| 4 | `fetch` | `/KACCWA/20261117_Muse/2026-11-17 KSDD Muse 공개 행사 팩 by Claude Code.md` | 텍스트 추출해 읽음. 행사 팩 규칙 확인 |
| 5 | `download` (1회) | `/KACCWA/20261102_StatusBoard/ksdd-status-board.html` | HTML이라 `fetch` 텍스트 추출이 비어 있어 다운로드로 내용 확인. Luma 링크만 있고 폼 링크는 없음 |

### 다운로드 받았나, 원격 참조만 했나 — 결론: 둘 다 있었고, 구분은 이렇다

- **`fetch` (3·4번)는 원격 참조에 가깝다.** 파일 바이트를 Muse 컴퓨터에 저장하지 않고, Dropbox 서버 쪽에서 텍스트를 추출해 그 텍스트만 도구 응답으로 받아왔다. Muse 워크스페이스에 해당 파일의 사본은 남지 않는다.
- **`download` (5번)는 실제로 내려받았다.** 다만 1개 파일(상태판 HTML)만, 그것도 내용 확인용 1회성 읽기였고, **오늘(11/18) 워크스페이스와 임시 폴더를 검색한 결과 해당 파일의 사본은 남아 있지 않다.** 저장 목적의 다운로드가 아니라 "fetch로 읽히지 않는 파일을 눈으로 확인하기 위한" 일회성 조치였다.
- **폴더 전체를 내려받은 일은 없다.** 186개 파일 중 Muse가 내용을 읽은 것은 위 3개 파일뿐이다. 나머지는 이름·크기·수정 시각 같은 목록 정보만 조회했다.

### 수정·생성된 파일이 있나 — 결론: Dropbox 안에는 0건

- Muse는 `/KACCWA`에 대해 **쓰기 호출을 한 번도 하지 않았다.** 생성(`create-file`)·수정·이동·삭제·공유 링크 생성 모두 0건이다.
- 오늘(11/18) 라이브 재확인: 186개 파일 중 업로드 점검 시점(11/17 18:14 UTC) 이후 서버 수정 시각(`modified_time`)이 바뀐 파일은 **0건**. 가장 최신 수정 시각은 18:07:48 UTC로, 업로드 자체의 시각이다. 즉 업로드 이후 Dropbox 안의 파일은 누구도 건드리지 않았다.
- Muse가 새로 만든 파일(5개사 정리본, 패널 토크 스크립트, 데일리 로그 기록 등)은 **Muse 자신의 워크스페이스(`~/workspace/...`)**에 있으며, Dropbox나 사용자 PC로 되돌아가지 않는다. 양방향 동기화가 아니다.

## 3. 동작 원리 — Muse는 로컬 PC를 직접 보지 않는다

1. **Muse가 보는 것은 클라우드다.** 사용자 PC의 Dropbox 폴더는 데스크톱 클라이언트가 Dropbox 서버로 동기화하고, Muse는 Dropbox API로 서버에 질의한다. PC 전원이 꺼져도 서버에 있는 사본이 읽힌다.
2. **이것은 11/14에 이미 증명된 방식이다.** PC-off 테스트에서 PC가 꺼진 상태에서 Muse가 Dropbox에 파일을 만들고(`pc-off-return-20261114.md`), 다시 내려받아 바이트 단위로 동일함을 검증했다. 이번 KACCWA 테스트는 그 증명을 실제 행사 자료에 적용한 것이다.
3. **읽기는 질문할 때마다 새로 일어난다.** Muse는 폴더 전체를 미리 복사·색인해 두지 않는다. 질문이 들어올 때마다 `list_folder`로 목록을 보고, 필요한 파일만 `fetch`/`download`로 읽는다. 그래서 어제 읽은 내용도 다음 질문 때는 다시 API로 확인하는 구조다.
4. **파일 형식에 따라 읽는 방법이 다르다.** 텍스트 기반 파일(.md/.txt, 텍스트 추출이 되는 PDF)은 `fetch`로 바로 읽힌다. HTML은 `fetch`가 빈 텍스트를 반환해 `download`가 필요했고, .pptx/.docx 같은 바이너리는 다운로드 후 별도 추출이 필요하다.
5. **읽은 범위는 열린 파일에만 한정된다.** 연락처 txt를 열어 내용은 확인했지만, 그 안의 전화번호·이메일은 채팅에 그대로 노출하지 않았다. 존재 여부와 범위만 답했다.

---

## 4. Dropbox 자료로 실제로 답한 것 (출처 구분이 중요)

Dropbox에서 읽은 자료가 답에 쓰인 경우와, 쓰이지 않은 경우를 구분하면 다음과 같다.

**Dropbox에서 와서 답에 쓰인 것**
- **행사 팩 규칙이 이후 모든 행사 답변의 기준이 됐다.** 공개 자료만 기준, 팩에 없는 사실은 "팩에 없음"이라 답하기, 문서와 메일이 다르면 최신 메일 우선, 되돌리기 어려운 일은 실행 전 묻기.
- **연락처 파일이 실제로 존재함을 확인**하고, 5개사 참석자 7명의 이름·소속을 대조했다. (단, 전화번호·이메일은 채팅에 노출하지 않음)
- **상태판 HTML에 참석자 등록 폼 링크가 없음**을 확인했다. (이후 폼 링크는 사용자가 직접 공유해 해결됨)
- **폴더 지도**(48개 폴더 구성)를 파악해, 이후 질문 때 어느 폴더에 무엇이 있는지 안내할 수 있게 됐다.

**Dropbox에서 온 것이 아닌 것 (혼동 주의)**
- 5개사 현장용 메모 정리본: 사용자가 채팅에 직접 올린 PDF(`2026-11-17____5.pdf`)에서 왔다.
- 패널 토크 모더레이터 스크립트: 사용자가 채팅에 직접 붙여넣은 원문이다.
- 참석자 명단 40명·Day 3 참석자 27명·한국 기업/재외동포청 리스트: 사용자가 공유한 구글 시트(보기용) 링크를 열어 세어 답한 것이다.
- 즉, 11/17 행사 당일 답변의 상당수는 Dropbox가 아니라 **채팅 업로드·붙여넣기·사용자 공유 링크**에서 왔다. Dropbox의 기여는 폴더 구조 파악과 행사 팩·연락처·상태판 확인이 중심이다.

## 5. 왜 Dropbox였나 — 왜 구글 드라이브가 아니었나

당시 Muse가 Dropbox를 먼저 권했고, Drive를 대안으로 둔 이유는 다음과 같다.

| 이유 | 내용 |
|---|---|
| **이미 연결돼 있었다** | Dropbox는 11/8에 Muse에 연결된 상태였고 읽기 권한이 있었다. Drive도 연결돼 있었지만, 아래 이유들이 Dropbox를 앞세웠다 |
| **PC-off 접근이 이미 증명돼 있었다 (결정적)** | 11/14 PC-off 테스트로 "PC가 꺼져 있어도 Dropbox 파일은 Muse가 읽을 수 있다"는 것이 실제로 증명돼 있었다. 이번 테스트의 목적 자체가 그 시나리오였으므로, 증명된 경로를 쓰는 것이 맞았다. Drive로는 같은 증명이 없었다 |
| **계정 가시성 문제** | Drive 커넥터는 사용자의 solkit70 구글 계정에만 연결돼 있다. 상공회의소 구글 계정은 연결돼 있지 않아, 상공회의소 계정에 있는 자료는 Drive·Gmail 검색에서 보이지 않는다. 실제로 같은 날 오전, 참석자 등록 폼/시트를 Drive·Gmail에서 찾지 못해 사용자가 링크를 직접 공유해야 했다. Dropbox는 사용자가 자기 계정에 직접 복사해 넣는 구조라 이런 계정 갈림이 없다 |
| **동기화 방식** | PC에 Dropbox 데스크톱 클라이언트가 이미 동기화 중이었으므로, 폴더를 복사해 넣기만 하면 자동으로 클라우드에 올라갔다. 별도 업로드 절차가 필요 없었다 |
| **쓰기 범위** | Dropbox는 첫 연결이 읽기 전용이고, 쓰기 범위(`content.manage`)는 11/14에 부여된 것이 확인돼 있다. 다만 이번 테스트에서는 쓰기를 전혀 쓰지 않았다 |

**Drive가 불가능했다는 뜻은 아니다.** 사용자 본인 계정(solkit70) Drive에 직접 올린 파일이라면 Muse가 읽을 수 있다. 다만 (a) PC-off 증명이 없었고, (b) 상공회의소 계정 자료는 Drive 검색에서 보이지 않는다는 점이 당일 확인됐기 때문에, 이번 테스트의 1순위는 Dropbox였다.

## 6. 한계와 주의점 (다음 테스트를 위해)

- **실시간 동기화가 아니다.** PC에서 Dropbox 폴더에 파일을 추가·수정해도, Muse는 질문할 때 새로 조회하기 전까지 모른다. "올렸다"는 말 한마디가 Muse가 다시 보게 하는 계기가 된다.
- **읽는 것은 필요한 파일만이다.** 186개 파일이 있다고 186개를 다 읽는 것이 아니다. 질문과 관련된 파일만 골라 읽는다. 따라서 "폴더를 통째로 Muse가 알고 있다"는 표현은 정확하지 않다. 정확히는 "목록은 알고 있고, 내용은 필요할 때 읽는다"이다.
- **형식 제약이 있다.** `fetch`는 텍스트 추출 기반이라 HTML·이미지·일부 바이너리는 내용을 못 읽는다. 그런 파일은 `download` 후 별도 처리가 필요하다.
- **쓰기는 권한과 실행이 별개다.** 쓰기 범위가 부여돼 있어도, 사용자가 명시적으로 지시하지 않으면 Muse는 Dropbox에 쓰지 않는다. 이번에도 0건이었다.
- **개인정보 노출 경계는 그대로다.** 폴더 안에 연락처 같은 개인정보가 있어도, Muse는 사용자가 명시적으로 물을 때만, 필요한 범위에서만 답한다. 폴더를 통째로 읽었다고 해서 그 안의 개인정보를 채팅에 풀어놓지 않는다.

## 7. 폴더 전체를 내려받아 쓰면 더 잘 답할 수 있나 (11/18 논의)

사용자 질문: "KACCWA 폴더를 Muse에 모두 다운받아서 사용하면, 로컬 데이터를 모두 참조해서 더 잘 알려줄 수 있지 않나? 왜 모두 다운로드하지 않았나?"

**기술적으로는 가능하다.** 186개 파일, 약 155MB. `download` 도구는 1회 최대 25개 항목이라 8회 정도 호출이면 전부 내려받을 수 있다.

**그런데 안 한 이유는, 내려받는다고 답이 좋아지지 않기 때문이다.**

1. **병목은 접근이 아니라 한 번에 읽을 수 있는 양이다.** 내려받아도 제가 한 번에 작업 기억에 담을 수 있는 양에는 한계가 있어서, 질문이 오면 결국 필요한 파일만 골라 읽게 된다. 지금 `fetch`로 필요할 때 읽는 것과 같은 방식이 된다.
2. **내려받은 사본은 금방 낡는다.** PC에서 파일을 고치면 Dropbox는 바로 동기화되지만, 내려받은 사본은 그 시점에 멈춰 있다. 필요할 때 Dropbox에서 직접 읽는 게 항상 최신본이다.
3. **대부분은 안 쓰인다.** 어제 하루 필요한 건 3개 파일이었다. 186개를 다 내려받아 두는 건 시간만 든다.
4. **내려받는 것만으로는 검색이 좋아지지 않는다.** 사본을 두는 것과 인덱스(무엇이 어디에 있는지 정리된 지도)가 있는 것은 다르다. 검색을 좋게 하려면 내려받은 뒤 텍스트 추출과 인덱스 구축이 따로 필요하다.
5. **최소화 원칙.** 필요한 파일만 읽는 것이 개인정보 노출 면에서도 낫다.

**전체 다운로드가 도움이 되는 경우도 있다.** 폴더 전체를 훑어야 하는 일괄 작업 — "전체 회의록에서 마감일을 다 찾아줘", "모든 파일에서 GOBI 언급을 찾아줘", "폴더별 내용 요약본을 만들어줘" 같은 경우다. 그럴 땐 내려받아 텍스트를 추출하고 인덱스를 만드는 것이 맞다. (미실행 — 사용자 결정 대기 중)

## 8. Obsidian 그래프 방식 자료, Muse 검색에 활용할 수 있나 (11/18 논의·검증)

### 사용자 데이터 관리 방식

- 로컬 파일은 대부분 **MD 형식**으로 정리돼 있고, 문서 안에 formatter나 관련 문서들의 **링크**가 있다.
- DB나 임베딩 방식으로 정리된 것이 아니라 **Graph 방식**이다. Obsidian을 쓸 때부터 이런 식으로 정리해 왔다.
- 즉, 정보 찾기는 "검색어로 뒤지는 것"이 아니라 "관련 문서를 링크로 따라가며 찾는 것"이 기본 동작이다.

### 검증 결과 (11/18, 실제 파일 확인)

- `2026-10-13 K-Startup Demo in Seattle 한국 선정 5개 스타트업 자료 정리 by Claude Code.md` 파일 하나에만 **`[[...]]` 위키링크 15개**가 들어 있다. 마크다운 링크 `[...](...)`는 0개다.
- 예시: `[[AI/Initiatives/KACCWA/20261012_Program/2026-10-12 K-Startup Demo in Seattle 참가안내 최종본 정리와 초안 대비 변경점 by Claude Code|참가안내 최종본 정리]]`
- Dropbox 내용 검색으로 `[[`를 직접 검색했을 때는 0건이 나왔으나(검색 인덱스 한계로 보임), 파일 본문을 열어 확인하니 링크가 실제로 존재했다. **검색 0건이 "링크 없음"을 뜻하지 않는다**는 점도 함께 확인됐다.

### Muse가 그래프를 쓰는 방식

- 질문이 오면 관련 노트에서 시작해 **나가는 링크(`[[...]]`)를 따라가고**, 반대로 **백링크**(그 노트를 가리키는 파일들)도 찾아 1~2단계까지 훑는다.
- 임베딩이 없어도 된다. 링크 자체가 "이 문서와 저 문서는 연결돼 있다"는 관계 정보라서, 따라가기만 하면 된다.
- 11/14 M4 테스트에서 위키링크 해석과 애매한 링크 처리(억지로 고르지 않고 애매하다고 밝히기)를 이미 경험한 바 있다.

### 그래프 방식의 장점

- **경로를 설명할 수 있다.** "이 답은 A 문서 → 링크 → B 문서에서 왔다"는 근거 경로를 그대로 보여줄 수 있다. 임베딩 검색은 비슷한 문서를 찾아주지만 왜 골랐는지 설명이 안 되는 경우가 많다.
- **명시적 관계라 정확하다.** 사람이 직접 연결해 둔 관계라, 주제와 직접 이어진 문서를 놓칠 확률이 낮다.

### 한계 — 검증에서 드러난 것 포함

1. **지속적인 인덱스가 아니라 그때그때 탐색이다.** 질문마다 목록을 보고 링크를 따라가서, 186개 규모에서는 되지만 느리고, 파일명이 조금이라도 다르면 링크를 놓칠 수 있다.
2. **링크 없는 관련 노트는 못 찾는다.** 그래프로는 내용만 비슷하고 링크로 연결되지 않은 문서를 찾을 수 없다. 키워드 검색과 병행해야 한다. 현실적인 조합은 **그래프 + 키워드 검색**이다.
3. **링크 경로 기준 문제 (검증됨).** 링크가 **볼트 루트 기준 경로**다 (`AI/Initiatives/KACCWA/...`, `Tasks/items/...`).
   - KACCWA 안의 대상은 접두사(`AI/Initiatives/`)를 떼면 연결된다. 실제 확인: 위 예시의 `2026-10-12 ... 참가안내 최종본 정리와 초안 대비 변경점` 파일이 `/KACCWA/20261012_Program` 안에 있다.
   - 반면 `Tasks/items/` 같은 KACCWA 밖을 가리키는 링크는 지금 상태에선 **막다른 길**이다. Dropbox 루트(11/18 확인)에는 `KACCWA`와 `Muse M4 Test - Synthetic` 폴더만 있고 `Tasks` 폴더가 없다. 해당 폴더도 Dropbox에 올려야 따라갈 수 있다.
4. **올린 범위 = 쓸 수 있는 범위다.** 그래프가 볼트 전체에 걸쳐 있어도, Dropbox에 올라온 부분까지만 따라갈 수 있다.

### 실용적인 다음 단계 (미실행)

- **그래프 인덱스 구축:** `/KACCWA` 안의 모든 MD 파일을 훑어서 각 노트의 나가는 링크·백링크·한 줄 요약을 뽑아 인덱스 파일로 저장한다. 다음 질문부터는 인덱스에서 출발해 훨씬 빠르고 빠짐없이 따라갈 수 있다.
- **링크 대상 폴더까지 함께 올리기:** `Tasks/items/` 등 볼트 내 관련 폴더를 Dropbox에 추가하면 그래프가 끊기지 않는다.

## 9. 로컬 데이터 관리 방식과 PC-off 환경에서의 AI 활용법 — 이번 테스트의 큰 그림

### 이번 테스트의 위치

사용자의 평소 방식은 **집 PC의 Obsidian 볼트(MD + 링크 그래프)**다. 이번 테스트는 "PC가 꺼진 집 밖에서도 로컬 데이터를 AI로 쓰기 위한 방법 중 하나"로서 **Dropbox–Muse 방식**을 실제 행사 상황에서 검증한 것이다.

### 과정 (재정리)

1. 로컬 폴더를 **복사**해 PC의 Dropbox 폴더에 넣는다 (원본 유지).
2. Dropbox 데스크톱 클라이언트가 클라우드로 동기화한다 (동기화 완료 확인이 전제).
3. Muse는 Dropbox API로 클라우드에서 읽는다. **이후 PC는 꺼도 된다.**
4. 질문마다 Muse가 목록을 보고 필요한 파일만 `fetch`/`download`로 읽는다.

### 더 잘 쓰려면 (어제 사례 기준)

1. **링크가 가리키는 폴더까지 함께 올리기.** `Tasks/items/` 등 볼트 내 관련 폴더를 추가하면 그래프가 끊기지 않는다 (8절).
2. **폴더 구조와 파일명을 일관되게 유지하기.** Muse는 목록(이름·크기·날짜)으로 위치를 찾는다. 이름이 바뀌면 링크도, 검색도 어긋난다.
3. **파일을 바꾸면 "바꿨어요" 한마디 하기.** Muse는 실시간으로 모른다. 변경 알림이 Muse가 다시 보게 하는 계기다.
4. **그래프 인덱스를 만들어 두기 (8절).** 질문마다 탐색하는 것보다 인덱스에서 출발하는 것이 빠르고 빠짐이 적다.
5. **자주 묻는 주제는 "공개 팩" 형태로 묶어 두기.** 이번 행사 팩이 이후 모든 행사 답변의 기준이 된 것처럼, 주제별 팩이 있으면 Muse가 일관되게 답한다.
6. **일괄 작업이 필요할 때만 전체 다운로드 + 인덱스 구축을 요청하기.** 평소 질문에는 필요할 때만 읽는 방식이 충분하고, 전체 훑기가 필요할 때만 7절의 방식을 쓴다.

### 리스크와 단점 (어제 사례 기준)

| 리스크·단점 | 어제 사례에서의 근거 |
|---|---|
| **최신성 — 동기화가 전제** | Muse는 질문할 때 새로 조회하지만, 동기화가 안 된 파일은 모른다. "올렸다"는 말이 없으면 Muse는 오래된 목록을 본다 |
| **부분 가시성 — 올린 범위만 쓸 수 있다** | `Tasks/items/` 링크가 Dropbox에 없어 막다른 길이 됐다. 그래프가 볼트 전체에 걸쳐 있어도 올린 부분까지만 따라간다 |
| **형식 제약** | HTML은 `fetch`가 빈 텍스트를 반환해 `download`가 필요했다. 이미지·바이너리도 마찬가지다 |
| **의미 검색 부재** | 링크 없는 관련 자료는 그래프로 못 찾는다. 임베딩 기반 의미 검색이 없어 키워드 검색 병행이 필요하다 |
| **Dropbox 의존성** | Dropbox 계정·연결 상태에 의존한다. 연결이 끊기면 못 읽는다. Drive는 대안이지만 계정 가시성 문제가 별도 (5절) |
| **개인정보 — 원본이 클라우드에 올라간다** | Muse는 필요한 파일만 읽지만, 열린 파일의 전문은 Muse의 작업 문맥에 들어간다. 연락처 등 민감 정보는 묻는 범위에서만 답한다는 경계는 유지되지만, 폴더 자체가 클라우드에 올라가 있다는 점은 인지할 것 |
| **단방향 읽기 — 쓰기가 돌아오지 않는다** | Muse가 만든 정리본·스크립트는 Muse 워크스페이스에만 있고 Dropbox·PC로 돌아가지 않는다. 정리본을 로컬에서 쓰려면 따로 내려받아야 한다 |
| **비용 — 전체 작업은 시간과 호출량이 든다** | 전체 다운로드·인덱스 구축은 186개 파일 기준으로도 적지 않은 작업이다. 필요할 때만 하는 것이 맞다 |

## 10. 결론 (업데이트)

- **테스트는 성공했다.** PC를 끈 상태에서도, 로컬 폴더를 Dropbox에 복사·동기화만 해 두면 Muse는 클라우드를 경유해 행사 자료를 참조해 답할 수 있었다. 11/14 PC-off 테스트의 증명이 실제 행사 자료로 재현됐다.
- **방식은 "전체를 내려받아 저장"이 아니라 "목록을 보고 필요한 파일만 그때그때 원격으로 읽는" 방식이다.** 186개 중 내용을 읽은 것은 3개 파일뿐이고, Dropbox 안에 수정·생성된 파일은 0건, Muse 컴퓨터에 남는 KACCWA 사본도 없다.
- **전체 다운로드는 가능하지만 답을 좋게 만들지 않는다.** 병목은 접근이 아니라 한 번에 읽는 양과 인덱스 부재다. 폴더 전체를 훑는 일괄 작업 때만 의미가 있다.
- **그래프 방식은 Muse 검색에 활용 가능하다. 검증됐다.** 파일 하나에 위키링크 15개, 따라갈 수 있다. 단, 지속 인덱스가 없고, KACCWA 밖 링크는 지금 상태에선 안 열린다. 그래프 인덱스 구축과 링크 대상 폴더 추가가 다음 단계다.
- **Dropbox 선택의 핵심 이유는 "이미 연결 + PC-off 증명 완료 + 계정 갈림 없음"이었다.** Drive도 본인 계정 파일에는 쓸 수 있지만, 당일 확인된 상공회의소 계정 가시성 문제와 증명 부재 때문에 1순위가 아니었다.
- **더 잘 쓰려면:** 링크 대상 폴더까지 올리고, 구조·파일명 일관 유지, 변경 시 알리기, 그래프 인덱스 만들기, 주제별 팩으로 묶기. 일괄 작업 때만 전체 다운로드를 쓴다.
- **리스크 요약:** 동기화 전제, 부분 가시성(올린 범위만), 형식 제약, 의미 검색 부재, Dropbox 의존, 단방향 읽기, 개인정보는 클라우드 원본에 있다는 점 인지.
- **다음에 같은 방식을 쓸 때:** 폴더를 Dropbox에 복사 → 동기화 완료 확인 → "됐어요" 한마디면 Muse가 목록을 보고, 질문마다 필요한 파일만 읽는다. PC는 꺼도 된다.
