# Episode Scripts 초안

## EP1 - FDE란 무엇인가

### 30초 Hook

"AI 시대에 기업들이 원하는 것은 멋진 데모가 아니라 실제 업무에 들어가 반복 사용되는 시스템입니다. Forward Deployed Engineer는 바로 그 사이, 제품팀과 고객 현장 사이에 서는 역할입니다."

### Narration Flow

1. FDE는 software engineer, consultant, solutions engineer의 일부를 섞은 역할처럼 보이지만 핵심은 production adoption이다.
2. 고객의 모호한 문제를 듣고, 업무 흐름과 데이터를 파악하고, 작동하는 prototype을 만들고, 실제 배포 가능한 형태로 좁혀 간다.
3. FDE의 산출물은 코드뿐 아니라 discovery note, architecture, eval, rollout plan, product feedback이다.
4. AI 시대에는 model capability가 빠르게 변하지만 고객 조직의 업무와 데이터는 복잡하기 때문에, 이 둘을 연결하는 사람이 더 중요해졌다.

### Closing Line

"FDE는 고객 현장에서 제품이 실제로 쓰이게 만드는 엔지니어링 역할입니다."

## EP2 - Palantir에서 AI FDE까지

### 30초 Hook

"FDE라는 이름을 유명하게 만든 회사는 Palantir입니다. 하지만 2026년의 FDE는 Palantir만의 이야기가 아니라 OpenAI, Cursor, Scale AI 같은 AI 기업들의 채용 언어가 되었습니다."

### Narration Flow

1. Palantir형 FDE는 고객 운영 문제를 플랫폼 위에 모델링하고 현장에서 직접 배포하는 방식으로 알려졌다.
2. 이 원형에서 변하지 않은 것은 embedded delivery, operational workflow, reusable pattern이다.
3. 달라진 것은 기술 중심이다. 이제는 ontology와 enterprise data뿐 아니라 LLM, RAG, agent, eval, AI workflow adoption이 들어온다.
4. AI 기업들은 고객이 모델을 "써보는 것"을 넘어 실제 업무 시스템에 넣도록 돕는 역할을 필요로 한다.

### Closing Line

"AI FDE는 Palantir식 현장 배포 모델이 생성형 AI adoption 문제와 만난 결과입니다."

## EP3 - OpenAI, Cursor, Scale AI의 FDE는 어떻게 다른가

### 30초 Hook

"FDE라는 title이 같아도 회사마다 실제 일은 다릅니다. 어떤 회사는 frontier model deployment에 가깝고, 어떤 회사는 개발자 workflow 전환, 어떤 회사는 public sector data infrastructure에 가깝습니다."

### Narration Flow

1. OpenAI형 FDE는 고객의 complex workflow를 model/API/custom software로 연결하는 성격이 강하다.
2. Cursor형 FDE는 개발팀의 AI-native coding workflow adoption과 debugging, eval, latency/cost trade-off에 가깝다.
3. Scale AI형 FDE는 data, agent, public sector, compliance-heavy deployment 맥락이 강하다.
4. Hebbia 같은 vertical AI 회사는 금융, 법률, 지식노동 workflow를 깊게 이해하는 FDE가 중요하다.
5. 지원자는 title보다 공고의 동사를 읽어야 한다. build, deploy, integrate, evaluate, unblock, generalize가 반복되면 FDE형이다.

### Closing Line

"좋은 지원 전략은 FDE라는 이름이 아니라 회사별 FDE archetype을 읽는 데서 시작합니다."

## EP4 - FDE가 되려면 어떤 기술을 알아야 하나

### 30초 Hook

"FDE가 모든 기술을 최고 수준으로 알아야 하는 것은 아닙니다. 하지만 고객 현장에서 AI workflow를 production에 가깝게 만들 만큼의 기술 판단은 반드시 필요합니다."

### Narration Flow

1. AI FDE delivery lifecycle은 discovery, scoping, prototype, eval, integration, rollout, handoff로 볼 수 있다.
2. discovery에서는 고객 업무와 data readiness를 읽고, prototype에서는 빠르게 작동하는 demo를 만든다.
3. eval 단계에서는 hallucination, answer quality, routing accuracy, human review 기준을 측정한다.
4. integration과 rollout에서는 API, auth, data boundary, observability, cost/latency, security를 다룬다.
5. FDE에게 중요한 기술력은 혼자 모든 것을 완성하는 능력보다 고객 제약 안에서 올바른 trade-off를 고르는 능력이다.

### Closing Line

"AI FDE의 기술 스택은 모델 사용법이 아니라 production adoption을 위한 판단 체계입니다."

## EP5 - 주니어, 시니어, 비IT 배경자의 진입 전략

### 30초 Hook

"FDE로 가는 길은 배경마다 다릅니다. 주니어는 증거를 새로 만들어야 하고, IT 시니어는 기존 경험을 번역해야 하며, 비IT 배경자는 인접 역할을 통해 들어가는 편이 현실적입니다."

### Narration Flow

1. 주니어는 FDE 직행이 쉽지 않기 때문에 RAG assistant, workflow automation, eval dashboard 같은 portfolio proof가 필요하다.
2. IT 시니어는 이미 delivery, 운영, stakeholder 경험을 가지고 있다. 문제는 이를 FDE 언어로 바꾸고 AI/LLM production gap을 채우는 것이다.
3. 비IT 배경자는 domain expertise가 강점이지만 technical minimum이 부족하면 FDE 직행이 어렵다.
4. domain solution specialist, AI consultant, implementation analyst, GTM engineer는 현실적인 bridge role이 될 수 있다.
5. 한국 AX, 일본 DX to AX, 유럽 regulated AI는 미국 FDE와 연결되지만 같은 개념은 아니다. 시장별 언어 차이를 이해해야 한다.

### Closing Line

"FDE 준비는 하나의 길이 아니라 배경별로 다른 증거를 만드는 과정입니다."

## EP6 - FDE 포트폴리오와 면접 준비

### 30초 Hook

"FDE 포트폴리오는 예쁜 앱이나 GitHub repo 하나로 끝나지 않습니다. 채용자가 보고 싶은 것은 고객 문제를 실제 시스템과 adoption metric으로 바꾸는 능력입니다."

### Narration Flow

1. 좋은 FDE 포트폴리오는 customer scenario에서 시작한다.
2. architecture에는 데이터, API, LLM, eval, observability, security boundary가 보여야 한다.
3. demo script는 5분 안에 고객 문제, AI workflow, eval, rollout을 모두 전달해야 한다.
4. 면접에서는 바로 solution을 말하기보다 discovery question, constraint, pilot metric, next experiment를 제시하는 것이 중요하다.
5. 최종 지원 패키지는 one-page narrative, portfolio README, architecture diagram, demo script, resume bullets, interview bank로 구성한다.

### Closing Line

"FDE 지원자는 코드를 보여주는 것이 아니라, 고객 현장에서 작동할 시스템을 설계하고 설득하는 증거를 보여줘야 합니다."
